# 文件脉络视图与目录审计

## 1. 需求与消费过程

L2 的真实消费过程（用户 2026-07-17 阐明）：**先看整个文件的脉络**（有哪些节、
表和附注不能漏）→ 自行分块 → 块内精查，偶尔跨块补查；几乎不跨公司查询。
因此 L1 对 L2 最重要的交付不是模糊搜索，而是：
1. 开篇一眼看清文件骨架（脉络视图）；
2. 骨架必须完整可信（目录审计兜底解析缺漏）。

## 2. 语料证据（2026-07-17 取证）

- 标题路径深度分布（86,252 单元）：1 级 7,831 / 2 级 13,439 / 3 级 27,767 /
  4 级 28,148 / 5 级 7,820 / 6+ 级 1,247——结构修复后细脉络真实存在，
  典型年报根标题恰为十节法定章节 + 封面件（大地熊样本 14 根全部合规）。
- 目录页单元文本干净可机读：两种主形态「节名….页码」（万科）与
  「页码 节名」（招商银行，含 3.1–3.12 子节）。
- 目录粒度是基线而非上限（用户判断成立）：招行目录列到二级，实际标题树到 4+ 级。

## 3. 第一步：文件脉络视图（derived，先实施）

**形态**：`disclosure_public.document_outline_v1` 派生视图（U7 红线同 06R 投影：
可从单元表确定性重算、不入 content_hash、不发 outbox、非证据）。

每行 = 一份文档的一个标题树节点：

| 列 | 含义 |
|---|---|
| document_id | 文档 |
| path / depth | 标题路径（jsonb）与深度 |
| unit_count / table_count / image_count | 该节点直属单元数按类型 |
| semantic_keys | 该节点直属单元的去重标签集 |
| page_span | 该节点单元的页码范围 |
| first_order_index | 排序锚 |

实现为普通 SQL 视图（GROUP BY document_id, heading_path 即可，无新表、无迁移
数据）；若性能不足再物化。L2 开篇 `SELECT * FROM document_outline_v1 WHERE
document_id = X ORDER BY first_order_index` 即得全骨架。

**验收**：视图行数=各文档 distinct heading_path 之和；抽样 5 份文档人工比对
骨架与 PDF 目录；契约导出与 reader 授权同 06R。

## 4. 第二步：目录审计（先审计后修复）

**原则**：目录反哺解析，从审计信号做起，有证据再升级为修复信号
（对标 docling-hierarchical 的 TOC-anchor：它直接用 PDF 书签重排；我们语料书签
覆盖仅 15%，改用文内目录页，且先只报不改）。

**实现**：`scripts/audit_toc_alignment.py`（离线审计，进语料审计工具族）：
1. 取每份文档 table_of_contents 标签单元的文本，解析成节名列表
   （两种形态的行文法：行首/行尾页码、点线分隔；解析失败按文档记录，不猜）；
2. 与该文档实际标题树（脉络视图）做规范化匹配（去空白/标点，前缀含关系）；
3. 输出三类 finding：`toc_section_missing_in_tree`（目录列了、树里没有——
   最重要，指向解析丢标题）、`tree_root_missing_in_toc`（树里有根、目录没列——
   多为封面件/附件，通常合法）、`toc_unparsable`；
4. 汇总按文档/发行人/文类分布，供人工定损与后续修复设计。

**升级路径（有证据才走）**：若 `toc_section_missing_in_tree` 揭示系统性丢标题
家族，把目录节名注册为仲裁框架的 S0' 信号槽（heading-level-arbitration.md §3
的阶梯顶端补一档「文内目录锚点」），进入正常的设计-验证循环。
→ **已走通（同日）**：首次审计的招行家族（71% 缺失）即此类——章首 heading 存在
但无前缀，被锚定吞章。S0' 已实装（见仲裁文档 §5），解析与 title path 现在
以目录为 base（用户方向）；共享解析器在 `unit_builder/toc_outline.py`，
审计与构建同源。

## 5. 首次审计结果（2026-07-17）

94 份有目录文档 / 1,217 条目录项 / 95.4% 命中标题树；56 条缺失分布 18 份文档：

- **招商银行 5 份定期报告 ×8 章 = 40 条（71%）**：目录列的 第一章~第九章
  （公司简介/会计数据摘要/管理层讨论与分析/ESG/公司治理…）在标题树中**整族
  缺失**——2023 年报全树仅 11 个根且全为封面件（提示/致辞/释义/目录），
  正文章标题被 vlm 对招行特殊章头排版整族漏检，正文单元全部错挂。此前假根
  等指标对"漏标题"不可见，仅目录比对可捕获。→ 修复设计的头号输入
  （候选：核查该章头在 IR 中的原始形态，评估目录锚定恢复即 §4 升级路径）。
- 权益变动报告书 3 份：断行碎片（解析伪缺失）+ 附表标题真缺失，小家族。
- 平安银行 2023 半年报：释义 单节缺失。
- 1 份目录不可解析（记录在案）。

**残余定性与根治（同日闭环，ub-2026.07-65/66）**：逐案 PDF 目验 + IR 解剖后，
16 条残余中 12 条同根因——**MinerU 表题吸收**：节标题紧贴首表时被折进
`table_caption`（平安释义×5、权益变动附表×6、宁德第十节×1），标题以结构化
字段完好保存。根治：退化档中表题满足强证据（自带第X章/节前缀、FIXED_L1、
目录声明顶层条目）即开节（复用 qa 附件的表题栈机械，`(续)` 续表不重开同名节）。
另 2 条审计假阳性由断行拼接+近似匹配消除；美的短横线页码（"- 3 -"）纳入第三种
页码文法；工行组织机构图整页为图，如实保留上报（不做 OCR 提升）。

## 6. 全库重解析回归（2026-07-18，ub-2026.07-68）

语料从 13 家扩到 1,353 家并从原始 PDF 全量重解析后，S0' 在 19/1,377 份
设计版式报告（大行定期报告、偿付能力摘要）上失效，最重工行 2023 年报
1,019/1,233 单元吞在目录根下。根因是 S0' 的三个排版偶然假设：页码与标题
同行、条目 kind==text、顶层必有第X章前缀。实际形态五种：裸标题+页码分列
（aside_text，招行）、条目被判 heading（平安/能辉）、阿拉伯顶层编号
「1. 释义」（工行）、空格页码「1 财务摘要 7」（建行）、中文序号顶层
「一、」（太保）。MinerU 官方契约确认目录页码预期即 aside_text、标题可为
text/title 块；Docling 用专设标签使目录行永不入标题树——两者定形本轮不变量：

- **目录由枚举结构定义**，与页码排版位置、元素 kind 无关。枚举族分级
  第X章 > 一、 > 1.，块内最高族为顶层；多级点号（3.1）恒为子条目；
  无前缀条目仅在未进入子结构前声明顶层（附表在章后仍算，专栏/热点不算）。
- **fail-closed 边界**：裸条目（无页码）与弱枚举门（中文序号/阿拉伯族，
  需 ≥3 递增序列）仅在自带「目录」标记的页面生效；无锚页面维持法定
  第X章+行内页码严门；<5 条目的块永不合格（鹏鼎 4 条小目录合法拒绝）。
- **目录区守卫（Docling 式）**：合格目录页上「标题+页码」形状的 heading
  是目录条目而非节首，降级为文本（曾泄漏为假根「第三章 …… 17」）。
- **目录声明压过编号惯例**：退化档中剥前缀后命中声明键的正文标题无条件
  开新根（工行「1. 释义」按点号文法本会挂深层）。

验证：19 份病例 rebuild-units 全部治愈（招行年报 11 假根形状→17 健康根），
全库 1,414 份批量重切至 ub-68。**残余家族（独立证据轮，不在本轮混修）**：
①中报附属财报册自带目录吞尾部（平安 p83 起 318 单元、建行 p100 起 556 单元
挂册封根下）；②工行「公司基本情况简介」小项编号与章号同族碰撞（11. 股份
登记处 等成根）；③个别节标题+表题双根。

## 7. 明确不做

- 不用目录直接改写标题树（未经审计验证的修复信号违反"低可靠证据不砍祖先"）；
- 不为脉络视图建新表/迁移（视图纯派生；物化仅在实测性能不足后）；
- 不做跨公司聚合面（L2 不跨公司查询）。
