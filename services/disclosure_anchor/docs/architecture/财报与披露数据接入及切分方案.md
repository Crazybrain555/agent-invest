# 财报与披露数据接入及切分方案 v1.0

> 本文件定义财务数据与披露文件如何进入投研预测引擎，以及财报、投关记录和公告应如何被切成 L2 可直接使用的对象。它是 `disclosure_anchor` 的**接入与切分实施方案**：术语、边界和硬决策以 `service-purpose.md`（canonical 契约）为准，本文件在其框架内给出标准数据 provider 分工、PDF 补充范围、切分细则和实施顺序。数据库、解析和接口实施文档应同时遵循两者。

# 0. 执行摘要

第一版从一开始就覆盖 **≥500 只人工精选股票**（研究员精选名单 → `tracked_companies`）的调度化批量接入，不是先跑几家样本的 POC。用几份样本 PDF 验证解析工具属于 pre-v1 的门槛步骤（见 §16 Phase 0），不是交付目标；交付规模与 `service-purpose.md` frontmatter `run_model: scheduled_incremental_polling` 一致。

第一版采用两条互补的数据路径：

```text
标准、可复用、已有 provider 覆盖的数据
→ Dataset API
→ 直接交给 L2 / L3

自维护公告和财报 PDF
→ disclosure_anchor
→ document + document_unit
→ 交给 L2
```

核心决策如下：

1. 标准数据 provider（Wind / Tushare / 同花顺 iFinD / Choice 等）和 PDF 属于同一逻辑 `L1`，但不塞进同一种物理表；具体用哪家 provider 可替换，不影响架构。
2. provider 已覆盖的三大表、标准财务指标、审计意见等不在本服务重建为第二套标准化 dataset；
   PDF 中实际出现的正文和表格仍作为 source-faithful evidence 发布。
3. PDF 主要补充经营细分、财务附注、管理层解释、问答和重大事项原文。
4. PDF 按 parser typed heading、文档自身 TOC、通用 outline 与版面关系形成完整结构块；
   不按业务词表、页码或 token 决定边界。问答语义由 L2 从完整上下文抽取。
5. 切分结果统一称为 `document_unit`；新 run 生成 `text / table / mixed`，`qa` 仅用于读取历史行；
   `mixed` 保存同一 heading occurrence 内有序的文本/表格/视觉 parts。
6. `heading_path` 是逻辑标题路径，不是 Markdown 文件地址；回到 parser artifact 使用可选 `artifact_locator`。
7. 表格第一阶段保留完整结构，不拆 cell，不急着建立全市场标准表。
8. 只有经过实际复用证明的表族，才从 `table unit` 晋级为标准 dataset。
9. 短公告不在 L1 生成 canonical `event_unit`；事件由 L2 抽取。
10. page/bbox 不成为独立业务实体，但必须保留在 artifact locator/provenance 中供证据定位；
    不常态化持久化 chunk/table_cell，也不默认运行多 parser 全量对账。
11. parser 或切分形态变化不触发 L3；真实内容、数字或来源值变化才触发。
12. 原始 PDF 和 parser artifact 保留；派生层只能删除由 source type + 位置/重复关系闭合证明的
    page furniture/空 carrier，不能按业务价值大胆去噪。

这套方案的目标不是完整复制 PDF，而是：

> 以尽可能小的数据库和解析复杂度，让 L2 稳定找到 L3/L5 当前真正需要的数据与原文。

# 1. 总体架构

## 1.1 L1 的两条主路径与其他来源

| L1 标准数据路径 | L1 披露文件路径 | L1 其他来源（非标，旁路） |
| --- | --- | --- |
| Wind / Tushare / 同花顺 iFinD / Choice / API | CNINFO / 交易所 PDF | 非标 API / MCP / Web / 搜索 |
| Dataset Registry → Provider Adapter → `Dataset API` | `disclosure_anchor` → `document` / `document_unit` → `Filing API` | 通用 `source_access`（登记为 `data_asset`/`source_ref` 后进 L2，不建 `document_unit`） |

三条路径最终都在 `L2` 汇合 →（抽取 claim / 事件 / 口径 / 冲突）→ `L3` 证据账本。

前两条是主路径，二者在职责上同层：都是来源接入与可用化。

二者在数据形态上不同：

- 标准数据 provider 返回标准记录；
- PDF 返回文档结构单元。

因此统一发生在访问契约和 L2 消费层，而不是底层数据库表。

（第三列“其他来源”是更轻的旁路：非标 API、MCP、Web、搜索经通用 `source_access` 直接进 L2，不强求转成 `document_unit`，详见 §1.2。）

## 1.2 第三类来源

Web、MCP、搜索、新闻和其他一次性 API 返回，由对应 L1 adapter 登记为 `data_asset`（携带通用 `source_access/source_ref` provenance）后进入 L2。

第一版不要求把这些来源全部转成 `document_unit`，也不要求 `disclosure_anchor` 承担它们。

# 2. 标准数据 provider 与 PDF 的分工

> **标准数据侧是 provider 无关的。** 下文以 Wind 为具体示例，但 Wind 只是首版采用的一个 provider，可整体或按 dataset 替换 / 并存为 Tushare、同花顺 iFinD、Choice 或其他数据源。抽象由 `dataset_registry`（语义 `dataset_key`）+ `provider_adapter`（各家参数与字段映射）承担：`dataset_key` 与具体 provider 解耦，下游 L2 只认 `dataset_key` 和返回模型，不感知背后是哪家。§2.1 的 `AShare*` 表名是 Wind 的内部对象，换 provider 时由对应 adapter 映射到相同的 `dataset_key`。

## 2.1 标准数据 provider 作为 operational primary（以 Wind 为例）

以首版采用的 Wind 为例，标准财务数据覆盖如下。换用其他 provider 时，由各自 `provider_adapter` 映射到相同的 `dataset_key`，下游不感知差异。

## 2.2 第一版不从 PDF 重建这些数据

以下内容默认不建立第二套本地标准表：

- 三大财务报表；
- 标准财务指标；
- TTM / MRQ 和衍生指标；
- 业绩预告、业绩快报的标准字段；
- 审计意见；
- 会计变更；
- 银行、券商、保险等专用标准指标。

PDF 中仍保留原文和 parser artifact，但默认不把这些表转换成核心 `document_unit(table)`。

## 2.3 不做日常双源核验

第一版把配置的标准数据 provider（首版为 Wind）当作日常使用的默认来源：

```text
operational_primary = <标准数据 provider>   # 首版配置为 Wind
```

不要求每次都重新解析 PDF，也不要求逐项双源对账。

只有出现以下情况才回到正式披露：

- provider 缺字段；
- 更正公告或追溯重述；
- 合并 / 母公司口径疑问；
- 报告期或单位异常；
- 关键数字明显不合理；
- L2/L3 需要公司原文解释；
- 重要预测节点需要加强复核。

因此正式披露是：

```text
authoritative_fallback
```

而不是常态重复数据源。

## 2.4 provider 数据的 as-of 快照

不需要把 provider 全库复制到本地，但进入 claim、假设或预测的值必须保存当时快照：

```text
dataset_key
provider
query params
queried_at
field
value
unit
period
scope
source_access_id
```

这样以后 provider 修订历史值时，仍能复盘当时预测使用了什么。

# 3. PDF 应该补什么

## 3.1 经营细分表

以下主题可在 L2 检索中优先排序：

- 分行业收入、成本和毛利率；
- 分产品收入、成本和毛利率；
- 分地区、分渠道和分客户类型；
- 产量、销量和库存量；
- 成本构成；
- 前五大客户和供应商集中度；
- 主要子公司和分部经营数据；
- 研发项目、研发投入和人员；
- 产能、扩产项目和资本开支。
等其他重要内容（以上只是我初步设想的）


这些表通常结构可复用，但公司维度值不同，因此第一阶段保存为完整 `table unit`，不建立统一产品字典。

## 3.2 财务附注表

优先提取：

- 应收账款账龄；
- 坏账准备和计提比例；
- 存货分类和跌价准备；
- 固定资产和在建工程；
- 债务结构及到期情况；
- 资产减值；
- 外币资产负债敞口；
- 重要子公司、联营企业和分部；
- 合并范围变化；
- 重大承诺、或有事项和关联交易；
- 与当前驱动树直接相关的其他附注。
等其他重要内容（以上只是我初步设想的）

这些表先作为 `table unit`，之后根据使用频率晋级。

## 3.3 管理层解释和业务文本

优先提取：

- 主营业务和产品结构；
- 行业变化；
- 价格、销量、订单、客户和渠道变化；
- 产能利用率、扩产和投产节奏；
- 毛利率、费用、现金流和资产负债变化原因；
- 技术、认证和新产品进展；
- 并购、合并范围和组织变化；
- 关键审计事项；
- 风险；
- 未来展望；
- 与个股预测驱动树相关的其他解释。
等其他重要内容（以上只是我初步设想的）

L1 不以该清单筛选内容；所有主题仍按 PDF 源结构保存。

## 3.4 投资者关系问答

投关活动记录、业绩说明会和公开交流按 PDF 的标题结构与 carrier 顺序保存。L1 不因为答案很长
按 token 拆碎，也不靠“问/答”短语强制生成 `qa unit`；L2 可从完整 source evidence 派生问答视图。

## 3.5 短公告和重大事项

分红、回购、定增、股权激励、重大合同、产能投资、并购等公告，第一版仍切成 `text/table` 单元。

事件结构化由 L2 完成：

```text
text/table unit
→ L2 识别 event_kind 和字段
→ event claim / 事件对象
```

这样 L1 不会逐渐膨胀成事实层。

# 4. 标准化的三段式路径

> 注：本节 A/B/C 是数据来源与标准化程度的分级（provider 已覆盖 / 表族待晋级 / 公司特有），不是清洗规则分类；顶层协议已废止的「A 类清洗 / B 类清洗」由 L1 载体规范化 + L2 证据化/语义归一取代，与此处无关。

用户提出的原则“可复用就标准化，不可复用就按主题保存”是正确方向，但第一版需要增加中间态。

## 4.1 A 类：provider 已覆盖的标准数据

直接通过 Dataset API 使用。

例子：

```text
financial.income_statement
financial.balance_sheet
financial.cash_flow
financial.indicators
financial.audit_opinion
```

不进入 `document_unit`。

## 4.2 B 类：可复用但尚未证明值得标准化的表族

先保存为 `table unit`。

例子：

```text
产品收入和毛利率
产销量和库存量
应收账款账龄
存货分类
在建工程明细
前五大客户
```

它们具有稳定的表语义，但公司业务维度、表头层级和披露细节不完全统一。

第一阶段只要求：

- 表能完整读出；
- 标题和单位清楚；
- 行列关系不丢；
- L2 能检索和引用。

## 4.3 C 类：公司特定或难复用的内容

保存为 `text` 或 `qa`。

例子：

- 某产品认证节奏；
- 特定客户导入；
- 某产线的技术改造；
- 管理层对库存增加的解释；
- 公司特有技术路线。

## 4.4 table unit 晋级标准 dataset 的条件

只有同时满足以下条件才晋级：

1. 多家公司或多期反复出现；
2. 字段语义相对稳定；
3. L2/L3/L5 反复查询；
4. 标准数据 provider 没有可靠覆盖；
5. 抽取质量可通过简单规则校验；
6. 标准化后的收益大于 schema 和维护成本。

晋级后：

```text
table unit 仍然保留
+ 新增一个 dataset adapter / standardized view
```

标准 dataset 不覆盖原始文档单元。

首批可能晋级的候选：

- `financial_notes.receivable_aging`；
- `financial_notes.inventory_composition`；
- `operating.volume_sales_inventory`；
- `operating.segment_revenue`；
- `operating.capex_projects`。

是否晋级以真实调用记录为准，不在第一版预判。

# 5. document_unit 模型

## 5.1 定义

`document_unit` 是披露文件中最小的 L1 可寻址结构单元。

它不是：

- page；
- parser block；
- RAG chunk；
- table cell；
- claim；
- event fact。

一条 unit 可以在 L2 中产生零条、一条或多条 claims。

## 5.2 通用契约

```text
asset_id
document_id               内部 UUID
provider_document_id      provider 侧标识（如 CNINFO textid），可选
processing_run_id
payload_kind              text / table / qa / mixed
heading_path              逻辑标题路径
title
order_index
semantic_key              可选受控 Unit 级 primary 路由键；证据不足时为 NULL
semantic_keys             完整有序 route set；首项等于 semantic_key，可保留 mixed Unit secondary recall
payload                   正文 / 表格 / 问答
content_hash
quality_status
artifact_locator          可选
```

## 5.3 heading_path

`heading_path` 是标题面包屑，而不是 Markdown 文件地址。

例如：

```json
[
  "第三节 管理层讨论与分析",
  "一、报告期内公司从事的主要业务"
]
```

它是 agent 和 L2 的逻辑地址。

## 5.4 artifact_locator

`artifact_locator` 是可选的技术地址，可用于回到：

- Markdown；
- parser JSON；
- 表格 HTML；
- 其他解析产物。

它可以只保存：

```text
artifact_path + artifact_unit_ref + order_index
```

第一版不要求 page、bbox 或字符偏移。

## 5.5 text payload

```json
{
  "text": "机械清洗后的完整正文"
}
```

## 5.6 table payload

以江海股份（002484）2025 年年度报告“应收账款 / 按账龄披露”为例：

```json
{
  "unit": "元",
  "headers": ["账龄", "期末账面余额", "期初账面余额"],
  "rows": [
    ["1 年以内（含1 年）", "1,765,831,017.43", "1,653,778,854.38"],
    ["1 至2 年", "23,872,757.96", "35,360,192.57"],
    ["2 至3 年", "14,382,374.82", "7,076,511.89"],
    ["3 年以上", "73,573,362.32", "78,454,116.92"],
    ["3 至4 年", "1,443,796.67", "11,272,000.94"],
    ["4 至5 年", "5,272,677.17", "450,708.56"],
    ["5 年以上", "66,856,888.48", "66,731,407.42"],
    ["合计", "1,877,659,512.53", "1,774,669,675.76"]
  ],
  "notes": [],
  "nearby_explanation": ""
}
```

表格保留原始字符串。第一版不要求把每个值转换成统一 metric。

> 注意原表中“3 年以上”为小计行，其下再拆“3 至4 年 / 4 至5 年 / 5 年以上”三个子区间；下游做“合计 = 各账龄之和”校验时应避免重复计数。这类小计与明细并存的结构由 L2 在使用时识别，L1 只忠实保留原始行。

## 5.7 qa payload

```json
{
  "question": "美国加征关税对公司有什么影响？",
  "answer": "完整回答"
}
```

会议时间、地点、参与人和活动类型放在 `document` 元数据中，不必在每个问答中重复。

# 6. 文本和表格的切分规则

## 6.1 结构边界优先级

```text
文档标题
→ 章节
→ 子章节
→ 显式编号条目
→ 完整 Q&A
→ 完整表格
→ 完整事项说明
```

## 6.2 不采用的边界

第一版不按以下方式持久化切分：

- page；
- 固定字符数；
- 固定 token 数；
- overlap；
- parser block；
- 每个单元格。

## 6.3 长文本

存在真实子标题时继续按子标题切。

没有更细真实结构时，即使内容较长，也保持一个完整 `text unit`。agent 运行时可以临时截取，不创建长期 chunk。

## 6.4 跨页表

跨页首先是需要被**独立证明**的关系，而不是 parser 改写 evidence 的理由。生产 MinerU
关闭跨页表合并；canonical table 一张只对应一个物理页。content/model 必须通过同页唯一
bbox 与 logical-cell 精确相等完成一一闭合，并保留本页 HTML、grid、crop 与 locator。
任一侧缺失、为空、歧义或不等价都使 parse 失败，不能发布 aggregate/ghost 占位，也不能
用 `needs_review` 代替查清 parser 缺口。

若下游需要“这些页内表属于同一逻辑表”，应在 canonical evidence 之上发布独立可审计关系；
它不得拼接行、抑制续页表头、改变 table payload/hash 或反向决定章节边界。业务词、caption、
标点或 taxonomy 不得参与正向结构判定。

## 6.5 相邻解释

表格 caption、单位、脚注和同一 typed heading occurrence 下连续的解释按源顺序进入同一
evidence cluster。归属来自标题 occurrence 和 parser relation，不来自“离得近”或主题词命中。
若发布为多个 unit，检索投影必须仍能按同一结构 occurrence 无歧义召回完整 cluster。

# 7. 不同文件类型的处理方案

## 7.1 年报、半年报和季报

处理流程：

```text
识别标题树
→ 验证 source carrier 与标题 occurrence 的归属
→ 按源顺序保存 text/table/image/caption/footnote
→ 生成完整 evidence blocks
→ 在边界完成后追加 retrieval taxonomy
```

净利润驱动树只决定 L2 检索优先级，不决定 PDF 哪些章节存在。

## 7.2 投资者关系活动记录和业绩说明会

```text
文档元数据
+ Q1 / A1
+ Q2 / A2
+ ...
```

L1 按 PDF 的 typed heading 与 source carrier 保存完整内容，不靠问句/“答：”词面重切。
Q/A 识别和一个答案中的数字、观点、时间范围均由 L2 在原证据上抽取。

## 7.3 业绩预告和业绩快报

- 标准区间、净利润等字段可优先从标准数据 provider 使用；
- PDF 仍完整保留标准字段、变动原因、一次性项目、口径说明和管理层解释；
- provider 缺失或需要原文时，再由 L2 从 unit 中抽取字段。

## 7.4 分红、回购、定增和股权激励公告

第一版按可回放的显式章节生成完整 evidence blocks。

不在 L1 直接形成 canonical event。L2 可以从中抽取：

- 分配基数；
- 每股金额；
- 登记日和除权日；
- 回购数量和价格；
- 募集规模；
- 激励对象和考核条件等。

## 7.5 问询函和回复

按源标题结构保存问题、回复和表格；是否形成 Q/A 视图属于 L2。

## 7.6 普通重大事项公告

短公告没有下级标题时以登记文档标题作为单一结构锚点；其下文字和表格保持源顺序。只有 PDF
显式标题结构能证明多个事项边界时才拆分。

# 8. 证据守恒与检索路由

## 8.1 canonical evidence

每个非空 source carrier 均须满足以下之一：

- 作为 payload、heading、caption、footnote、applicability 或视觉证据发布；
- 被一个封闭的 source-type + 位置/重复关系证明为外部版面元数据，并有 disposition ledger；
- 为空或不可用的二进制载体，且该事实可由源字段直接验证。

目录、责任声明、会计政策、标准报表、签章、联系方式和 provider-covered 内容只要含独有文本，
就仍是 canonical evidence。它们可以低排序，但不能因业务价值判断消失。

## 8.2 可确定不生成独立业务 unit 的载体

范围仅限：

- parser 明确标注、且位置/重复证据一致的页码或 running furniture；
- 当前 parser 不接受的空 table carrier（若 provider 产出则解析失败并追查来源，不进入 unit）；
- 没有内容寻址资产、caption 或可读文本的空视觉 carrier；
- 与登记 metadata 精确相等、且 source role 明确的重复 header 字段。

原 PDF/parser artifact 的存在不能替代可检索 unit；非空内容若没有位置或关系证据，必须追查
MinerU page/model/middle/content-list 或页图，而不是加入标题/短语黑白名单。

## 8.3 taxonomy 与启发式

监管 taxonomy、表族标签和业务短语只在 evidence blocks 组装完成后生成 retrieval facets。
它们不得改变 title、heading_path、payload、顺序、边界、drop 或 source ownership。

标点、短语、长度等启发式可以用于候选召回或作为证据组合的一项，但只有在跨公司、跨报告类型
的真实正反语料上验证稳定，并与 parser type、层级、bbox/页面关系或多模态结果等独立证据一致
时，才允许影响结构。单一词面命中永远不能决定切分或删除；每个结构变换必须记录来源与证据码。

## 9.1 江海股份 2025 年年度报告

“主要会计数据和财务指标”、合并利润表、资产负债表和现金流量表属于标准财务数据路径。

处理：

```text
保留原 PDF
保留 parser artifact
发布 PDF 原始表格证据，但不生成第二套统一口径标准财务 dataset
```

### text unit

```json
{
  "heading_path": [
    "第三节 管理层讨论与分析",
    "一、报告期内公司从事的主要业务"
  ],
  "payload_kind": "text",
  "semantic_key": "business_overview"
}
```

应收账款“按账龄披露”和“按组合计提坏账准备”分别保留为完整表格单元：

# 10. 数据源目录和适配器

## 10.1 dataset_registry

统一数据源能力的 canonical 定义应放在 Git 中，而不是首先做成一张人工维护的数据库表。

每个 dataset contract 描述：

```text
dataset_key
description
query model
result model
primary provider
fallback provider
refresh policy
schema version
owner
status
```

示例：

```yaml
key: financial.income_statement
description: A股利润表
primary_provider: wind          # 示例；可换 tushare / ifind / choice，dataset_key 与 provider 无关
provider_object: AShareIncome
fallback_provider: official_filing
query_fields: [company, period, scope]
result_model: IncomeStatement
```

```yaml
key: disclosure.receivable_aging
description: 应收账款账龄和坏账计提
primary_provider: official_filing
provider_object: document_unit
query_fields: [company, period]
result_model: TableUnit
```

## 10.2 provider_adapter

每个 provider 负责：

```text
统一查询参数
→ provider 参数转换
→ 获取数据
→ 转换为统一返回模型
→ 记录 source_access
```

第一版可以只是普通 Python adapter，不必立即建设复杂框架。

## 10.3 source_access

数据库只记录实际发生的访问：

- dataset key；
- provider；
- 查询参数；
- 访问时间；
- 状态；
- 结果哈希；
- 错误；
- 必要的返回快照或定位。

接口文档、字段定义和 provider 映射由 Git 中的 registry 管理。

# 11. 最小数据库

## 11.1 第一版核心对象

```text
company
security
source_access
document
processing_run
document_unit
optional source_checkpoint
```

## 11.2 company / security

维护公司和证券基础关系。公司主体与证券代码分开。

## 11.3 source_access

覆盖标准数据 provider（Wind / Tushare / 同花顺 iFinD / Choice 等）、CNINFO、MCP、Web 和其他 API 的实际调用记录。

> 命名对应：本服务的 `source_access` 承载顶层协议 §2.3 的 `source_ref` provenance 引用（`source_ref` = `source_access_id`），public view 为 `source_refs_v1`。v0.7 已把 `source_ref` 降级为可由视图或 endpoint（`GET /v1/units/{id}/source-ref`）派生的引用字段，不要求独立主表；本服务第一版只实现 L1 这一段，不建 claim/evidence 表。

## 11.4 document

用于自维护披露文件：

- provider document id；
- 公司和证券；
- 公告标题和类型；
- 公告日期和报告期；
- source_access；
- 原文件路径和哈希；
- 当前状态；
- 更正和替代关系。

## 11.5 processing_run

记录下载、解析、清洗和结构切分的运行版本和状态。

## 11.6 document_unit

只服务披露文档，保存 `text/table/qa/mixed`。

标准数据 provider 的记录不写入 `document_unit`。

## 11.7 source_checkpoint

仅在增量同步需要游标时建立。

## 11.8 文件系统

```text
raw_documents/
  原始 PDF

parser_artifacts/
  Markdown
  parser JSON
  table HTML / JSON
  其他调试产物
```

> `document_unit` 存的是**切好的内容快照本身**（在 `payload` 里），不是只存地址：数据库保存原文件路径、哈希、检索索引，以及每个单元的 `payload` 快照。`artifact_locator` 只是可选的回溯指针，用于回看原文核对；查询和证据引用都依赖 `payload` 快照。这也是为什么内容固化后不需要 parser block 镜像表 / table_cell / persisted chunk 等回指结构（见 §11.9）。

## 11.9 第一版不建设

- `filing_text_block`；
- `filing_text_chunk`；
- `filing_table_cell`；
- page / bbox locator；
- cross-parser alignment；
- 独立向量库；
- 图数据库；
- 全量标准数据 provider 镜像仓库；
- 每种财务附注表一张 SQL 表。

# 13. 追溯、版本和 as-of

## 13.1 披露来源

一个正式披露 claim 可以引用：

```text
source_access_id
+ document_id
+ raw_file_hash
+ processing_run_id
+ asset_id
+ exact snapshot
```

无需强制 page 和 bbox。

## 13.2 标准数据来源

标准数据 provider claim 引用：

```text
dataset_key
+ provider
+ query params
+ queried_at
+ returned field/value snapshot
```

## 13.3 G0 定义（已由 v0.7 §2.9 采纳）

披露侧 G0（顶层协议 §2.9 追溯等级）定义为：

```text
自维护原文件
+ 文件哈希
+ 精确 document_unit / 表格快照
+ 来源链（source_ref）
```

页码或视觉区域是附加复核信息，不是必要条件。

## 13.4 版本策略

- 原始文件版本不可变；
- parser run 可重跑；
- unit 属于具体 run；
- 当前查询默认返回 active run；
- 旧 claim 保留旧 run 和 exact snapshot；
- 不要求新旧 parser unit ID 一致。

# 14. 变更传播

## 14.1 不触发 L3

- page 变化；
- bbox 变化；
- Markdown 样式变化；
- parser 版本变化；
- 逻辑 unit 边界变化；
- 运行时上下文截取变化；
- 同一内容的格式差异。

## 14.2 触发 L2 重新处理

- 新公告；
- 更正公告；
- 原文件哈希变化；
- unit 正文变化；
- 表头、行、单位或数字变化；
- 新保留规则识别出新的候选单元；
- 解析质量状态改善；
- 标准数据 provider 历史值修订。

## 14.3 触发 L3/L5 的条件

只有当重新处理形成：

- 新 claim；
- claim 值变化；
- claim 状态变化；
- 假设变化；
- 口径契约变化；

才沿血缘触发预测更新。

parser 几何变化不直接触发预测。

# 15. 解析和质量策略

## 15.1 默认 parser

当前唯一写入后端是 MinerU 3.4.4 Hybrid-medium，入口位于
`src/disclosure_anchor/adapters/parsers/mineru_medium/`；High/页窗仅允许 DB-free 诊断。

Docling、Camelot 或其他工具只在以下情况按需启用：

- 默认 parser 失败；
- 关键表结构明显错误；
- 某张表即将进入正式预测，需要增强复核；
- 对特定文档类型形成专用 fallback。

## 15.2 轻量质量检查

正文：

- 文本非空；
- 标题顺序合理；
- 断行和乱码可接受；
- Q&A 边界完整。

表格：

- 有标题或可识别语义；
- 有表头和数据行；
- 单位可识别或标记缺失；
- 行列数合理；
- 数字解析率合理；
- 有显式合计时做简单加总检查。

不通过时标记：

```text
needs_review
unusable
```

## 15.3 不做的质量工程

- 全量双 parser；
- 所有表逐 cell 对账；
- 所有 PDF 数字和标准数据 provider 逐项核验；
- 所有错误自动修复；
- 所有视觉坐标正规化。

更严格的复核由“是否真的进入重要 claim”决定。

这一步**不入库、不建 dataset_registry / provider adapter / source_access、不接 CNINFO 同步、不做查询 API**，只验证“PDF → 结构正确的 document_unit”这条解析链路成立。通过后才进入 Phase 1。

1. 从净利润驱动树列出第一版真正需要的数据；

## Phase 2：标准数据访问（覆盖整个股票池）

> 范围边界：第一版是 ≥500 只**人工精选池**的全覆盖，不是**全市场全 A（~5000+）全量抓取**——后者仍是非目标（见 `open-source-references.md`「当前取舍」）。

## Phase 4：批量解析与切分

1. 对池内股票的目标公告，用 Phase 0 验证过的解析链路批量生成 `document_unit(text/table/qa/mixed)`；
2. 应用 §8 的保留 / 跳过策略；
3. 轻量质量检查不过的进 `needs_review` 队列，不污染干净数据；
4. 每次解析写 processing_run，保留 active run。

## Phase 5：查询闭环与运行监控

L2 能按以下维度对全池直接查询：

```text
company
period / event date
filing_type
payload_kind
heading_path
semantic_key
title
asset_id
```

并提供运行面板：池内覆盖率（已发现 / 已下载 / 已解析 / 失败）、解析质量分布、needs_review 积压。

## Phase 6：运行后晋级

运行一段时间后，根据实际调用频率：

- 晋级高复用 table family 为标准 dataset；
- 增加少量 semantic key；
- 增加专用抽取器；
- 只对明确瓶颈增加全文或语义检索；
- 按需扩大股票池或新增来源（如港交所）。

# 17. 第一版验收标准

> 下面是**完整第一版（≥500 只人工精选池）**的验收，不是 Phase 0 解析工具验证的验收。Phase 0 只需回答一件事：样本 PDF 能否解析出结构正确的 `text/table/qa/mixed`（章节切对、页内表闭合、问答完整不拆、数字按原值保留）。

1. 三大表和标准财务指标从标准数据 provider 获取，不从 PDF 重建第二套数据；
2. **股票池 ≥500 只的目标公告能稳定发现 → 下载 → 解析，覆盖率、失败率可度量；**
3. 池内任一公司年报的主营业务和经营分析可按 heading path 取得；
4. 分产品收入、产销量、应收账款账龄等完整表格可直接读取；
5. 池内任一投关记录可按完整 Q&A 读取；
6. 权益分派等短公告可被 L2 抽取成分红 / 事件；
7. L2 不需要打开 PDF，也不需要理解 page、bbox 和 parser block；
8. `heading_path` 能作为稳定的逻辑导航；
9. parser artifact 能通过 `artifact_locator` 按需回看；
10. parser 版本变化但内容不变时，不触发 L3；
11. 新公告、修订值或真实内容变化只重跑受影响部分；
12. 任一进入预测的值都保存 source access 和 exact snapshot；
13. 下载、解析和切分失败可定位、可重试；
14. 数据库保持少量核心对象，不因新增一种附注表就新增一张 SQL 表；
15. 不上向量数据库也能完成主要检索和 L2 消费闭环。

# 20. 最终架构结论

最合适的第一版不是“把所有 PDF 变成一个完整数据库”，也不是“把所有内容都做成 RAG chunk”。

正确形态是：

```text
标准数据 provider（Wind / Tushare / 同花顺 iFinD / Choice 等）
负责标准、可复用数据

披露文件服务
负责原文件、标题结构、完整表格和问答所需的完整源上下文

L2
负责从这些对象中抽取事实、事件、口径和重要性

L3/L5
负责证据、假设和预测
```

财报切分的核心单位不是页，也不是 chunk，而是：

```text
有真实标题边界的 text
有完整行列结构的 table
同一结构 occurrence 下保持源顺序的 mixed evidence block
```

数据库只保存需要被查询、约束、版本化和追踪的对象。其余 parser 细节留在文件系统，未来有实际需求再提升。
