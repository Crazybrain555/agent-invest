## 0. L1 层宪法

1. **L1 是来源资产层，不是事实层。**  
   L1 的正式产出只有 `data_asset`，回答“资料从哪里来、何时取得、如何复查、现在是什么可消费形态、是否发生变化”。L1 不回答“是否高价值、是否采信、支持哪个预测假设”。

2. **所有来源一个信封。**  
   PDF、结构化数据库、HTTP API、web / MCP 工具结果、人工上传件，都统一落到 `data_asset = identity + scope + time + provenance + payload + state`。差异进 `asset_kind`、`payload_kind`、payload 与登记过的扩展字段，不默认新增顶层对象。

3. **raw 止于 L1，但 L1 不是全量 raw data lake。**  
   披露 PDF 与人工上传原件自维护；标准数据库 / API / tool result 可以轻存储，只保存可消费 snapshot、访问记录、locator、provider_as_of、query_params 等追溯信息。轻存储不等于轻职责。

4. **L1 做载体规范化，不做投资语义。**  
   文档侧做解析、OCR、切分、表格结构保留、heading_path / order_index / content_hash；结构化侧做字段契约核实、类型规整、机械单位换算、查空、幂等、取代；上传侧做原件登记、转写 / OCR / Excel 区块结构化。L1 不做 claim 抽取、冲突裁决、采信、预测相关性判断。

5. **AI 可见的是目录与契约，不是裸库权限。**  
   L1 必须让 AI / agent 看得到“有哪些来源、哪些数据集、哪些表 / endpoint / 字段、哪些已核实、哪些只是 inventory”，但 AI 不能拿凭证裸连，也不能绕过登记路径。

6. **探索可以存在，但必须受控。**  
   预注册数据集不是唯一入口。字典可见但未注册的数据，可以通过受控 ad-hoc 通道形成一次性 `dataset_snapshot`。但 ad-hoc 不能长期滞留为稳定数据产品，复用即转正。

7. **append-only 是一跳追溯成立的前提。**  
   data_asset、source_access、processing_run / action_log、change_event 都不原地改写事实。内容变化产生新资产或 supersede；正常消费只存一跳引用，全链由审计递归重建。

8. **LLM 出候选，规则做裁决。**  
   LLM 可以帮助起草查询需求、字段映射候选、material_type 候选、检索关键词、结构摘要，但凡进入登记、准入、执行、字段契约、权限边界的地方，必须由确定性规则校验。

## 1. L1 的统一对象：data_asset

### 1.1 最小字段组

每个 L1 资产都应映射到以下六组字段：

```text
identity     asset_id / asset_uri / asset_kind / payload_kind / contract_version
scope        subject_candidates / company_ref? / security_ref? / report_period? /
             material_type / title / heading_path / semantic_key / parent_ref / order_index
time         event_time / published_at / observed_at / provider_as_of
provenance   source_ref / source_access_ref / provider / adapter / tool / locator /
             raw_asset_ref / producer_action_ref / source_tier / trace_level
payload      text / table / qa / recordset / search_result / api_response /
             calculation_table / model_table / checklist / note
state        quality_status / content_hash / is_active / superseded_by / sensitivity
```

字段纪律：能列化、需要检索、需要过滤、需要权限控制的字段进列；内容形态差异进 payload。`company_ref` / `security_ref` 只能在 Subject Registry 或服务内 crosswalk 能确定时列化；未解析前用 `subject_candidates`，不得伪造 canonical ref。

### 1.2 source_ref 与 locator

`source_ref` 是 provenance 引用，不是第二套来源对象。它可以由 public view / endpoint 派生，但语义必须稳定。`locator` 用于定位来源内部的子位置，例如 PDF 页码 / 段落、表格行列、provider table_alias、API endpoint、web URL、tool result item id。

### 1.3 raw 与 payload

`payload` 是下游可消费内容；`raw_asset_ref` 是原始字节或原始响应的保真引用。披露 PDF 与上传文件必须保留 raw；结构化数据和工具结果可以不保留完整 raw response，但必须保留足以复查的 payload snapshot 与 source_access。

## 2. asset_kind 分型

| asset_kind | payload_kind | 来源路径 | L1 最小职责 |
|---|---|---|---|
| `document_unit` | `text` / `table` / `qa` | disclosure_anchor、upload_service | 原文保真、业务结构切分、表格 / Q&A 完整保留、heading_path、locator、content_hash |
| `dataset_snapshot` | `recordset` | asset_intake、upload_service 数据摘录 | provider、dataset_key、query_params、returned_fields、provider_as_of、records / 摘要、字段状态 |
| `tool_result` | `search_result` / `api_response` / `page_snippet` | web / MCP / Claude / Codex / plugin / 外部 API | tool/source、query、returned_items、每项 locator、raw response 可选、agent 总结不得当来源 |
| `artifact_unit` | `calculation_table` / `model_table` / `checklist` / `note` | 人工上传、研究工件 | 上传人 / 作者、material_type、sensitivity、可复核性、原件 hash、区块 locator |

人工上传不是单独的 asset_kind。上传只是入口，最终按内容形态进入以上四类之一。查空也不是 asset_kind；查空记录在 `source_access(result_status = empty)`，只有当它回应 evidence_request 时，才由 L2 生成 `null_observation`。

## 3. L1 服务版图

```text
packages/envelope_kernel
  统一信封模型 / kind 矩阵 / asset:// URI / 契约 schema

services/disclosure_anchor
  披露 PDF / 公告 / 财报硬锚路径
  raw PDF + parser artifact + document_unit + change feed

services/asset_intake
  结构化数据 dataset_snapshot
  轻载外部结果 tool_result
  source catalog / dataset contract / provider adapter / registrar

services/upload_service（未来）
  人工上传文件 / 文本 / 表格 / 图片 / 录音转写 / Excel / 模型工件
  raw 保真 + 载体规范化 + sensitivity + material_type 人声明
```

服务拆分原则：是否拆服务不按来源数量决定，而按生命周期、权限边界、raw 处理形态决定。披露 PDF 是自维护硬锚，保留独立服务；人工上传涉及原件、OCR / 转写、敏感度和权限隔离，倾向独立服务；结构化数据与轻载 tool_result 都是“访问外部源后登记 snapshot / item”，可以同属 asset_intake。所有服务必须复用同一信封核与同一 public contract 风格。

## 4. 统一入库生命周期

```text
source discovery / source policy
→ source_access：记录访问、查询参数、结果状态、provider_as_of、错误或查空
→ producer action：parser / adapter / tool harness / upload parser 的执行记录
→ data_asset：形成可寻址、可追溯、可消费资产
→ public view / API：按 *_v1 读契约暴露
→ change feed：observed / materialized 事件供 L6 与 L2 消费
```

状态判别：

- `ok`：有结果并形成 data_asset；
- `empty`：查询成功但无结果，只记 source_access，不建 data_asset；
- `error`：权限、连接、限流、schema 不匹配、preflight 失败，不得伪装成 empty；
- `observed`：看过但内容未变；
- `materialized`：新资产或内容变化；下游失效只由 materialized 触发。

## 5. 披露 PDF 路径：disclosure_anchor

披露 PDF 是 L1 中最硬的自维护锚。它的职责不是“把 PDF 切成 chunk”，而是把交易所披露文件转成可复查、可增量感知、可由 L2 精选抽取的 document_unit。

硬规则：

1. 原文件不可变：raw PDF、hash、provider document id、download / access 记录必须保存。
2. 按业务结构切：标题、段落、完整表格、完整 Q&A、脚注、跨页表格优先保持逻辑完整；不得按 token 或版面碎切作为主契约。
3. scope 继承：document 级 company / security / report_period / filing_type / announcement_date 等，必须在 unit 级 public view 可检索。物理表可以范式化，读契约必须反范式化。
4. L1 不删实质信息：风险提示、会计政策、重大事项、业绩变化等不得因“像套话”永久不可见。
5. disclosure_anchor 的三 schema、public views、outbox、processing_run、source_ref、contract_version，是其他 L1 服务的蓝图。

## 6. 结构化与工具源治理：asset_intake

### 6.1 四类配置件

结构化与工具源接入采用“四类配置件 + 一个登记器”：

1. **source / provider catalog**：描述外部源、连接 profile、source_tier、trace_level、安全规则、rate limit、freshness check、active table / endpoint、preflight 规则。凭证不得入配置。
2. **dataset contract**：描述 provider-independent 的语义数据集，例如 `cn_equity.fin_statement`。包含 query_params、字段、单位、时间语义、dedup、content_hash、provider mapping。只有 dataset contract 才能成为长期订阅和稳定 numeric_observation 输入。
3. **source inventory**：由 prober / discover 生成的日期戳快照，记录“源里有什么表 / endpoint / stream / 字段”。inventory 是可见性，不是语义承诺；可以给 AI 看，但不得直接等同于 dataset contract。
4. **query template / request spec**：登记允许执行的查询形态、绑定参数、谓词、最大行数、timeout、字段投影规则。SQL 型走白名单模板；API / MCP 型走 endpoint request spec。

登记器唯一写 DB。provider adapter 只返回 result，不直接写库；registrar 负责 source_access、data_asset、幂等、supersede、outbox。

### 6.2 多 provider 纪律

1. `dataset_key` 语义命名、provider 无关。provider 进入 provenance、provider catalog、locator、source_access，不进入稳定 dataset_key。
2. provider_priority 是服务级配置，不进入 dataset_key，不改变下游契约。
3. L1 不跨 provider 合并、不裁决。Wind 与 Tushare 对同一 dataset_key 的结果各自入账；冲突、采信、优先级裁决在 L2 / L3。
4. adapter 可以做字段名映射、类型规整和配置声明的机械单位换算，但不得把 provider 指标误标成披露原始事实。
5. preflight fail-fast：缺表、缺列、缺 endpoint、freshness 异常、权限不足，必须显式 error，不得静默降级。

## 7. 结构化数据三条 Lane

### Lane A：注册数据集

适用：长期订阅、增量维护、进入 L2 numeric_observation 主链的数据。  
要求：dataset contract + provider catalog + fixture + preflight + registrar 全链。  
结果：`dataset_snapshot(contract_status = registered)`，可作为 L2 稳定准入源。

### Lane B：可发现 inventory

适用：让 AI / 人知道外部源里可能有什么。  
要求：机器可读、日期戳、标明 active / stale / unknown、字段存在性、样本探测结果、freshness 结论。  
限制：inventory 不是 dataset contract，不承诺字段语义、单位、口径、去重规则；不能直接作为 L5 订阅源。

### Lane C：受控 ad-hoc snapshot

适用：evidence_request、研究课题、人工问题中出现“字典可见但未注册”的一次性取数需求。  
形态：AI 起草 `AdhocDatasetRequest`，不是自由 SQL。请求包含 source_policy、provider、inventory_ref、table_alias / endpoint、字段、谓词、绑定参数、max_rows、timeout、用途说明。validator 依据 provider catalog、inventory、query template 安全规则和 source_policy 裁决。

登记规则：

```text
dataset_key       = adhoc.<subject_domain>.<semantic_slug>    # provider-independent
provider          = wind_rds / tushare_api / web_search / ...
adhoc_signature   = normalized request spec hash
contract_status   = adhoc_unverified
adhoc_status      = exploratory / promotion_required / closed
```

Lane C 输出仍是 `dataset_snapshot`，但字段语义契约未注册，这是显式状态。L2 可以在一次性场景中引用它并完成字段映射确认；但它不能成为 L5 长期订阅源、不能承担自动增量、不能被当成稳定数据产品。

晋升规则：满足任一条件，后续必须转 Lane A：同一 adhoc_signature 反复出现；进入 L5 data subscription；需要 source_checkpoint 增量；被 L2 多次映射为同一 metric；进入正式预测流程后需要持续复验。历史 adhoc snapshot 不迁移，保持原样可追溯。

## 8. 轻载 tool_result 路径

web search、MCP、Claude / Codex、第三方插件、外部 HTTP API 的返回，先是 L1 `tool_result`，不是证据。

硬规则：

1. agent 总结不是来源；总结引用的网页、API 返回、搜索结果 item、原始片段才是来源。
2. 每个 returned_item 必须有 locator。没有 locator 的结果只能进入临时上下文，不得入 L1。
3. tool source 也应 catalog 化：tool name、provider、认证 profile、rate limit、返回结构、locator 规则、raw response 留存策略、source_tier 默认值。
4. 弱信源默认低 trace / 低 tier，可进入冷存或待核，但不能单独支撑正式预测。
5. tool_result 到 L2 仍需准入：网页片段可以形成 observed_claim，API item 可以形成 numeric_observation，但都不能绕过 L2。

## 9. 人工上传路径：upload_service

人工上传是 L1 中最容易污染系统的一条路径，因此必须从第一天按服务契约设计，而不是把文件临时塞给 L2。

硬规则：

1. 原件保真：上传文件、文本、图片、音频、Excel、PPT、Word 都先登记 raw_asset_ref + hash。
2. material_type 由人显式声明：纪要、调研笔记、数据摘录、计算表、模型工件、框架建议、待办清单等。L1 不靠 LLM 自行判定其投资语义。
3. sensitivity 必填：公开、内部、敏感、一手、疑似 MNPI / 合规隔离等；权限过滤从 L1 public contract 开始。
4. 载体规范化：文本切分、表格区块、OCR、转写、Excel sheet / range、公式保留、脚注和单位保留。
5. 拿不准的上传件默认 `artifact_unit`，由 L2 通过 change_candidate / 人工裁决决定是否转证据；不得默认当作事实。

## 10. 数据目录与 AI 可读性

L1 的目录不是传统 RAG chunk 索引，而是面向 agent 的 source / asset / contract directory。

目录至少暴露：

```text
sources/providers        有哪些源、凭证 profile、tier、trace、freshness、preflight 状态
datasets/contracts       注册数据集、字段、单位、时间语义、provider mapping、样例
inventory snapshots      源内表 / endpoint / stream / 字段、探测日期、语义未核标记
query templates          可执行请求形态、参数、限制、示例
assets/public views      已登记 data_asset，可按 scope/time/type/quality 过滤
source_access            查过什么、空结果、错误、provider_as_of
change feed              observed / materialized 事件
```

为了提高 AI 检索质量，L1 可以保留 `title`、`heading_path`、`semantic_key`、`keywords`、`retrieval_summary` 等检索辅助字段。但这些字段只是召回辅助，不是证据正文；L2 形成 evidence_record 时必须引用原文 exact_span、表格 locator 或 record locator。

未来 MCP 包装遵守同一原则：目录和资产读侧是 resources；取数、上传、登记、探测是 tools；资源只读，写动作一律走 tool。

## 11. L1 / L2 边界

| 问题 | L1 | L2 |
|---|---|---|
| PDF / Excel / OCR / 转写 | 处理并形成 data_asset | 不处理 raw，收到即回流 |
| 文档切分 | 业务结构切分，保留上下文 | 精选高价值 evidence |
| 表格结构 | 保留表头、单位、脚注、行列 locator | 抽取指标、统一 registry |
| 结构化数据 | 查询、登记、字段契约、机械单位规整 | numeric_observation、metric mapping、采信 |
| 工具结果 | 记录 query、item、locator | 判断是否可作为证据 |
| 人工上传 | 登记、哈希、sensitivity、material_type 人声明 | change_candidate、采信 / 驳回 |
| 冲突 | 不裁决 | contested / accepted / rejected / cold |
| 预测影响 | 不判断 | 经 L3 / L5 / L6 传播 |

一句话：L1 保证“看得见、找得到、可复查、可消费、知道是否变化”；L2 才判断“这条信息在预测系统里是什么意思”。

---

## 12. 对外读契约

每个 L1 服务都必须提供同构读契约：

1. `*_v1` public views / API，跨服务只读 public contract，不读私有表。
2. `asset://<service>/v<n>/<kind>/<asset_id>` 稳定 URI。
3. scope keys 过滤 + 游标分页。
4. source_ref / source_access_ref 可追溯。
5. change feed：`GET /v1/changes?after_seq` 或等价视图；事件至少区分 observed / materialized。
6. 错误码：`L1_PROCESSING_REQUIRED`、`NOT_FOUND`、`CONTRACT_VERSION_MISMATCH`、`GONE_SUPERSEDED`。
7. public contract 必须携带 sensitivity / quality_status，读侧按权限过滤。

## 13. 当前固定决策

1. L1 总协议应合并 v0.2 与 v1.2 的主思想；provider framework 降为结构化源接入细则。
2. upload_service 应作为未来独立 L1 服务设计，而不是 L2 附件，也不建议简单塞进 asset_intake 主职责。
3. Lane C 保留，但必须改成 provider-independent adhoc 命名 + 明确状态机 + 晋升约束。
4. 数据目录是一等公民：contract 与 inventory 必须分开；AI 可以看 inventory，但不能把 inventory 当稳定契约。
5. `company_ref` / `security_ref` 不可伪造。未解析前用 subject_candidates；document_unit 的继承承诺与结构化 snapshot 的候选主体状态要分开写。
6. 结构化 / tool_result 可以轻存储 raw，但不能轻登记：payload snapshot、locator、source_access、provider_as_of、query_params 是底线。
7. 任何来源进入预测系统，必须先过 L1 / L2；agent 自己看网页后总结，不能直接改预测。

---

## 14. 不进入本协议正文的细节

以下内容应放在服务实现细则或附录，不放在 L1 总协议正文中：

- Wind / Tushare 的具体表名、字段名、单位勾稽、active_table 裁决；
- 四个首发 dataset 的完整 YAML 字段清单；
- provider adapter 函数签名与测试矩阵；
- disclosure_anchor 的 milestone 状态；
- upload_service 的 OCR / ASR 工具选型；
- 任何排程、批次、里程碑。

总协议只锚定原则、边界、对象、服务版图、治理规则和硬约束；实现细节由各服务文档和 registry 契约承接。
