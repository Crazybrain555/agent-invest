## 1. L1 全景:四条路径现状与缺口

```text
路径                服务/入口                    状态          统一出口
披露 PDF            services/disclosure_anchor   live(07 进行) data_asset(document_unit)
结构化数据          services/asset_intake        M-C 完成      data_asset(dataset_snapshot)
工具/网页结果       asset_intake.register_tool_result  入口就绪  data_asset(tool_result)
人工上传            upload_service               未立项(最后)  data_asset(document_unit/
                                                              dataset_snapshot/artifact_unit)
共享核              packages/envelope_kernel     M-B 完成      信封模型/kind 矩阵/asset:// URI
```

### 1.1 disclosure_anchor(披露 PDF)

现状:milestone 06 Filing API 冻结(送审通过);milestone 07 CNINFO 增量同步由并行会话进行中
(含免凭证 web fallback、real-API 验收 A25/A26/A27 已过)。本会话对该子树只读。

缺口(对照协议 §3.10 的三点补强):

- **G1 change feed 端点**:outbox_event 表 + change_events_v1 视图已落,但 `GET /v1/changes`
  端点与 observed/materialized 两事件语义(§2.8)未落——建议列入其 milestone 08。
- **G2 envelope_kernel 反向接入**:术语已收敛(asset_id / payload_kind / event_kind),
  但信封模型、URI 规则、kind 矩阵仍是服务内自持定义。建议时机:07 收尾且 API 契约稳定后,
  做"对齐性接入"——用 envelope_kernel 的契约测试替换服务内重复定义,不改运行时行为。
- **G3 跨路径对账锚**:(security, report_period) 键两侧已就绪(披露侧 filing、intake 侧
  fin_statement/earnings_event);对账本身是 L2 的职责,L1 只保证键可用。

### 1.2 asset_intake(结构化数据)——M-C 已交付

现状(P1–P6,commit 链见 docs/agent):端口冻结、双层配置(4 dataset + 2 provider catalog,
全部实测核实)、确定性 registrar(幂等三态 + supersede)、intake_public 三视图 + 权限收口、
契约导出、tool_result 登记入口;真实 F12 preflight 对活 RDS 全绿。

队列(按序):

1. **P-通道**:真实 WindRdsProvider(先)→ TushareApiProvider(后,fallback/交叉校验),
   含 freshness smoke 与显式 opt-in 真源测试;
2. **source_checkpoint**:增量游标表(行情按交易日、财务/事件按公告日 + lookback),
   新 migration,配合 §2.5 的调度形态;
3. dataset 扩容(见 §2.4);
4. L2 numeric_observation mapper——属 L2 里程碑,不在本服务。

### 1.3 upload_service(人工上传)——未立项,维持"最后立项"

定位(§3.8):统一 upload adapter;**material_type 由人显式声明**,L1 不做语义推断;按内容形态
分发为 document_unit(纪要文本)/ dataset_snapshot(数据摘录)/ artifact_unit(计算/模型工件);
拿不准默认 artifact_unit 走 change_candidate 复核(§4.8)。

边界与复用:raw 保真留存 + 哈希;信封走 envelope_kernel;登记手法复用 asset_intake registrar
(独立服务 vs 并入 asset_intake 第三入口——kickoff 决策是独立服务,立项时再给对比确认)。

建议时机:**L2 最小闭环之后**——上传件的价值依赖 L2 准入/退回改派链路(§3.8 判定责任),
在 L2 缺位时立项只能积压。

### 1.4 tool_result 轻载路径——入口就绪,源未接

现状:`register_tool_result`(每条 item 必带 locator、错误≠查空、Tier 2/G2 默认)。
缺口:①源目录化——web search / MCP / API 源各建 `registry/providers/*.catalog.yaml` 同款
配置(F12 同一原则:一切皆配置、预检 fail-fast);②第一批真实源接入(§3)。

## 2. provider 路线图(结构化数据)

### 2.1 已实测双通道(2026-07-06,详见 v1.2 §11)

- **wind_rds**(阿里云 SQL Server,50 表子集):主通道。行情至上一交易日、预告至当天;
  批量/表宽占优;活表裁决与列名/单位全部实测入 catalog。
- **tushare_api**(HTTP,同事共享 token,将换密钥):备用 + 交叉校验。八个所需 endpoint
  当前 token 全通;限流按积分。

### 2.2 通道对比(含潜在第三家)

| 维度 | wind_rds(实测) | tushare_api(实测) | 同花顺 iFinD(候选,**未实测**) |
|---|---|---|---|
| 覆盖 | A股行情/财务/事件/指数/基金/HK 50 表 | 覆盖同类,接口粒度细 | 宣称全,未核 |
| 新鲜度 | 预告当天、行情 T-1 | 同级 | 未核 |
| 稳定性 | RDS 直连,受同事同步作业影响 | 官方 SaaS,受积分/频控 | 未核 |
| 限流 | 无(自律:白名单模板+行数上限) | 积分制,min_interval 300ms | 未核 |
| 凭证合规 | 同事账号,将轮换;只读 | 同事 token,将轮换 | 需自有账号,采购流程 |
| 接入成本 | catalog 已就绪,只差 adapter | 同左 | 全新 catalog + adapter |
| dataset_key 映射 | 四条首发全覆盖 | 四条首发全覆盖 | 待字典核实 |

结论维持 F11:wind 主、tushare 备;iFinD 仅在前两者不可持续时启动评估,不预投入。

### 2.3 同事 tushare MCP 封装的定位(重申 v1.2)

不作为接入通道(账本唯一:source_access + data_asset,不允许第二套 SQLite cache);
其限流退避、错误分类、工具索引设计已吸收进 tushare_api catalog 与未来 adapter 实现参考。

### 2.4 dataset 扩容 roadmap(优先级序)

1. 首发四条打通真实通道(P-通道);
2. `cn_equity.valuation_daily`:估值日频(RDS 实测有 AShareValuationIndicator 表 +
   AShareEODDerivativeIndicator 视图;列/单位未核,接入前照 R4 纪律实测);
3. 证券主档/行业分类(AShareDescription / AShareIndustriesClassCITICS 等,实测存在):
   喂将来的 Subject Registry(L4/L6 议题,不是 L1 dataset 常规扩容);
4. 披露日历(财报季调度用):RDS **无** AShareIssuingDatePredict;tushare `disclosure_date`
  接口**未实测权限**——启用前先核;
5. 一致预期(AShareForcast,实测存在):协议 §15.6 baseline claims 暂不启用,
   仅登记为将来对照模块的输入,不进 L5 主假设。

### 2.5 增量与调度

- 行情:AShareCalendar(实测至 20271231)驱动 security × trade_date 窗口;
- 财务/事件:公告日(ANN_DT/ann_date)增量 + lookback 窗口兜重述,不按 max(report_period);
- 理想终态:disclosure_anchor 的 change feed(G1 落地后)触发同期财务数据拉取——跨服务联动,
  在 L6 调度脊柱建立前,用"手动 CLI + 定时批"(§15.7 允许)。

## 3. 轻载外部源调研(tool_result 路径)

接入总原则(全部继承已定框架):一切皆配置(source catalog + F12 预检 fail-fast)、
统一走 `register_tool_result`(agent 总结不是来源,§16.18)、Tier 2/3 + G2、
错误≠查空、凭证只走环境变量、限流退避在 adapter。

### 3.1 同事包内已有(本机已读 SKILL.md)

- **news-newsapi-search**(NewsAPI.org):/everything + /top-headlines,5000+ 源,
  免费档 100 请求/天。评估:英文源为主(Reuters/BBC 级),对 A 股公司的中文本地新闻弱;
  适合海外供应链/行业信号;HTTP + key,接入成本低。→ 候选第二批。
- **capture-search-x**(xAI Grok x_search):X/Twitter 实时搜索带引用。评估:传闻/情绪类,
  按 §2.9 应预设 Tier 3(status=cold),不能单独支撑正式预测;付费 key。→ 按需/第三批。
- 其余观察(未评):capture-alphapai-web、capture-gangtise-upgrade、capture-polymarket-trade
  ——纪要/预测市场类,与净利润预测主链相关性待课题机制(§9)成型后再评。

### 3.2 公开候选(**全部未实测**,启用前逐个核权限/限流/条款)

- 论文类:arXiv API(免费)、OpenAlex(免费、元数据广)、Semantic Scholar(免费限流)。
  用途:技术趋势 → 行业主题课题;建议等拉式回路(evidence_request)成型再接,
  否则登记了也没有消费方。
- 中文财经新闻:**优先核 tushare 的 news/major_news 类接口**(同一 token 同一通道,
  复用成本最低,权限未实测);财联社/东财等无官方开放 API,爬虫路径合规与稳定性差,不建议。
- 通用 web-search MCP(brave/tavily 类):可作 agent 侧工具,但结果登记必须显式过
  register_tool_result;MCP server 本身按 F12 建 source catalog。

### 3.3 第一批建议(待拍板 D-c)

tushare 新闻接口(若权限核实可用)**或** NewsAPI 二选一先行,打通"tool_result source
catalog + 真实源"全链;论文类与 X 搜索押后。
