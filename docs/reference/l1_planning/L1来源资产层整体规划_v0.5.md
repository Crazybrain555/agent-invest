# 0. L1 层宪法

1. **L1 是来源资产层,不是事实层。**
   L1 的正式产出是 `data_asset` 与必要的访问 / 处理账本,回答"资料从哪里来、何时取得、
   如何复查、现在是什么可消费形态、是否发生变化"。L1 不回答"是否高价值、是否采信、
   支持哪个预测假设"。
2. **所有来源一个信封。**
   PDF、结构化数据库、HTTP API、web / MCP 工具结果、人工上传件,统一落到
   `data_asset = identity + scope + time + provenance + payload + state`。差异进
   `asset_kind` / `payload_kind` / payload 与登记过的扩展字段,默认不新增顶层对象。
3. **raw 止于 L1,但 L1 不是全量 raw data lake。**
   披露 PDF 与人工上传原件自维护;标准数据库 / API / tool result 可以轻存储,只保存
   可消费 snapshot、访问记录、locator、provider_as_of、query_params、单位信息等追溯要素。
   **轻存储不等于轻职责,更不等于轻登记。**
4. **L1 做"投资资料友好"的载体规范化,不做投资判断。**
   L1 可以识别"这是股权激励事项""这是管理层讨论""这是财务表格"——这些是资料结构与检索
   上下文,切分与登记规则以投资阅读逻辑设计(规则层的领域知识);但 L1 不判断"这个激励
   是否利好""这个订单是否可信""是否应进预测"——那是运行时投资语义,属 L2+。
   **存储单元宁整勿碎**(粒度纪律见 §5);不得因"像套话"删除可能含实质信息的内容。
5. **文档切分以完整事项为第一原则。**
   主切分单位不是 token、页、孤立小标题或勾选项,而是完整业务事项、完整章节、完整表格、
   完整 Q&A、完整管理层讨论单元;超长才在业务小节边界二级切分(parent-child)。
6. **探索是常态入口,登记与追溯是底线。**
   预注册数据集不是唯一入口:字典可见的数据都可经统一取数通道形成 `dataset_snapshot`
   (§7)。registered 契约是"维护好的省心稳定入口",不是系统跑通的前置条件;沉淀为注册
   契约是**人工治理动作**,不设自动晋升(业界同款:discovered → configured 均人工选定)。
7. **append-only 是可追溯的默认纪律,允许治理性清理。**
   public 资产与账本不原地改写语义;内容变化产生新资产或 supersede;正常消费一跳引用,
   全链由审计递归重建。误入库、敏感隔离、垃圾清理、迁移可经 tombstone / 归档 / 离线 GC
   处理——但不能悄悄改历史事实。
8. **LLM 出候选,规则做裁决。**
   LLM 可以做 OCR 纠错、版面识别、表格转写、结构摘要、字段映射候选、material_type 候选、
   检索关键词、取数请求起草;凡进入登记、准入、执行、字段契约、单位换算、权限边界的地方,
   必须由确定性规则或人工确认兜底。LLM 不进登记层。
9. **账本唯一,harness 不自带私账。**
   source_access + data_asset + processing_run / action_log 是 L1 唯一账本;任何 adapter /
   skill / harness 不得自带第二套 cache 或私账;agent 上下文不是长期事实库,材料要进系统
   必须回补 L1。
10. **一切皆配置,代码只是解释器;工程化面向服务化。**
    语义契约、物理映射、provider 优先级、安全策略、单位字典、上传 manifest schema 全部
    与代码分离——近期 Git YAML(可 review、可回滚),后续可由 API / 管理端读取维护;
    "代码解释配置"是原则,"全在一个 YAML 里"不是。配置启用前预检 fail-fast。L1(以及
    将来 L2 / L3)可能对外部前端 / 其他后端供数,设计上随时可加 HTTP API / MCP 包装而
    零改造,封装成本低时即可先行。

# 1. 统一对象:data_asset

## 1.1 最小字段组

每个 L1 资产映射到六组字段(分组是叙述结构,契约约束只来自字段定义与必选性,协议 §2.1):

```text
identity     asset_id / asset_uri / asset_kind / payload_kind / contract_version
scope        subject_candidates / company_ref? / security_ref? / report_period? /
             material_type / title / heading_path / semantic_key / parent_ref / order_index
time         event_time / published_at / observed_at / provider_as_of
provenance   source_ref / source_access_ref / provider / adapter / tool / locator /
             raw_asset_ref / producer_action_ref / source_tier / trace_level
payload      text / table / qa / mixed / recordset / search_result / api_response /
             page_snippet / calculation_table / model_table / checklist / note
state        quality_status / content_hash / is_active / superseded_by / sensitivity
```

字段纪律:能列化、需检索、需过滤、需权限控制的字段进列;内容形态差异进 payload;新增
字段一律按协议 §2.1 扩展字段纪律登记(如 tool_result 的 `trace_status`,§8;dataset 的
`contract_status`,§7)。**字段级**语义(如每个数值字段的单位状态)记在 payload / 契约的
field_units 结构里,不冒充资产级信封列。信封模型与 kind 矩阵由 `envelope_kernel` 共享包
承载,服务内不得重复定义或私改;kind 矩阵变化经协议升版(`mixed` 即 v0.8 新增)。

## 1.2 source_ref 与 locator

`source_ref` 是 provenance 引用,不是第二套来源对象;可由 public view / endpoint 派生
(协议 §2.3),语义必须稳定。`locator` 定位来源内部子位置:PDF 页 / 章节 / 表格行列、
mixed 单元内 parts 序号、Excel sheet / range、provider table_alias 与实际 active 物理表、
API endpoint、web URL、DOI、MCP resource URI、search result item id。locator 严禁含
host / token / cookie / 任何凭证。

## 1.3 raw 与 payload

`payload` 是下游可消费内容;`raw_asset_ref` 是原始字节 / 原始响应的保真引用。

- 披露 PDF、人工上传文件:必须保留 raw;
- 结构化数据库 / API:可不留完整 raw response,但必须保存 records 或可复查 snapshot、
  returned_fields、field_units、query_params、provider_as_of、locator;
- web / MCP:能保存原始 item / snippet 最好;保存不到时至少保存 URL / DOI / 查询参数 /
  accessed_at,并标 `trace_status = locator_only`(§8)。

## 1.4 scope 两级承诺(canonical ref 不可伪造)

- **披露 document_unit**:company_ref / security_ref / report_period / filing_type /
  announcement_date 必须从 document 继承到 unit 级读契约(协议 §3.6 / §16.10)——物理存储
  可范式化,读契约必须反范式化。
- **dataset_snapshot / tool_result / artifact_unit**:`subject_candidates`(subject_key
  全形式)是底线字段;没有单一公司时可声明 industry / theme / market 级候选
  (`industry:光模块` 等),但必须有明确范围。canonical company_ref / security_ref 仅在
  Subject Registry 或服务内 crosswalk 可确证时列化,**未解析是显式状态,不得伪造**。

# 2. asset_kind 分型

| asset_kind | payload_kind | 来源路径 | L1 最小职责 |
|---|---|---|---|
| `document_unit` | text / table / qa / mixed | disclosure_anchor、upload_service | 原文保真、按业务事项切分、表格 / Q&A / 图文表混排块完整保留、heading_path、locator、content_hash |
| `dataset_snapshot` | recordset | asset_intake、upload_service 数据摘录 | provider、dataset_key、query_params、returned_fields、**field_units**、provider_as_of、contract_status |
| `tool_result` | search_result / api_response / page_snippet | web / MCP / API / harness 回补 | tool / source、query 或访问参数、可回链引用、accessed_at、trace_status |
| `artifact_unit` | calculation_table / model_table / checklist / note | 人工上传、研究工件 | 上传人 / 作者、material_type、sensitivity、可复核性、原件 hash、区块 locator |

三条说明:

- **入口与形态是两层概念,不矛盾**:人工上传是**入口**(ingest route),不是 asset_kind。
  上传年报 PDF → document_unit;上传 Excel 数据摘录 → dataset_snapshot 或 artifact_unit;
  上传模型底稿 → artifact_unit。`artifact_unit` 不等于"所有上传件"——它是四类形态之一,
  承接计算表 / 模型表 / 清单 / 纪要底稿等无法自然归入披露文档 / 结构化数据 / tool_result
  的研究工件(有作者与可复核性问题,默认走 change_candidate 复核)。
- **查空 / 失败不入账本**(对协议 §3.9 的有意收窄,§4 / §15):`empty` 不建 data_asset;
  是否持久化 source_access 由 §4.3 access_log_policy 决定。
- `mixed`(协议 v0.8):一个业务语义块内 text / table(/ 图)交替是披露与上传资料的常态;
  payload kind 不决定 unit 边界,`mixed` = `semantic_type` + 有序 `parts`。

# 3. L1 服务版图与拆分原则

```text
packages/envelope_kernel(已建)
  统一信封模型 / kind 矩阵 / asset:// URI / 契约 schema——跨服务共享核

services/disclosure_anchor(收尾中)
  披露 PDF / 公告 / 财报硬锚路径:raw PDF + parser artifact + document_unit + change feed
  其手法是其余 L1 服务的复用蓝图(三 schema / *_v1 views / outbox / processing_run)

services/asset_intake(已建骨架;真实 provider adapter 待接)
  结构化数据 dataset_snapshot + 轻载外部结果 tool_result
  配置件 + provider adapter + registrar(唯一写 DB)

services/upload_service(未来,独立服务——固定决策 D1)
  人工上传 md / txt / docx / xlsx / csv / pdf(格式白名单渐进放开)
  raw 保真 + manifest 准入 + 载体转换 + material_type 人声明
```

**服务拆分原则**:是否拆服务不按来源数量决定,而按**生命周期、权限边界、raw 处理形态**
决定。披露 PDF 是自维护硬锚,保留独立服务;人工上传涉及原件、OCR / 解析、manifest、
敏感度与权限隔离,独立成服务;结构化数据与轻载 tool_result 都是"访问外部源后登记
snapshot / item",同属 asset_intake。所有服务复用同一信封核与同一 public contract 风格。

**现有代码的地位**:asset_intake 与 envelope_kernel 有测试门禁且全绿,但未经用户验收——
定位为**参考实现**,允许按本协议推倒重建;本协议约束目标形态,不为现有代码背书。
各服务现状缺口统一见 §17。

# 4. 统一入库生命周期与拒收门槛

## 4.1 标准生命周期

```text
需求(人工 / evidence_request / 课题 / harness agent 回补)
→ 前置校验:参数、权限、manifest、引用锚点、单位、格式(fail-fast,报错列明缺什么)
→ producer action:parser / adapter / tool harness / upload parser 的执行记录
  (processing_run,即 action_log 的 L1 特化;含失败与空结果的运行留痕)
→ source_access:按 access_log_policy(§4.3)记录有效访问与结论性查空
→ data_asset:可寻址、可追溯、可消费资产(幂等判定 + supersede)
→ public view / API:按 *_v1 读契约暴露
→ change feed:observed / materialized 事件供 L2 / L6 消费
```

## 4.2 结果处置(全路径统一;原则:**账本只收有价值信息**)

- `ok`:形成 data_asset(+ source_access);
- `empty`:查询成功但无结果——不建 data_asset;
- `error`:权限、连接、限流、schema 不匹配、preflight 失败——不得伪装成 empty;
- `rejected`:缺关键参数、缺来源锚点、乱码、不可解析、manifest 不合格——不建 data_asset,
  报错列明缺什么(错误码 `INGEST_REJECTED`);
- `observed`:巡检过、内容未变(记 content_hash),不触发下游失效;
- `materialized`:新资产 / 内容变化 / 取代——**下游失效只由 materialized 触发**(协议 §2.8)。

## 4.3 access_log_policy:留痕分档,防账本污染

不是每次失败尝试都要进长期数据库。按访问目的分三档:

| 场景 | source_access(账本) | 说明 |
|---|---|---|
| 注册数据集取数 / evidence_request 正式取证 / 工具正式回补 | **记** | 需要复查"查过什么、为何为空或失败";evidence_request 的结论性查空由此支撑 L2 `null_observation` 结案(协议 §3.9 路径保留) |
| 系统巡检 / freshness / preflight | **记** | 诊断数据源状态 |
| 临时探索、手工试错、无锚点 harness 片段、乱码 | **不记**——运行日志(带保留期)即可 | 避免早期大量 null / 垃圾污染公共账本 |

重复出现的同类错误 / 空结果可聚合成 summary 再记,不逐条落账本。业界对照:空 / 失败尝试
一律记在 jobs / runs 元数据 store(带保留期),绝不写主数据表(Airbyte / Meltano / dlt /
dbt 一致;dlt 只给"跑完但零行"留成品记录、失败批次不留,§14)。

# 5. 披露文件路径:disclosure_anchor

披露 PDF 是 L1 中最硬的自维护锚。职责不是"把 PDF 切成 chunk",而是把交易所披露文件转成
可复查、可增量感知、可由 L2 精选抽取的 document_unit。

## 5.1 核心规则

1. **原文件不可变**:raw PDF、hash、provider document id、download / access 记录必须保存。
2. **scope 继承**:document 级 company / security / report_period / filing_type /
   announcement_date 必须在 unit 级 public view 可检索(§1.4 第一级承诺)。
3. **不删实质信息**:风险提示、会计政策、重大事项、股权激励、客户变化、产能、订单、
   资本开支、关联交易、问询函、管理层讨论不得因"像套话"永久不可见。
4. **表格不拆散**:表头、单位、脚注、行列 locator 与表格上下文一起保留;除非表格极长,
   不按行生成顶层 unit。
5. **蓝图地位**:其三 schema、public views、outbox、processing_run、source_ref、
   contract_version 是其他 L1 服务的复用蓝图(协议 §3.10)。

## 5.2 切分粒度纪律:宁整勿碎,按完整事项切

推荐的主单元层级:

```text
document
  → 章节(business / statutory section)
      → 完整业务事项(主 document_unit;text / table / qa / mixed)
          → 子定位(表格、勾选项、公告索引、脚注、子段落——locator / parts 序号,不是独立 unit)
```

**应保留为一个主 unit 的典型**:"股权激励计划、员工持股计划或其他员工激励措施的情况及其
影响"整节(事项概述 + 查询索引 + 适用性勾选 + 高管授予表 + 考评机制说明);同一管理层
讨论主题下的文字 + 表格 + 补充说明;同一重大事项的概述、索引、后续进展;一个完整 Q&A;
一个完整财务附注表格及其脚注——`mixed` payload(semantic_type + 有序 parts)即为此而设。

**不得独立成顶层 unit 的典型**:"□适用 √不适用"孤立勾选项;"其他说明:□适用 √不适用"
这类脱离主事项无独立语义的短句;表格单行 / 单个数值;只有查询索引没有事项上下文的公告
标题。**勾选 / 适用性标记行永远不得进入 heading_path / title**——它们是所属事项的属性
(applicability 等结构字段)或 parts 内局部标记。

**超长事项**用 parent-child 结构二级切分,不切断上下文:

```text
parent_unit: 股权激励计划及实施情况(完整事项壳)
  child_unit_1: 已披露且后续无重大变化的激励事项
  child_unit_2: 董事、高管报告期内被授予的股权激励表
  child_unit_3: 考评机制与激励机制说明
```

初始经验阈值"超过当前模型可稳定消费的预算(如 50k tokens 量级)再拆",阈值配置化、
不写死为协议常量。**存储粒度与检索 / 消费粒度解耦**:L1 契约锚定"完整事项"这一层;
更细的检索索引(子块、局部定位)属检索层手段,后续按需加,不因消费需要而碎化存储契约。
(业界同款:结构感知的章节级切分在财报检索上显著优于固定 token 切分,勾选框等碎片一律
并入章节;small-to-big / parent-document 检索即为解耦而生;超大块直接喂 LLM 反而降准确率
——所以"整存"与"细取"要分开,见 §14。)

## 5.3 "投资资料友好"≠"投资语义判断"

允许 L1 做:按标题 / 目录 / caption 识别 material_type;判断一段文本是否属于同一披露
事项;提取 heading_path / title / retrieval_summary / keywords 作召回辅助;保留"股权激励 /
订单 / 产能 / 客户 / 会计政策 / 风险提示"等结构标签。

不允许 L1 做:判断事项利好 / 利空;判断激励是否足够强;判断订单是否进收入预测;抽 claim
并采信;因模型觉得"没价值"而删原文。

(outbox 表 + 视图已落);**G2** envelope_kernel 反向接入;**G3** 跨路径对账锚已就绪、
持续维持。切分粒度整改(mixed 语义块、标记行清理)正在该服务收尾中落地。

## 6.1 配置件:职责分离,不锚定文件数量

以下配置**职责**必须分离——近期 Git YAML(可 review、可回滚),后续可由 API / 管理端
服务化(§10.2);"必须拆成几个文件"不是协议约束:

```text
1. source / provider catalog   外部源:连接 profile 名、tier / trace、安全底线与可选加固、
                               rate limit、freshness 探针、候选表 + activation、preflight。
                               凭证不入配置。
2. dataset contract(沉淀件)  provider 无关的稳定语义数据集:query_params、字段 / 单位 /
                               时间语义、dedup、provider mapping。人工治理的沉淀产物,
                               不是取数前置门槛;只有 contract 数据才能作 L2 稳定准入源
                               与 L5 订阅源。
3. source inventory            prober / discover 生成的日期戳不可变快照:源里有什么表 /
                               endpoint / 字段、存在性、新鲜度、以及**能拿到的字典单位
                               注记**。是可见性,不是语义承诺。
4. query template / request spec  可执行查询形态:绑定参数、谓词、max_rows、timeout。
                               注册契约的模板与 AI 起草的临时请求同属此类、同一 validator。
```

单位语义横跨第 2 / 3 / 4 类:contract 字段带 unit 声明;inventory 尽量携带字典单位注记;
任何执行结果必须落 field_units(§6.3)。**登记器(registrar)唯一写 DB**:provider
adapter 只返回 result 不碰库;registrar 负责 source_access、data_asset、幂等、supersede、
outbox。

现状映射(与仓库实况一致):第 1、2 类已落地(2 个 provider catalog;dataset contract
3 条 active + eod_quote deprecated);第 3 类**未建**(50 表清单仅存于附录 C 文字,不可
机读);第 4 类部分落地(SQL 白名单模板寄生于 contract 的 providers 段,临时请求

## 6.2 多 provider 纪律

1. **dataset_key 语义命名、provider 无关**(原 F1):provider 进 provenance / catalog /
   locator / source_access,不进稳定 dataset_key。
2. **provider_priority 是服务级配置**(原 F11):不进 dataset_key、不改下游契约。
3. **L1 不跨 provider 合并、不裁决**(原 F5):同 dataset_key 多 provider 各自入账
   (`(provider, dedup_key)` 唯一);冲突、采信、优先级裁决在 L2 / L3。
4. **provider 指标 ≠ 披露原始事实**(原 F2):adapter 可做字段名映射、类型规整、配置声明
   的机械单位换算,派生指标必须带 `metric_origin`;earnings_event 与 fin_statement /
   fin_metric 分立。
5. **preflight fail-fast**(原 F12):缺表、缺列、缺 endpoint、freshness 异常、权限不足,
   显式 error 并列明缺什么;预检通过才允许 fetch;doctor / adapter 启动必跑。

## 6.3 单位纪律:数值字段必须带单位状态

Wind / tushare / 交易所表格 / Excel / 人工摘录都存在单位差异,**同一 provider 内不同
endpoint 单位也不同**(元 / 万元 / 千元 / percent,附录 C 实证)。字段级最小约束:

```text
field_name / provider_field_name / value_type
provider_unit     元 / 万元 / 股 / 手 / 千元 / percent / ratio / unknown
canonical_unit    元 / 股 / percent / decimal / unknown
unit_source       provider_dictionary / table_caption / manual_manifest / inferred_unverified
unit_transform    multiply:<factor> / percent_to_decimal / none
unit_status       verified / declared / inferred_unverified / unknown
```

硬规则:

- registered 契约的数值字段 `unit_status` 必须是 verified / declared,否则不能成为
  稳定字段;
- adhoc 取数允许 unknown / inferred_unverified,但必须显式标注;**此类字段不得直接进入
  L2 numeric_observation 稳定主链**(一次性引用需人工 / 规则确认单位后方可);
- 人工上传表格:表头、脚注、caption、manifest 都定不了单位时,该数值区块只能作
  unresolved artifact / raw table,不得伪装成规范化 dataset;
- 百分比必须分清 percent 还是 decimal;金额必须分清元 / 万元 / 千元;成交量必须分清
  股 / 手。单位 / 口径未知必须显式 `unknown`,严禁默认(协议 Unit / Scope Registry 纪律)。

## 6.4 取数安全:底线、自动范围、可选加固三层

**底线(不可省;业界地板,应用层"只读包装"已被实证攻破——见 §14)**:

1. **数据库侧只读强制**:专用最小权限角色(仅该 agent 用),角色级 read-only / 仅 SELECT
   授权——不靠 server 或 adapter 自律;
2. **单语句强制**(解析器级,防 `COMMIT; DROP …` 拼接)+ **语句类型白名单**(仅 SELECT /
   EXPLAIN 类;拒 DDL / DML / SET / RESET / DO 等会话状态操作);
3. **绑定参数**(不拼接字符串)+ **max_rows + timeout**;
4. **审计**:每次执行落 processing_run;有效结果落 source_access;凭证只走环境变量。

**自动范围(默认开,零维护)**:可查表 / 字段的 allow-list **由 inventory 自动生成**,
不靠手工维护——AI 依 inventory 起草请求,validator 校验标识符确实存在于探测清单中
(既满足 OWASP 的 allow-list 校验,又不产生人工白名单的维护负担)。大表扫描受限:
无主键谓词、无日期窗口、无分页的全表扫默认拒绝;正式全市场任务必须显式声明窗口与分块。

**可选加固(per-source 配置)**:手工收紧的表 / 列白名单、required 索引谓词、篮子上限等,
按 provider catalog 声明——共享 / 昂贵的库(如同事的 Wind RDS)建议开,自有库可不开。
方言级细则见附录 B.5。

## 6.5 幂等、去重、取代(原 F6)

semantic_key = dataset_key(或 adhoc key)+ 规范化 query scope;dedup_key =
sha256(semantic_key || content_hash);`(provider, dedup_key)` 唯一。同 provider 同
semantic_key:content_hash 同 → `observed`;变 → `materialized` + supersede 旧 active。
content_hash 不含查询时间;registry / request spec 版本走 provenance,不进 dedup_key。

## 6.6 增量与调度

财务 / 事件按公告日(ANN_DT / ann_date)增量 + lookback 窗口兜重述,不按
max(report_period);载体是 source_checkpoint 增量游标表(待建,属 registered 契约的
稳定能力,不强塞 adhoc)。调度遵守协议 §15.7:定时批 + 手动拉起,不依赖实时在线;
disclosure_anchor change feed(G1 落地后)触发同期财务拉取是跨服务联动的目标形态。

# 7. 结构化取数通道与契约状态

**取数只有一条通道**;注册与否只是契约状态差异,不是两套流程。registered 的价值是
"省心、稳定、可复用",**不是"只有它能入库"**——早期大多数取数走 adhoc 完全正常。

```text
需求(人工 / evidence_request / 课题)
→ AI 依字典(catalog + inventory)起草查询请求(registered 数据集直接用现成契约与模板)
→ 确定性 validator 按 §6.4 底线 + 自动范围裁决(+ 该 provider catalog 声明的可选加固)
→ adapter 执行 → registrar 登记 dataset_snapshot
→ 必填不降:provider / query_params / returned_fields / field_units / provider_as_of /
  adapter 版本 / 主体候选;经 asset_intake 的 CLI(未来 MCP tool)执行,
  不是让 agent 拿凭证裸连——登记、审计自动发生
```

**请求形态**(AI / 人起草的是结构化请求,不是自由 SQL 文本):

```text
AdhocDatasetRequest:
  provider / source_policy
  inventory_ref / table_alias / endpoint
  query_intent(用途说明)
  subject_candidates / date_range 或 report_period
  fields / predicates / bound_params
  max_rows / timeout
  unit_policy(字典单位引用 / 人工单位覆盖)
```

**契约状态两态**:

- `contract_status = registered`:有 dataset contract(字段 / 单位 / 时间语义 / dedup
  经核实),可作 L2 numeric_observation 稳定准入源与 L5 订阅源;
- `contract_status = adhoc`:无预注册契约——显式状态,不是缺陷伪装成正常;
  `dataset_key = adhoc.<domain>.<semantic_slug>`(provider 无关,同 §6.2-1);
  单位按 §6.3 允许 unknown 但显式;L2 一次性引用需字段映射与单位确认;
  **不得**作 L5 长期订阅源、不承担自动增量。

**沉淀是人工治理动作,不阻断使用**:某类 adhoc 请求反复使用、进入正式预测、需要增量
维护、或被 L2 多次映射为同一 metric 时,系统**提示**"建议沉淀为 dataset contract",
由人(或人授意 AI 写代码)整理——不设自动晋升,也不阻断同类请求继续执行。业界同款:
Airbyte / Meltano / dbt 的 discovered → configured 全部人工选定,不存在按使用频率自动
转正的先例(§14);将来最多加用量统计辅助人判断。

# 8. 轻载 tool_result 路径(harness 现实下的回补式登记)

**现实约束**:web / MCP 检索发生在 harness 的 agent 回路里(拉式阶段),大量尝试、大量
丢弃是常态;hosted 检索工具常常不返回原始载荷。登记模式是**回补式**(harness-first /
backfill),不是全程截获式。

规则:

1. **探索自由**:harness agent 检索、阅读、筛选不经 L1;没找到有用东西的尝试不留账本
   记录(运行日志除外,§4.3)。
2. **回补义务**:凡是要进入 L2 / L3 / L4 的结论,必须回补一条 L1 `tool_result`——最低
   载荷 = 可回链引用(URL / DOI / API 参数 / MCP URI / 结果 item id)+ 标题 + accessed_at
   + 简短摘录;拿得到原始片段就带上,拿不到不阻塞登记。
3. **引用是底线**:"agent 总结不是来源"(协议 §16.18)的执行标准 = **结论必须回链到至少
   一个可定位引用**;完全无引用的内容不得登记为 tool_result(错误码 INGEST_REJECTED),
   只能当线索 / 待办或低等级 artifact_unit(显式标注为 agent 观点,非来源)。这也是深研
   产品的通行标准(OpenAI / Perplexity / Gemini 均为结论级 URL 引用 + 访问时间,无一
   归档全程原始响应,§14)。
4. **trace_status 分级**(tool_result 的登记扩展字段,与协议 trace_level 组合而非替代
   ——trace_level 说来源等级,trace_status 说本条记录实际存了什么):

   | trace_status | L1 记录内容 | L2 使用限制 |
   |---|---|---|
   | `full_item` | 原始 returned_item / snippet / 响应片段 + 引用 | 可直接进 L2 准入检查(exact_span 可锚) |
   | `locator_only` | 仅引用 + 标题 + accessed_at(+ 摘录) | L2 证据化前必须 re-fetch 或人工核验 exact_span |

   一次回补可含多条 items(研究报告的 Sources 清单 = 多条 locator_only items 一次登记)。
5. **链路验收**:登记后由复核步骤(程序或 LLM)抽验链路完整性——L2 记录 → L1
   tool_result → 引用可访问(或标注已失效 + 当时摘录);关键 / 易腐来源可选留存快照。
6. **tool source 渐进 catalog 化**:常用源沉淀最小 catalog 条目(tool 名、source_type、
   locator 规则、raw 留存策略、rate limit、认证 profile、tier 默认);一次性来源不强求
   先建 catalog;**没有 locator 规则的工具不得进入正式来源路径**。弱信源(传闻 / 情绪类)
   预设 Tier 3,不能单独支撑正式预测(协议 §2.9)。

候选源事实与选型判据见附录 A(不排批次)。

# 9. 人工上传路径:upload_service

定位:把杂乱的人工资料**规范成与 disclosure_anchor 同款的一致性资产**。披露路径的来源
格式相对固定、重心在按结构切分;上传路径材料形态与质量差异大、重心在"不规则 → 规则"的
**载体转换**(格式解析、OCR、表格提取)——允许用 LLM / OCR 产出转换与结构候选(宪法
第 8 条:候选仍经确定性校验,且必须记录 model / tool / version / confidence /
parser_config);资料定性(material_type)仍由人声明。

硬规则:

1. **manifest 准入,缺硬必填即拒收**(fail-fast,错误码 INGEST_REJECTED,报错列明缺什么;
   不收"无主体、无日期、无来源"的 trash):硬必填 = title、uploader、material_type、
   source_origin、subject_scope(至少一个 subject_key 候选或显式行业 / 主题范围)、
   时间语义(event_time / report_period / meeting_time / document_date 至少一种)、
   source_attribution(URL / 作者 / 机构 / 会议 / 自己整理,至少一种)。
   **sensitivity 由系统默认 `internal`**(对内使用阶段不作人工必填;字段保留、可显式改;
   显式标 sensitive / possible_mnpi 时 permission_note 必填,D12)。完整 schema 见附录 D。
   拒收示例:"公司光模块有望获得大客户订单 xxxx"——无公司、无日期、无来源,
   不得进入 public L1,最多留在人机上下文当草稿(或走 §9.1 补全流程)。
2. **原件保真**:raw_asset_ref + hash 先落,再做转换。
3. **首发格式白名单**:md / txt / docx / xlsx / csv / pdf(文本型优先;扫描 PDF 走 OCR
   并标低置信);图片、音频、PPT 后续按需开;白名单是配置。
4. **能不切分就不切分**:默认整文件 / 整 sheet / 整节为一个单元(document_unit 用
   `mixed` 承载图文表混排);超长才按 §5.2 粒度纪律 parent-child 二级切分。
5. **单位保留**:Excel / 表格保留表头、脚注、caption、单位说明;定不了单位按 §6.3
   处理(unresolved,不伪装)。
6. **拿不准默认 `artifact_unit`**,由 L2 经 change_candidate / 人工裁决决定是否转证据;
   不得默认当作事实。
7. **时间语义**:event_time = 资料对应时间(非上传时间);published_at 按
   source_available_at 语义(协议 §2.5),无法证明更早可用时退化到 observed_at。

上传产物映射:

| 上传内容 | 推荐 asset_kind | 说明 |
|---|---|---|
| 年报 / 公告 PDF | document_unit | 路径同披露蓝图,来源标 upload |
| 会议纪要 / 调研笔记 / 专家交流 | artifact_unit(必要时派生 document_unit) | L2 再决定是否抽证据 |
| Excel 数据摘录 | dataset_snapshot 或 artifact_unit | 单位、来源、表头、sheet/range 必须保留 |
| 模型底稿 / 估值表 | artifact_unit | 研究工件,非外部事实 |
| 网页剪藏(带 URL) | tool_result | 走 §8 回补式登记 |
| 无来源短句 / 传闻 | 拒收 | 不进 public L1(或走 §9.1 补全流程) |

## 9.1 对话式人工陈述(轻量第二入口)

高频人机互动——专家 / 研究员在会话中说了一句话、一段话("某个数据应该是 X,在哪里
哪里")——与文件上传同属本服务,但走 **API / tool 形态的轻量入口**。它与 §8 tool_result
**同构**:先在 harness 会话里发生,值得留的再回补;整个回补与确认流由**组装层**驱动
(系统以 headless 单次调用运行 harness,如 `claude -p` / `codex exec`,即协议 §15.7 的
session 式形态),harness 是被调用的执行器,不是流程的主人。

流程:

```text
人说一句话 / 一段话(harness 会话内)
→ AI 预填元数据候选:uploader = 当前用户、observed_at = now、source_origin 候选、
  material_type 候选、subject 候选(从话中抽取)、sensitivity = internal(默认,D12)
→ 弹窗人工确认:默认参数一键确认;缺失参数人工补填
→ 补不齐:输入暂存为草稿,写一条 L6 人机待办("补全后登记");
  待办超期未处理(阈值可配)→ 作废——草稿丢弃、运行日志留痕,不入 public L1
→ 确认齐:登记 L1 资产(document_unit(text) 或 artifact_unit;Tier F / G3)
→ 若陈述指向系统内部对象的修正("你们那条假设拍错了"):同一次输入可同时生成
  change_candidate(target_layer = L3 / L5) 引用该资产——轻量不等于绕过人批
  (单人场景人批 = 一次显式确认 + 留痕,协议原则 15)
```

对话式变体的人工硬必填只剩三件(其余自动预填):**material_type**、**主体确认**
(AI 出候选,人点选)、**来源归因**(转述专家 / 会议 vs 本人判断——决定 Tier F 一手转述
还是个人观点,影响 L2 置信上限)。

锚定说明:一句话没有 URL / 文档,其"原文" = 登记文本本身 + 说话人 + 时间(G3 人工
记录级的本义);§8-3"无引用不收"是 tool_result 的规则,不适用于人工陈述。若话里给了
出处("数据在某公告第 X 页"),该陈述作**线索**登记,并触发 evidence_request 把真正来源
取回锚定(协议 §8.6)——真正的证据是被指向的披露件,不是那句话。

高频卫生:不是每句话都登记——判据是"这句话会被引用去支撑证据或修改假设吗";闲聊与
过程性讨论留在会话里(运行日志除外,§4.3)。为什么必须走 L1 / L2 而不给"直接改 L5"的
后门:复盘要能归因到"是那句话带偏的"并回写来源可信度(协议 §14.3);as-of 按录入时点
防前视(协议 §2.5 source_available_at);Tier F 必须进冲突检测与披露锚对账。

框架先行:先支持常见场景与白名单格式,以配置渐进放开;独立服务(D1)。

# 10. 数据目录、配置服务化与 AI 可读性

L1 的目录不是传统 RAG chunk 索引,而是面向 agent / 前端 / 后端的 source / asset /
contract / inventory directory(协议 §15.5)。成败标准:**LLM 在 L2–L6 的任何环节要数据
时,能靠目录找到该用什么、怎么取、单位口径是什么**。

## 10.1 目录至少暴露

```text
sources / providers      有哪些源、凭证 profile 名、tier / trace、freshness、preflight 状态
datasets / contracts     注册数据集、字段、单位、时间语义、provider mapping、样例
inventory snapshots      源内表 / endpoint / 字段、探测日期、字典单位注记、"语义未核"标记
request specs            可执行请求形态、参数、限制、示例
unit semantics           字段单位、换算规则、来源、状态(§6.3)
assets / public views    已登记 data_asset,按 scope / time / kind / quality 过滤
source_access            正式访问与结论性查空、provider_as_of(探索噪音不进,§4.3)
change feed              observed / materialized 事件
upload manifest schema   上传准入字段、必填项、示例、拒收原因
```

检索辅助字段(title / heading_path / semantic_key / keywords / retrieval_summary)只是
召回辅助,不是证据正文;L2 形成 evidence_record 必须引用原文 exact_span、表格 / parts
locator 或 record locator。

## 10.2 配置服务化

近期 Git YAML(简单、可 review、可回滚);工程量可控时提供读 API / 管理端,让 L1 服务
前端、其他后端与 L2–L6 agent,而不是只服务本地 CLI:

```text
GET  /v1/catalog/providers | /v1/catalog/inventory | /v1/catalog/datasets |
     /v1/catalog/units | /v1/upload/manifest_schema
POST /v1/admin/catalog/...        # 后续可选,需权限;非首期硬要求
```

## 10.3 MCP 映射

目录与资产读侧是 **resources**(只读);取数、上传、登记、探测、回补是 **tools**;
资源只读、写动作一律走 tool,且 tool 必须经 registrar(协议 §3.11)。字典不含凭证。

# 11. L1 / L2 边界

| 问题 | L1 | L2 |
|---|---|---|
| PDF / Word / Excel / OCR / 转写 | 处理并形成 data_asset,或拒收 | 不处理 raw,收到即回流(L1_PROCESSING_REQUIRED) |
| 文档切分 | 投资资料友好的业务结构保真切分,宁整勿碎 | 精选高价值 evidence |
| 表格结构 | 保留表头、单位、脚注、行列 / parts locator | 抽取指标、registry 归一、口径判断 |
| 结构化数据 | 查询、登记、字段契约、单位状态、机械规整 | numeric_observation、metric mapping、采信 |
| adhoc 取数 | 默认探索入口,形成 adhoc dataset_snapshot | 判断能否进证据 / 指标主链(单位 unknown 需先确认) |
| 工具结果 | 回补登记:引用、accessed_at、trace_status | locator_only 先 re-fetch / 核验 exact_span,再证据化 |
| 人工上传 | manifest 准入、哈希、载体转换、sensitivity | change_candidate、采信 / 驳回 |
| 冲突 | 不裁决 | contested / accepted / rejected / cold |
| 预测影响 | 不判断 | 经 L3 / L5 / L6 传播 |

一句话:**L1 保证"看得见、找得到、可复查、可消费、知道是否变化、不被垃圾污染";
L2 才判断"这条信息在预测系统里是什么意思"。**

# 12. 对外读契约与服务化

每个 L1 服务提供同构读契约:

1. `*_v1` public views / API;跨服务只读 public contract,不读私有表;演进遵守协议 §2.7。
2. `asset://<service>/v<n>/<kind>/<asset_id>` 稳定 URI(协议 §2.3 三条硬规则)。
3. scope keys 过滤 + 游标分页是契约义务。
4. source_ref / source_access_ref / producer_action_ref 可追溯。
5. change feed:`GET /v1/changes?after_seq` 或等价视图;observed / materialized 两事件;
   单调 change_seq、at-least-once、消费端幂等、同 subject 保序(协议 §2.8)。
6. 错误码:`L1_PROCESSING_REQUIRED` / `NOT_FOUND` / `CONTRACT_VERSION_MISMATCH` /
   `GONE_SUPERSEDED` / `INGEST_REJECTED`(兼容性新增,协议 §2.7 允许)。
7. public contract 携带 sensitivity / quality_status / contract_status /
   trace_status(tool_result);**敏感度读侧过滤在对外开放前暂缓启用**(字段照存,D12);
   upload_service 另供 manifest schema 与拒收原因查询。

**服务化目标**:L1(以及将来 L2 / L3)可能对外部前端 / 其他后端供数——public views 是
第一形态,HTTP API / MCP 是包装层,设计上零改造;封装成本低时即可先行。现状(已知偏差,
显式记录):读侧暂 SQL 视图;HTTP / MCP 未建;两服务 `/v1/changes` 端点未落(§17)。

# 13. 其余横切纪律

1. **Subject Registry 采集义务**(协议 §6.5.1 规则 4 / 5):所有创建公司 / 证券侧信息的
   L1 producer 对 identifier scheme(lei / uscc / sec_cik / isin / exchange:ticker…)
   "有则必填";强键校验走本地快照,不在主链路实时调外部 identifier API。现状:披露侧已有
   company_identifier 表(scheme 覆盖**未核**);intake 侧尚无 identifier 采集——盘点列入缺口。
2. **凭证纪律**:只走环境变量或密钥管理;配置只存 profile 名;locator / 字典 / 导出物
   不含凭证;泄露即轮换;agent 用专用最小权限凭证,不复用应用 / 管理员账号。
3. **harness 无关**(协议 §15.8):Claude / Codex / MCP / web search 是包装,不是事实层;
   控制逻辑沉淀在配置、registrar、public contract 与 action_log。
4. **删除纪律**:public 资产默认 append-only;确需清理走 tombstone / supersede / 归档 /
   离线 GC,不做静默物理删除(宪法第 7 条)。
5. **状态显式,拒收优于污染**:quality_status / contract_status / trace_status /
   unit_status 不得省略,不得把未知伪装成已核实;早期宁可拒收无锚点材料,不为"都收录"
   把 public L1 做脏。

# 16. 当前固定决策(D1–D12;推翻哪条,改本文对应条款即可)

1. **D1 upload_service 独立服务**:不并入 asset_intake,不做 L2 附件——原件、OCR / 解析、
   manifest、sensitivity、权限边界独立。
2. **D2 取数单通道、契约两态**:所有结构化取数同一链路;registered / adhoc 只是契约状态
   差异;registered 是省心稳定入口,不是跑通前置;不做独立的 ad-hoc 状态机。
3. **D3 沉淀人工、不阻断**:adhoc → registered 由人(或人授意 AI 写代码)沉淀;复用只
   触发提示,不设自动晋升、不阻断继续使用。
4. **D4 canonical ref 不可伪造**:scope 两级承诺(§1.4)。
5. **D5 登记底线含单位**:payload snapshot、returned_fields、**field_units(§6.3)**、
   locator、source_access、provider_as_of、query_params——轻存储不轻登记;单位未知的
   数值不得进 L2 numeric_observation 稳定主链。
6. **D6 回补式过 L1 / L2**:harness 探索自由;入账结论必须回链可定位引用并标
   trace_status;locator_only 证据化前须 re-fetch / 核验;链路可验收。
7. **D7 范围与通道**:行情 / 价格 / 复权 / 行情增量移出主线(price / market data 支线
   后议;eod_quote 已 deprecated 退场);wind 主 / tushare 备为默认;iFinD 不预投入;
   一致预期按协议 §15.6 暂不启用。
8. **D8 查空与垃圾按 access_log_policy 分档**:正式取证 / 巡检记账本;临时探索只进运行
   日志;rejected 不建资产(对协议 §3.9 的有意收窄,§15)。
9. **D9 上传 manifest 拒收**:文件式上传硬必填缺失即拒(附录 D);首发格式白名单
   md / txt / docx / xlsx / csv / pdf。
10. **D10 配置与代码分离、允许服务化**:近期 Git YAML,后续读 API / 管理端可选;
    append-only 默认成立,治理性清理走 tombstone / 归档 / 离线 GC。
11. **D11 对话式人工陈述轻量通道**(§9.1):AI 预填 + 弹窗人工确认;缺参不当场拒收——
    暂存草稿并挂 L6 待办,超期未补即作废(不入 public L1);一次输入可同时落 L1 资产与
    change_candidate;轻量不等于绕过人批;回补与确认流由组装层驱动(headless harness,
    协议 §15.7)。
12. **D12 sensitivity 简化(对内阶段)**:sensitivity 默认 `internal`、不作人工必填,
    读侧敏感度过滤暂缓启用;字段保留在信封与契约中,对外开放时启用开关即可,不改 schema;
    显式标 sensitive / possible_mnpi 时 permission_note 仍必填。

# 18. 风险清单

1. **供应商换轨 / 密钥轮换**(数月内可能全换):宪法第 10 条已把换源收敛为改配置;
   轮换后必跑 doctor + preflight。
2. **凭证暂存于同事 skill 目录**(`docs/reference/api resource/`,已 gitignore):轮换前
   属临时态;轮换后凭证只留 shell / 私有 env,目录内 .env 删除。
3. **取数通道误用**:validator 与只读专用角色是底线,启用前需实测(当前**未实测**);
   共享 RDS 上未开可选加固时靠 max_rows / timeout / 大表扫描限制兜底。
4. **单位误标**:inferred_unverified 被下游误当 verified——靠 unit_status 显式分级 +
   L2 主链只收 verified / declared 双兜底。
5. **回补式的漏登记风险**:harness 探索自由意味着"该回补而没回补"不会被入口拦住——
   靠链路验收(§8-5)与 L2 准入(无引用不收)双兜底。
6. **上传成为垃圾入口**:靠 manifest 拒收(D9)+ sensitivity 权限过滤控制;拒收标准
   过严会把有价值一手资料挡在门外,manifest 字段以实践迭代。

# 19. L1 硬边界(一句话,共 20 条)

1. L1 统一出口是 data_asset 信封;解决新问题先加规范 / 扩展字段,默认不新增顶层对象。
2. raw 止于 L1;L2 收到 raw 即 `L1_PROCESSING_REQUIRED` 或经 L6 回流。
3. "先轻后重"只指存储不指职责;轻存储不等于轻登记,可复查是底线。
4. L1 不做投资判断,但必须做投资资料友好的结构保真;不得因"像套话"让实质信息永久不可见。
5. 账本唯一:source_access + data_asset + processing_run;禁止任何第二套 cache / 私账。
6. 空结果 / 错误 / 垃圾载荷不建资产;留痕按 access_log_policy 分档,临时探索不污染账本;
   仅正式取证 / 巡检落 source_access。
7. append-only + supersede;content_hash 判变;一跳引用,审计递归全链;治理性清理走
   tombstone / 归档 / 离线 GC,不静默改写。
8. dataset_key 语义命名、provider 无关;provider 只进 provenance。
9. L1 不跨 provider 合并、不裁决;对账采信在 L2 / L3。
10. 一切皆配置 + 预检 fail-fast;配置与代码分离,允许服务化;绝不静默降级。
11. 取数安全底线不可省:DB 侧只读专用角色、解析器级单语句、语句类型白名单、绑定参数、
    max_rows、timeout、审计;可查范围由 inventory 自动生成,手工白名单仅是 per-source
    可选加固。
12. LLM 不进登记层;LLM 出候选(查询请求 / 载体转换 / 映射),确定性规则裁决。
13. inventory 是探测产物不是契约;不得当 dataset contract 或 L5 订阅源使用。
14. adhoc 契约状态显式;沉淀为注册契约是人工治理动作,无自动晋升、不阻断使用;
    adhoc 不得作 L5 长期订阅源。
15. 数值字段必须带单位状态;单位 / 口径未知显式 `unknown`,严禁默认;单位未知不得进
    L2 numeric_observation 稳定主链。
16. 入账结论必须回链至少一个可定位引用并标 trace_status;无引用不得登记为来源资产;
    探索尝试不留账本记录。
17. 上传必附 manifest:文件式缺硬必填即拒收,对话式缺参挂 L6 待办、超期作废;
    material_type 由人声明;sensitivity 默认 internal、字段保留(读侧过滤对外开放前暂缓)。
18. canonical company_ref / security_ref 不可伪造;未解析用 subject_candidates 且显式。
19. 跨服务只经 `*_v1` public 契约消费;change feed 两事件语义,失效只由 materialized 触发。
20. 存储单元宁整勿碎:完整业务事项一个 unit(`mixed` / parent-child 承载);勾选 /
    适用性标记行不得独立成 unit,不得进入 heading_path / title。
