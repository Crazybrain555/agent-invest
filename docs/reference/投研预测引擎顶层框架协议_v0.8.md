# AI Agent 投研预测引擎顶层框架协议 v0.8

> 目标：一个人机交互下的、数据驱动的、持续运行的财务预测引擎。
> 当前正式产出：契约口径下的公司未来季度 / 年度净利润预测。
> 未来演进方向：从净利润预测，逐步扩展到利润表、资产负债表、现金流量表的完整预测。

## 版本说明

本文件是**完整独立正文**，直接替代 v0.7（修订最终版本）。

v0.8 的唯一实质改动（2026-07-06，phase008 切分审查后经用户确认）：
**`document_unit` 的合法 `payload_kind` 增加 `mixed`**。一个业务语义块内 text 与
table（或 image part）交替是披露文件的常态（股东会一项议案 = 审议结果 + 表决表格 +
会议决定；年报一个小节 = 说明文字 + 多张表）；payload kind 不决定 unit 边界。
`mixed` 的 payload = `semantic_type` + 有序 `parts`（每个 part 复用对应 kind 的
payload schema，可带局部小标题 / 适用性标记）；payload schema 细节由
`disclosure_anchor` 的 `service-purpose.md` §6.5 登记（符合 §2.7 kind 注册要求）。

以下为 v0.7 版本说明（继续有效）。v0.6 及此前的《v0.7 升级修改稿》《v0.7 二次修订稿》均为历史讨论稿，不再作为有效协议引用。

v0.6 解决的问题是 L2 / L3 不能混在一起：

```text
L2 = 观测证据层：来源直接说了什么，当前采信什么，哪里冲突；
L3 = 派生证据层：系统基于证据和规则构造出了什么。
```

v0.7 保留这一拆分，解决的问题是 **L1 / L2 不能被写成只服务文档的流水线**。核心改动：

1. **L1 统一出口是 `data_asset` 信封**：一个信封 + 少量判别字段（`asset_kind` / `payload_kind`）+ payload。`document_unit` 只是 `asset_kind` 之一，不是 L1 的唯一出口。
2. **L2 统一产物是 `evidence_record`**：用 `record_kind` 判别记录形态（四类证据记录 + 一类治理记录），信封结构与 L1 同构。不再为每类来源发明一套对象。
3. **`source_ref` 降级为 provenance 引用**：它是信封里的一个引用字段，可由视图或 endpoint 派生（如 `source_refs_v1`），不是"L1 统一出口"的名称，也不要求独立主表。
4. **raw 止于 L1**：PDF 解析、OCR、表格识别、文件归档、人工上传件处理全部是 L1 adapter 的职责。L2 收到 raw 输入应报错（`L1_PROCESSING_REQUIRED`）或经 L6 回流 L1。
5. **删除 A 类 / B 类清洗的叫法**：L1 做**载体规范化**（carrier normalization），L2 做**证据化与语义归一**。不存在独立的"语义清洗后文本"资产。
6. **claim 抽取是高价值选择性抽取**：允许返回空列表 `evidence_records = []`；L2 可以联合多个 data_asset 做一次抽取，但不新增长期 packet 对象。
7. **追溯轻量化**：每条记录只存 `producer_action_ref` 一跳引用；模型、规则、输入、输出细节统一记在 `action_log`（即 v0.6 的 M-LOG）。正常消费看一跳，审计递归解析全链。
8. **L4 增加规范库 / Registry**：主体、单位、时间、指标、关系、口径六册规范，支撑 raw → normalized 双轨，带候选、审批、升版、重新归一的完整生命周期。
9. **L6 增加 evidence_request（拉）并规范 change feed（推）**：预测缺口通过 evidence_request 发起拉式取证；每层对下游暴露同构的 change feed 契约。
10. **从第一天建立数据目录与检索键意识**：L1 / L2 的稳定检索键、统一 URI、public views 契约版本化、对外 API / MCP 封装约定写入协议。

这版文档仍然不写代码、不写 SQL、不写详细 schema、不写目录结构。它只锁定顶层架构、层间职责、统一范式、运行机制和硬边界。

# 0. 系统宪法

## 0.1 系统本质

这不是问答系统，不是单次 case 驱动的研究助手，也不是"人提问、机器搜索、返回答案"的工具。

它是：

> **一个人机交互下的、数据驱动的、持续运行的财务预测引擎。**

系统长期吸收资料，沉淀证据，维护公司预测模型，发现冲突，触发研究课题，更新假设，生成预测快照，并在财报季复盘自己的错误。

## 0.2 唯一正式产出

系统唯一正式产出是：

> **公司未来财务预测。**

当前阶段对外输出：

> **契约口径下的未来季度 / 年度净利润预测。**

"契约口径"可以很轻：

- v0：原始财报口径；
- v0.1：原始财报口径 + 扣非；
- 后续：逐步加入公司特定调整项、一次性项目、会计政策变化处理、业务重组口径等。

## 0.3 系统不做什么

系统不做：估值、选股、买卖建议、便宜判断、组合构建、市场短期博弈判断。

这些由投资经理拿着预测结果另行判断，不进入本系统边界。

## 0.4 设计原则

原则一律一句话；缩进行是注释，不是原则本体。

1. **预测优先。**
   任何模块存在的理由，都必须能解释它如何改善财务预测或其可解释性、可复盘性。
2. **证据优先。**
   观点必须被拆成证据记录，标注来源、口径、时间、置信度和冲突状态后才能被使用。
3. **派生有边界。**
   derived claim 必须有输入引用、规则版本、契约版本和 as-of 语义，不能变成第二套真相。
4. **披露为锚。**
   财报、公告、业绩预告、问询函回复是硬锚；外部数据不能无解释地违反披露锚。
5. **所有来源一个信封。**
   来源差异进 `kind` 判别字段和 payload，解决新问题优先"加规范、加扩展字段"；默认不新增顶层对象，仅当具备独立生命周期 / 状态机 / 权限边界时经协议升版新增。
6. **raw 止于 L1。**
   解析、OCR、表格识别、文件归档只发生在 L1；L2 只接收已登记、已结构化、可追溯的 data_asset。
7. **claim 是高价值证据单元。**
   不逐句切片，不做全文知识图谱化；抽取允许返回空列表。
8. **raw + normalized 双轨。**
   normalized 由规范库支撑，只做最小必要标准化，不新增原文没有的事实，不覆盖 raw。
9. **正常消费一跳，审计递归全链。**
   记录端只存直接引用；全链由审计端沿引用遍历重建，不在每层冗余拷贝。
10. **追溯轻量。**
    记录只指 producer；模型、规则、输入、输出细节在 action_log。目标是可归因，不承诺 LLM 逐位重放。
11. **LLM 出候选，规则做裁决。**
    能确定性完成的不交给 LLM；LLM 输出必须经原文锚定、结构化校验、规范归一和准入规则后才能入账。
12. **推拉双向。**
    数据流入沿 change feed 推；预测缺口通过 evidence_request 拉。
13. **课题不是旁支。**
    课题是 L6 行动库中的复合行动，其资料必须走 L1 / L2 / L3，不能绕过证据层改预测。
14. **规则与调度分离。**
    规则是判断依据，调度是运行控制，行动是一次执行。
15. **人批关键认知变化。**
    框架、口径契约、重大冲突裁决、对 L3 / L4 / L5 的重大修改候选、正式预测发布必须有人参与；低风险修改候选可按规则自动通过并留痕（§4.8）。
16. **快照不可回改。**
    发布后只能产生新快照或重述复盘。

# 1. 总体形态

系统由一条主管道、一个旁路层、一根调度脊柱、一个存储与运维底座、两条记录线和一个拉式取证回路组成。

## 1.1 分层总图

```text
                        ┌──────────────────────────────┐
                        │  L4 知识与规则层               │
                        │  框架库 / 规则工件库 / 规范库  │
                        └──────────────┬───────────────┘
                                       │ 加载规则 / 引用框架 / registry 归一
                                       ▼
┌────────────────┐    ┌────────────────────┐    ┌────────────────────┐    ┌──────────────┐    ┌──────────────┐
│ L1 来源资产层   │ -> │ L2 观测证据层       │ -> │ L3 派生证据层       │ -> │ L5 公司预测层 │ -> │ 预测快照      │
│ data_asset     │    │ evidence_record    │    │ derived claim /    │    │ 驱动树/假设   │    │ 正式/影子     │
│ 信封+kind       │    │ 账本+采信视图       │    │ canonical fact     │    └──────────────┘    └──────────────┘
└────────────────┘    └────────────────────┘    └────────────────────┘            │
        ▲   │ change feed（推）        ▲                    ▲                     │
        │   └────────────────────────►│                    │                     │
        │                             └──── evidence_request / 课题取证（拉）◄────┘
        │
        └──── 公告 PDF 服务 / Dataset API / web / MCP / Claude / Codex / 人工上传 / Excel / OCR

               ┌──────────────────────────────────────────────┐
               │ L6 调度脊柱：感知 / 触发 / 准入 / 行动 / 队列 │
               └──────────────────────────────────────────────┘

               ┌────────────────────┐      ┌────────────────────┐
               │ 执行账本 action_log │      │ 人机待办            │
               │ 输入/输出/版本/动作 │      │ 裁决/调研/补证据     │
               └────────────────────┘      └────────────────────┘

               ┌──────────────────────────────────────────────────┐
               │ 存储与运维底座（横切）：文件存储 / DB / 数据目录 │
               └──────────────────────────────────────────────────┘
```

## 1.2 主管道：数据推动预测

```text
L1 data_asset（来源资产）
→ L2 evidence_record（观测证据 / 采信视图）
→ L3 derived claim / canonical fact（派生证据）
→ L5 assumption / driver tree / forecast node（假设与预测）
→ forecast snapshot（预测快照）
```

新公告、新财报、新纪要、新 API 数据、新网页资料进入时，系统不直接改预测，而是先在 L1 形成可追溯来源资产，再在 L2 形成观测证据，然后在 L3 形成归一化、对账后、派生后的证据，最后由 L6 判断是否影响 L5 的假设和预测。

## 1.3 L1 / L2 / L3 的本质关系

```text
L1 = 来源资产层：把外部资料、结构化数据、工具结果、人工上传件转成可追溯、
     可消费、可增量感知的 data_asset。raw 处理在此截止。

L2 = 观测证据层：从 L1 data_asset 中吸收精选的高价值信息并证据化，
     经规范库统一主体 / 时间 / 单位 / 指标 / 关系 / 口径，
     长期维护采信、冲突、冷存、人工裁决与 as-of 账本。

L3 = 派生证据层：基于 L2 当前证据视图和 L4 规则 / 契约 / 规范库，
     构造公司 / 行业 / 主题 / 宏观层面的 derived claims、canonical facts
     和对账后事实——通常是"综合多条 L2 证据才有"的新价值状态。
```

三条判别规则：

1. **判别 L2 与 L3 的标准仍是"来源直接说的 vs 系统按规则构造的"**。"综合多条 L2"是 L3 的典型形态，不是判别标准——单条 numeric_observation 按口径契约派生扣非值，同样属于 L3。
2. **L2 的"清洗提纯"通过选择性证据化实现**：不修改、不删除 L1 资产；废话的处理方式是"不为它建证据记录"，不是物理清除。每条证据必须指回原文定位。
3. **"统一口径"分两段**：L2 做口径标注与 registry 归一（raw → normalized）；L3 做口径契约下的重构（扣非、合并范围调整等）。

来源分级（Tier）的目的也在于此：分级决定 L2 吸收什么、按什么规则采信、需要什么强度的对账（见 §2.9）。

## 1.4 主体域：公司 / 行业 / 宏观 / 主题

公司、行业、宏观、主题不是单独层，而是 L2 / L3 的主体域和作用域。

**主体域不是主体的分类学，而是路由语义**：它声明"该主体的信息按哪套合同被下游消费"。一个枚举成员存在的唯一依据是拥有独立的下游消费合同——两个域若消费方式相同就该合并；某主体若无法套进任何一份现有合同，才有资格讨论新增域。

| 主体域 | 例子 | 下游消费合同 |
|---|---|---|
| company | 公司、子公司、业务线 | 唯一可直接成为 L5 预测建模对象的域（传导终点） |
| industry | 行业、产业链环节、供需格局 | 横截面聚合 / 比较口径与行业 driver 输入，不单独出结论 |
| macro | 政策、利率、汇率、关税 | 永远不是预测主体，只能经 driver mapping 折算进公司 |
| theme | Rubin、CPO、AI 服务器 | L6 传导图的载体（跨公司影响路径），本身不进投资结论 |

**industry 与 theme 的判别规则**：industry 有外部分类学锚点（行业分类标准、产业链位置），长期存在；theme 是有生命周期的传导假设——会退潮、会被证伪、也可"毕业"成 industry。生命周期不新增字段，复用 Subject Registry 双状态机制：退潮 → status = inactive；毕业 → status = inactive 且 successor_id 指向新登记的 industry 主体（§6.5.1）。

主体域枚举锁定为这四类。产品、平台等是**主体的 subject_kind（即 entity_type）**，由 L4 Subject Registry 承担；每个 subject_kind 归属且仅归属一个主体域，subject_domain 由 kind → domain 映射派生，不单独录入（映射表见 §6.5.1）。客户、供应商是**关系角色**不是 subject_kind，经 Relation Registry 的 role_schema 表达（§6.5.5）。区域作为口径切片走 Scope Registry 的 region 轴（§6.5.6）。以上都不扩充主体域枚举。同一条信息可以从主题传导到行业再传导到公司；L6 负责跨主体域传播影响，L5 只接收最终会影响具体公司预测的输入。

## 1.5 推拉双回路

**推**：L1 / L2 / L3 每层对下游暴露同构的 change feed（见 §2.8）。新资产、证据状态变化、派生失效沿 feed 传播，由 L6 消费并决定行动。

**拉**：新增个股、冷启动、关键假设缺失、冲突无法裁决、人工问题时，从预测问题出发生成 evidence_request（见 §8.6）：

```text
L5 假设缺口 / L3 派生缺口 / L2 冲突缺口 / 人工问题
→ L6 生成 evidence_request（绑定目标、来源要求、预算、结案条件）
→ 先查存量：L2 账本 / 冷存 / 历史查空记录 → L3 既有派生（§10.8）
   ├─ 存量可满足 → 直接触发 L3 重派生 / L5 假设更新，request 结案，不取新数据
   └─ 确有缺口 → L1 获取或登记新 data_asset
                → L2 证据准入 → L3 派生 → L5 更新假设或生成待办
```

禁止的捷径：

```text
agent 缺数据 → 自己上网 → 总结一个答案 → 直接改预测
```

## 1.6 旁路层：L4 知识与规则层

L4 不装事实，装三类东西：

1. **框架库**：怎么理解一个行业、公司、业务、技术路线、商业模式、财务结构。
2. **规则工件库**：怎么抽取、清洗、对账、仲裁、派生、复盘、设定口径契约。
3. **规范库 / Registry**：主体、单位、时间、指标、关系、口径的命名与归一规范，支撑 raw → normalized。

它被 L2、L3、L5、L6 和课题回路加载使用，但不替代证据层。

## 1.7 调度脊柱

```text
感知 → 触发 → 准入 → 行动 → 队列
```

- 感知：维护最小血缘图与订阅索引；
- 触发：消费 change feed、定时事件与人工指令；
- 准入：判断是否值得执行、立即执行、入队、仅记录或转人工；
- 行动：执行抽取、校验、对账、派生、重算、取证、课题推进等动作，全部落 action_log；
- 队列：管理失效、重算、低优先任务、人工待办和失败重试。

## 1.8 存储与运维底座（横切）

- **文件存储**：自维护原始字节（公告 / 财报 PDF、人工上传原件）与派生工件（parser artifact 等），按路径 + 哈希存放。
- **数据库**：各层核心对象同一物理库内按职责分 schema，不按层分库。DB 只存需被约束 / 去重 / 版本化 / 追溯 / 检索的对象；大文件留文件系统，DB 存路径 + 哈希。
- **数据目录**：L1 / L2 的稳定检索键、统一 URI、public views 是底座的一等公民，从第一天设计（见 §2.3、§4.20）。
- **运维**：schema 迁移、角色与权限、备份、保留与清理策略。

底座服务 L1–L6 的全部职责，但不属于其中任何一层。

# 2. 统一范式与命名规范

本章是全文字段与命名的唯一权威。其他章节与本章冲突时，以本章为准。

## 2.1 统一信封范式

```text
envelope = identity + scope + time + provenance + payload + state
```

- L1 的信封叫 `data_asset`（§3.2），L2 的信封叫 `evidence_record`（§4.3）。两层信封**同构但不强并为一**：资产与证据的生命周期、状态机、准入规则不同。
- 信封核心字段极少且稳定；差异进 `kind` 判别字段和 payload；横切需求（敏感度、序号、质量）进登记过的扩展字段。
- `evidence_request` 是控制单据（command），不是数据，不套信封（§8.6）。
- change feed 事件同样采用"信封 + kind"范式（§2.8）。
- 信封的六组分组是叙述与对齐结构，不构成契约约束；契约约束只来自字段定义与必选性。

**扩展字段纪律**（借 CloudEvents extensions 目录的做法）：凡非必选字段一律作为"登记过的扩展字段"管理——平铺列化、可索引、命名入规范、在协议中登记用途。以后解决新问题的顺序是：先查已有字段和规范 → 再登记一个扩展字段 + 规范 → 默认不新增顶层对象、不改信封核心。仅当对象具备独立生命周期、独立状态机、独立权限边界或独立血缘根时，才允许经协议升版新增顶层对象。

## 2.2 判别字段规范

| 判别字段 | 层 | 职责 | 枚举 |
|---|---|---|---|
| `asset_kind` | L1 | 资产类型 | document_unit / dataset_snapshot / tool_result / artifact_unit |
| `payload_kind` | L1 | payload 内容形态 | 见下方组合矩阵 |
| `record_kind` | L2 | 记录形态（证据 / 治理） | 证据：observed_claim / relation_claim / numeric_observation / null_observation；治理：change_candidate |

**asset_kind × payload_kind 合法组合矩阵**：

| asset_kind | 合法 payload_kind | 最小可引用单元 |
|---|---|---|
| document_unit | text / table / qa / mixed | 单元本身；表内行列用 locator 定位，mixed 内部件用 parts 序号定位 |
| dataset_snapshot | recordset | 快照本身；行 / 字段用 locator 定位 |
| tool_result | search_result / api_response / page_snippet | 单条返回项 |
| artifact_unit | calculation_table / model_table / checklist / note | 工件内区块，用 locator 定位 |

- `disclosure_anchor` 服务曾用 `unit_kind`（text / table / qa）指代 `payload_kind`（当 asset_kind = document_unit 时）。`unit_kind` 已在代码与契约中收敛为 `payload_kind`，仅作曾用名保留于术语表。
- 每个 `payload_kind` 必须有登记的 payload schema 及版本（§2.7）；kind 不是自由标签。

## 2.3 标识与引用规范

**稳定 ID 与 URI**。每个可引用对象有一个不透明稳定 ID，并可展开为路径式 URI：

```text
{scheme}://{service}/v{n}/{kind}/{stable_id}

asset://disclosure_anchor/v1/document_unit/{asset_id}
asset://upload/v1/artifact_unit/{asset_id}
ev://evidence/v1/record/{record_id}
reg://registry/v1/subject/{subject_id}
act://action/v1/log/{action_id}
```

三条硬规则（借 DataHub key aspect）：

1. URI 只含不可变身份（kind + 稳定 ID / 自然键），字段必须是稳定字符串且必填；
2. 非身份字段（quality_status、title）与跨版本判变字段（content_hash）一律不进 URI，进列化索引字段；content_hash 对单个资产版本不可变；
3. 保留字符与转义规范固定：`/` 仅作层级分隔，其余字符 URL-encode。

**source_ref 是 provenance 引用**。它指向一次文件获取、查询、访问、工具返回或人工上传的可追溯记录，是信封 provenance 组里的一个参数。它可以由派生视图（如 `source_refs_v1`）或 endpoint（`GET /v1/units/{id}/source-ref`）提供，不要求独立主表。

**subject_key 全形式** = `subject_kind:subject_id`，如 `security:002371.SZ`、`company:{不透明 subject_id}`、`theme:ai-server`。前缀是 §6.5.1 的 subject_kind（符合 §2.4：`*_kind` = 判别字段）——security 是 kind 不是主体域，故前缀不能用 domain。company kind 的 subject_id 是 Subject Registry 的不透明稳定 ID，不得用证券代码充当（§6.5.1：实体标识与证券标识分层）。`subject_domain` 由 kind → domain 映射（§6.5.1）派生，单独保留为过滤列；两列一个规范，不新增对象。

## 2.4 命名后缀规范

| 后缀 / 形态 | 含义 | 例子 |
|---|---|---|
| `*_ref` | 对象引用（ID 或 URI） | source_ref、producer_action_ref、raw_asset_ref |
| `*_kind` | 判别字段 | asset_kind、record_kind |
| `*_key` | 稳定检索键 | subject_key、metric_key、period_key |
| `*_status` | 状态 | quality_status、record_status |
| `*_version` | 版本 | contract_version |
| `*_at` | 时刻戳，RFC 3339，存储统一 UTC | observed_at、published_at、started_at |
| `*_date` | 纯日期，YYYY-MM-DD | announcement_date |
| `*_period` | 期间 | report_period |
| `event_time` | 业务发生时点（日期或时刻），valid time | 投产日、会议时间 |
| `basis_time` | 相对时间解析基准时点（形态同 event_time） | basis_time = published_at |
| `as_of` | 复盘截断轴上的时点 | as_of |

**同义字段钦定**（一个概念一个名，其余为局部别名）：

| 钦定名 | 废弃 / 局部别名 |
|---|---|
| asset_id | document_unit_id、unit_id（disclosure_anchor 曾用名；asset_kind = document_unit 时为同一值） |
| published_at | source_publish_time、publish_time；announcement_date 是其披露侧日期粒度形态；disclosed_at 为 disclosure_anchor 契约曾用名 |
| event_kind | event_type（disclosure_anchor outbox 曾用名，已收敛） |
| observed_at | query_time、call_time、access_time、上传时间 |
| action_log | M-LOG（曾用名）；processing_run 是它在 L1 的特化实现 |
| producer_action_ref | producer_ref、action_log_id、extraction_run_id、derivation_run_id |
| payload_kind | unit_kind（disclosure_anchor 曾用名，已收敛） |
| material_type | 资料类型；filing_type 是披露侧的 material_type |
| locator | source_locator、artifact_locator（L1 局部名） |
| subject_candidates | primary_subject_candidates |
| heading_path | section_path |

**semantic_key 跨层不等价**：L1 的 semantic_key 是载体侧粗语义标签（如 receivable_aging，规则 / 人工标注）；L2 的 semantic_key 是 §4.11 定义的规范化组合键。两者是不同规范条目，同名不同物，蓝图复用时不得互相照抄。

中英文对照原则：协议正文中文叙述、字段名英文 snake_case；每个英文术语在术语表（§17）有唯一中文对照。

## 2.5 时间三轴与期间格式

三条时间轴（bi-temporal 的金融扩展）：

| 轴 | 字段 | 含义 | 类比 |
|---|---|---|---|
| 事实轴 | event_time / report_period | 事实发生或为真的时间 | valid time |
| 来源轴 | published_at | 来源公开、或对本系统决策流程可获得该信息的时间（source_available_at 语义），**防前视偏差（look-ahead bias）的 as-of 轴** | 来源侧 transaction time |
| 系统轴 | observed_at | 本系统首次记录的时间 | 系统侧 transaction time |

as-of 查询规则：回测与"当时已知"查询沿 `published_at` 截断（缺失时退化到 `observed_at`）；业务口径筛选沿 `event_time` / `report_period`。对非公开自有资料（调研、访谈、人工笔记），published_at 语义扩展为 source_available_at——资料对本系统 / 决策流程可用的时间；无法证明何时可用时退化到 observed_at（例：6 月 1 日的调研 6 月 5 日才上传且无法证明更早已进入决策流程，as-of 按 6 月 5 日截断）。不引入第四个时间字段。

**期间格式规范**（Time Registry 的核心条目，见 §6.5.3）：

```text
date            YYYY-MM-DD
timestamp       RFC 3339，强制时区偏移，存储统一 UTC（Z）
period 真值     ISO 8601 interval：start/end（如 2026-01-01/2026-03-31）；
                用作 key / 文件名时以 -- 替代 /
quarter label   YYYYQn（如 2026Q1），规范定义为自然季度
annual label    YYYYA（如 2025A），A 股财年 = 自然年
forecast label  YYYYE / YYYYQnE（如 2027E），仅是表面 label；
                真值 = 对应 interval + scope 的 scenario 轴 = estimate，
                保证同一区间的预测值与实际值 period 真值一致、可直接对账
```

财年主体（美股 / 港股等财年 ≠ 自然年的公司）：FY / 财季 label 离开该主体的财年日历不可解析，必须经 Time Registry 的每主体财年日历表解析为 interval 真值。

相对时间必须落四元组：

```text
raw_time_text = "明年"
basis_time    = published_at（默认）；"报告期内 / 本期"类 basis = 该文档 report_period
normalized_interval = 2027-01-01/2027-12-31
resolution_basis    = 说明用哪条基准解析
```

## 2.6 追溯范式：一跳引用 + 递归审计

**记录端契约**：

```text
每条 evidence_record / derived claim 必填：
  producer_action_ref     （wasGeneratedBy：谁产的，一条）
  直接输入引用             （wasDerivedFrom：primary_asset_ref + supporting_asset_refs，
                            或 L3 侧的输入 evidence_record refs）
```

**审计端契约**：全链由只读的递归解析接口 / 视图沿引用遍历重建（带深度参数）；任何跨层引用（如快照直接断言对某 L1 资产的依赖）是显式补充断言，不是默认字段，也不靠传递推理。

一跳引用成立的硬前提：**被引用对象 append-only 且版本化**（§12.3 的不可变清单）。上游对象被取代时产生新版本，不原地改写，旧引用永远可解析。

模型追溯的最小充分集（目标是**可归因**——区分来源变了、模型变了还是规则变了；不承诺 LLM 逐位重放）：

```text
evidence_record 上：producer_action_ref（必填）
action_log 上：model_ref + rule_bundle_ref + input/output refs + 时间 + 状态
```

`rule_bundle_ref` 是 prompt / 解析配置 / 抽取 spec / 校验器 / registry 版本的打包版本引用，粒度须足以区分"prompt 变了"和"parser / 校验器变了"，否则复盘归因到不了具体环节。prompt_version、schema_version、temperature 等不作为记录级默认字段，需要时作为 rule_bundle 的内部构成。纯代码 / 规则动作：model_ref = null，code_ref 必填。

业界锚点：W3C PROV（wasDerivedFrom 不做传递推理）、OpenLineage / Marquez（事件只带直接输入输出，血缘图查询时组装）、MLflow（model version 只存 run_id）、dbt（表只写 invocation_id）、OpenTelemetry（span 只存 parent_span_id）。

## 2.7 版本化双轴与契约演进

| 轴 | 载体 | 变更纪律 |
|---|---|---|
| 信封版本 | `contract_version`（如 data_asset.v1、evidence_record.v1） | 只在破坏性变更时升版；兼容性新增字段不升版 |
| payload schema 版本 | 每个 payload_kind / record_kind 各自的登记 schema | 按 kind 独立演进；不兼容变更 = 换 schema 引用 |

对外契约演进（复用 disclosure_anchor 的 public views 实践）：

- 读契约以 `*_v1` 视图 / endpoint 暴露；升 v2 时 v1 并行保留一段弃用期，弃用须有迁移说明；
- 破坏性变更的定义：删字段、改字段语义、改枚举含义、改唯一性约束；
- 消费方以 (provider, asset_id) 判重：producer 必须保证二者组合唯一（生产侧去重键是其实现，如 disclosure_anchor 的 (provider, provider_document_id, raw_file_hash)）。

## 2.8 变更通知范式：change feed

每层对下游暴露**同构**的 change feed 契约（L1 → L2、L2 → L3 / L5、L3 → L5；所有层的 feed 同时由 L6 消费，§8.3），事件也用信封 + kind：

```text
event = { event_id, source, event_kind, subject_ref, change_seq, occurred_at, payload? }
```

- **两种事件语义**（借 Dagster）：`observed`（巡检过、内容未变，记录 content_hash / data_version）与 `materialized`（新增 / 内容变更 / 取代 / 失效）。**下游失效只由 materialized 触发**；parser 升级但内容快照不变属于 observed，不触发 L3。
- 消费协定：单调 `change_seq` 作游标，可断点续读；at-least-once 投递 + 消费端幂等；同一 subject 内保序。
- L1 的落地形态即 outbox_event 表 + `change_events_v1` 公共视图；对外端点 `GET /v1/changes?after_seq` 为目标契约（随 Phase005+ 落地，见 §3.10）。L2 / L3 同构复制该形态。

## 2.9 来源分级与追溯等级

两套枚举沿 v0.6 收敛保留，并作为规范条目进 registry 管理（source_tier / trace_level 是所有信封的必填 provenance 字段）。

**来源分级 Tier**——决定 L2 吸收什么、按什么规则采信、需要什么强度的对账：

| 层级 | 类型 | 例子 | 使用原则 |
|---|---|---|---|
| Tier 0A | 硬披露锚 | 财报、公告、业绩预告、问询函回复 | 最高优先级；原文必存；用于对账和复盘 |
| Tier 0B | 软披露锚 | 投关记录、业绩说明会、官网材料 | 可提升置信度；仍需结合硬锚 |
| Tier 1 | 结构化外部数据 | 券商库、政府统计、协会、海关 | 重要输入；需记录口径和查询时间 |
| Tier 2 | 外部研究与观点 | 研报、纪要、专家访谈 | 可形成估算 / 观点型证据；需对账、冲突检测 |
| Tier 3 | 弱公开信源 | 自媒体、论坛、社群传闻 | 默认 status=cold；不能单独支撑正式预测 |
| Tier F | 自有一手资料 | 自己调研、专家交流、路演笔记 | 高价值不天然高置信；看可复核性和披露锚一致性 |

**追溯等级 G0–G4**：

| 等级 | 含义 | 判据 |
|---|---|---|
| G0 | 原文级 | 自维护原文 + 文件哈希 + 不可变 unit 快照 + 来源链；page / bbox 仅为可选复核信息 |
| G1 | 数据服务级 | 数据源 + 查询参数 + 返回字段 + as-of |
| G2 | 网页 / 工具级 | URL / 工具名 + 访问时间 + 可定位片段 |
| G3 | 人工记录级 | 会议笔记、访谈纪要、转述记录 |
| G4 | 弱追溯 | 来源模糊、截图不完整、二手传闻 |

硬规则：追溯等级必须进入 L2 证据元数据；弱追溯有置信度上限；G4 不能单独支撑正式预测；重要的弱追溯信息应触发课题或人工待办，而不是直接采信。

# 3. L1：来源资产层

## 3.1 定位

L1 是所有外部输入进入系统前的来源资产层，负责把不同来源转成可被下游引用、可追溯、可增量感知的 `data_asset`。

L1 回答：

```text
这条资料 / 数据 / 工具结果来自哪里？
什么时候取得？用什么 adapter / provider / query / parser 取得？
它现在是什么可消费形态？
它的追溯等级、质量状态和下游契约是什么？
```

L1 不回答：

```text
这是不是高价值投资信息？它支持哪个预测假设？
它和历史证据是否冲突？它应不应该被采信？
```

实现上 L1 是一组按来源划分、各自带 adapter 的接入服务：披露文件侧（`disclosure_anchor`）、标准数据侧（Dataset API + provider adapter）、轻载外部侧（web / MCP / agent 工具登记）、人工上传侧（upload adapter）。`disclosure_anchor` 只是其中一条路径，不等于整个 L1。

## 3.2 统一信封：data_asset

L1 的统一出口不是 `document_unit`，而是 `data_asset` 信封。架构层只要求六组信息，不规定 SQL schema：

```text
A. identity（身份）
   asset_id            稳定 ID，可展开为 asset:// URI
   asset_kind          判别字段（§2.2）
   payload_kind        内容形态（§2.2）
   contract_version    信封契约版本（如 data_asset.v1）
   content_hash        payload 快照哈希，判变与幂等依据（对单个版本不可变）

B. scope（作用域，检索键）
   subject_candidates  公司 / 证券 / 行业 / 主题候选（company_ref、security_ref 等）
   title
   heading_path        文档内标题层级（文档型）
   semantic_key        粗粒度语义键（可选）
   parent_ref          所属 document / dataset 批次 / 上传件
   order_index         同一 parent 内顺序
   material_type       资料类型；披露侧为 filing_type

C. time（时间，§2.5 三轴）
   event_time          业务发生时点（会议时间、事项时间）
   published_at        来源公开时间；披露侧日期形态为 announcement_date
   report_period       报告期（如 2025A、2026Q1）
   observed_at         系统首次登记时间

D. provenance（来源与追溯）
   source_ref          provenance 引用（可为派生视图 / endpoint，§2.3）
   provider / adapter / tool
   query_params        查询 / 访问参数
   source_tier         Tier 0A–F（§2.9）
   trace_level         G0–G4（§2.9）
   locator             原始返回中的定位（URL / 片段 / 结果 ID）
   raw_asset_ref       原始字节引用（文件路径 + 哈希）
   producer_action_ref 生成该资产的动作（L1 局部名 processing_run_ref）
   sensitivity         敏感 / 未公开重大信息标记（合规隔离用）

E. payload（内容）
   payload             按 payload_kind 的内容快照（jsonb）

F. state（状态与变更）
   quality_status      解析 / 登记质量（ok / needs_review / unusable / empty）
   is_active           是否当前 active 版本
   change_seq          change feed 序号
   superseded_by       被哪个新资产取代（可选）
```

必选最小核：`asset_id`、`asset_kind`、`contract_version`、`observed_at`、`source_ref`、`source_tier`、`trace_level`、`payload` 或 `raw_asset_ref` 至少其一。其余字段按扩展字段纪律管理（§2.1）。

查询键（scope / time 组与 quality_status、content_hash）应列化、可索引；payload 承接变化快的内容。这与 `disclosure_anchor` 已验证的"稳定键列化 + jsonb payload"手法一致。

## 3.3 asset_kind 分型

| asset_kind | 说明 | 例子 |
|---|---|---|
| `document_unit` | 自维护文档 / 人工文本 / OCR 后文本的最小可追溯结构单元 | 公告段落、完整表格、完整 Q&A、纪要片段 |
| `dataset_snapshot` | 标准结构化查询结果或数据快照 | Wind 三大表、行业数据库、Tushare 查询结果 |
| `tool_result` | web / MCP / Claude / Codex / 插件返回的轻载外部结果 | 搜索结果项、网页片段、MCP tool JSON |
| `artifact_unit` | 人工计算工件、模型表、勾稽表被 L1 结构化后的单元 | Excel 区块、手工利润桥、调研问题清单 |

三条说明：

1. **人工上传不是单独的 asset_kind**。上传只是入口，上传件经 upload adapter 处理后按内容形态成为 document_unit（纪要文本）、dataset_snapshot（数据摘录表）或 artifact_unit（计算 / 模型工件）。
2. **查空不是 asset_kind**。"查过但没找到"记录在 provenance 层（source_access 访问记录，quality_status = empty），见 §3.9。
3. 每个 asset_kind 的**最小可引用单元**按 §2.2 矩阵执行；L2 引用快照内某行 / 某字段时用 locator，不为此拆更细的资产。

## 3.4 raw 边界：raw 止于 L1

```text
raw PDF / raw image / raw OCR / raw audio / raw PPT / raw Excel
→ L1 adapter / upload service / parser service
→ data_asset
→ L2
```

L2 收到 raw PDF、未 OCR 图片、未解析音频、未结构化 Excel 时，返回：

```text
L1_PROCESSING_REQUIRED
```

或由 L6 生成回流任务，把资料送回对应 L1 adapter。L2 不得自行解析文件。

这条边界必须硬写。否则 L2 会同时承担 PDF parser、OCR、表格识别、web fetch、claim 抽取、冲突检测的全部职责，成为全系统最重且不可维护的层。

## 3.5 载体规范化

v0.7 删除"A 类 / B 类清洗"的叫法。L1 做的是**载体规范化（carrier normalization）**——只处理结构和载体，不做投资语义：

- PDF / Word / PPT / 图片 / OCR / 文本解析；
- 段落、标题、表格、Q&A、列表、注释切分（按业务结构切，不按版面和 token 切）；
- 表格标题、表头、行头、单位、脚注保留；Q&A 问题与回答绑定；
- heading_path / order_index / semantic_key / content_hash 生成；
- 页眉页脚、页码、水印、控制字符等稳定噪声处理；
- raw 文件保真留存或登记；producer_action_ref / contract_version / quality_status 记录。

L1 不做：claim 抽取、高价值判断、预测相关性判断、投资主题归因、证据采信、冲突仲裁。

一句话：

```text
L1 负责让 unit 不孤立；L2 负责理解 unit 在说什么。
```

**安全红线**：L1 不得因"像套话"删除可能含有实质风险、业绩变化、会计政策、重大事项的信息。可以标记质量或不为其生成 unit（原文和 parser artifact 仍保留、可重处理），但不得让下游永久不可见。"重要提示"这类常含退市风险、业绩大变的板块，不得按标签整段跳过。

## 3.6 scope / context 检索键与继承

每个 data_asset 都应尽量带上可索引的 scope / time 上下文（§3.2 B / C 组）。关键规则：

> **company_ref、security_ref、report_period、material_type 不是只属于 document 的字段。它们必须从 document 继承到每个 unit 的可检索上下文。**

否则 L2 / L3 无法按"某公司某报告期的所有毛利率相关单元"直接召回，每个消费方都要自己 join。

继承是**契约 / 视图层的反范式化承诺**：public view 和 API 返回的每个 unit 都带全 scope keys；物理存储可自由范式化（unit 表外键 + 视图 join 均可）。

## 3.7 各 asset_kind 的 payload 契约要点

**document_unit（payload_kind = text / table / qa / mixed）**：沿用 `disclosure_anchor` 的契约——text 保留完整业务边界的正文；table 保留表名、单位、表头、行数据、脚注的完整结构，跨页仍是一个逻辑单元，不拆 cell；qa 保留完整 Question + Answer，不按 token 拆碎；mixed 承载一个业务块内 text/table 交替的完整事项（议案、短公告整体、长文档业务小节），payload 为 semantic_type + 有序 parts。单元切分优先级、保留 / 跳过策略、质量控制沿 `service-purpose.md` §8–§14。

**dataset_snapshot（payload_kind = recordset）**：必填 provider、dataset_key、query_params、returned_fields、provider 侧 as-of、adapter 版本；返回记录或可复查摘要进 payload。同一 dataset 的字段契约由 dataset_registry（Git 管理的 L1 adapter 配置清单，不属于 L4 规范库六册）声明，DB 只记实际发生的访问。

**tool_result（payload_kind = search_result / api_response / page_snippet）**：必填 tool / harness 名、query、observed_at、returned_items、每项的 locator（URL / title / citation / snippet / 结果 ID）；raw response 可选留存。

**artifact_unit（payload_kind = calculation_table / model_table / checklist / note）**：必填作者 / 上传人、material_type（人工显式标记，见 §3.8）、涉及公司 / 行业 / 主题候选、event_time（资料对应时间，非上传时间）、可复核性、sensitivity；文件哈希 + 原件引用。

各 kind 的信封字段完全一致，差异只在 payload 与少数必填项——一张 kind × 必填字段矩阵即可校验一致性。

## 3.8 人工上传入口

人工上传走统一 upload adapter，复用 disclosure_anchor 蓝图（信封 + producer_action_ref + public view + change feed），不单独做一套体系：

```text
人工上传文件 / 文本 / 表格 / 图片 / 录音转写
→ L1 upload adapter：登记、哈希、载体规范化
→ data_asset（document_unit / dataset_snapshot / artifact_unit）
→ L2 准入
```

判定责任：

- 上传时**由人显式声明 material_type**（纪要 / 数据摘录 / 计算工件 / 模型假设 / 框架建议）；L1 只按显式标记归 kind，不做语义推断；
- 标错由 L2 准入退回改派，动作记 action_log；
- 拿不准时默认按 artifact_unit 登记，走 change_candidate 复核路径（§4.8），而不是默认按证据处理。

## 3.9 查空与检索记录

主动 search、API 查询、MCP 调用即使没有结果，也要记录。查空记录在 L1 provenance 层：一条 source_access 访问记录（记录查询参数、时间、空结果状态），不建 data_asset。

"查过但没找到"的三个价值：避免重复检索；说明某结论目前缺证据而不是系统忘了查；可转为人机待办。

仅当"已查无果"本身是某个 evidence_request 的结论性回答时，才由 L2 生成 `evidence_record(record_kind = null_observation)` 引用该访问记录并回链 request_ref（§4.4）。同一次查空不在两层重复建对象。

URL 日后失效 → source_ref 仍在，按追溯等级降级，不当作没记过。

## 3.10 disclosure_anchor：L1 adapter 的模板实现

`disclosure_anchor` 是 L1 中"上市公司公告 / 财报 PDF"路径的落地实现，其手法作为 L1 其他 adapter 的复用蓝图：

```text
PostgreSQL 主库 + 文件系统（原始 PDF、parser artifact）
三 schema：core（私有写侧）/ public（只读视图 *_v1，跨服务唯一读契约）/ ops（outbox + 迁移）
统一信封：asset_id + payload_kind + payload(jsonb)，稳定查询键列化
版本与去重：processing_run 管 active / history；(provider, provider_document_id, raw_file_hash) 去重
契约版本化：contract_version = normalized_ir.v1；每对象 JSON schema
source_ref 派生：source_refs_v1 视图 + GET /v1/units/{id}/source-ref
变更 feed：outbox_event 表 + change_events_v1 视图（已落地）→ GET /v1/changes?after_seq（目标契约，随 Phase005+ 落地）
最小 provenance：parser = { name, package_version, backend, method, language }
角色最小权限：owner / app / reader / future_l2_reader；跨服务只经 public 视图消费
```

v0.7 对它的三点补强：

1. `document_unit` 的 public view 保留足够 scope keys（company_ref、security_ref、filing_type、report_period、announcement_date、payload_kind、heading_path、semantic_key、quality_status、content_hash、contract_version、producer_action_ref、source_ref、parent_ref、order_index）；
2. 术语对齐本协议（已完成收敛：document_unit_id → asset_id、unit_kind → payload_kind、outbox event_type → event_kind；processing_run 保留为 action_log 的 L1 特化）；
3. change feed 补齐 `GET /v1/changes` 端点与 observed / materialized 两事件语义（§2.8）。

`service-purpose.md` canonical 契约已随本节补强及术语收敛升版（当前 v1.2），front matter 指向本协议。

## 3.11 L1 对外契约

L1 各服务对下游（L2、agent、未来其他服务）的消费契约必须专业、可封装，一页写死：

1. **可寻址**：每个 data_asset 有稳定 ID 与 `asset://` URI（§2.3）；
2. **读契约版本化**：public views / API 按 `*_v1` 暴露，演进遵守 §2.7；
3. **可检索**：按 scope keys（公司 / 期间 / 类型 / heading_path / semantic_key）过滤 + 游标分页是契约义务；
4. **change feed**：游标、at-least-once、幂等、保序语义遵守 §2.8；
5. **错误模型**：错误码枚举至少含 `L1_PROCESSING_REQUIRED`（L1 读侧语义：请求对象仅有 raw 登记、尚未完成载体规范化；L2 输入侧语义见 §3.4）、`NOT_FOUND`、`CONTRACT_VERSION_MISMATCH`、`GONE_SUPERSEDED`；
6. **MCP 映射**（后续包装时零改造）：查询走 tool（参数 = 检索键，游标分页），取回走 resource（`resources/read` 按 URI 返回 public view 契约内容），变更走 `notifications/resources/updated` / `list_changed`；资源只读，写动作（如上传、取证请求）一律建模为 tool。

# 4. L2：观测证据层

## 4.1 定位

L2 是系统的消化系统和免疫系统。

```text
吸收：从 L1 data_asset 中吸收精选的高价值信息（Tier / G 分级为此服务）；
证据化：把高价值文本 / 表格 / 工具结果 / 结构化数据转成 evidence_record；
归一：经规范库统一主体、时间、单位、指标、关系、口径（raw → normalized）；
账本：长期维护采信视图、冲突状态、人工裁决、冷存、as-of 可复盘的观测证据账本。
```

L2 负责回答：

> 来源直接支持了什么？以什么形式进入系统？当前是否被采信？是否有冲突？

L2 不负责回答：

> 系统基于这些证据最终推导出了什么？（属 L3）

L2 不处理 raw（§3.4），不做 PDF / OCR / web fetch / 第三方 API 原始拉取——那些是 L1 adapter 或 L6 调度动作。

## 4.2 输入准入

L2 只接受满足以下条件的输入：

```text
有 asset_id、asset_kind / payload_kind、contract_version；
有 source_ref 或等价 provenance；
有 source_tier / trace_level；
有基本 scope / time / quality_status；
payload 已由 L1 结构化到可消费形态。
```

不满足条件的输入不进入抽取，只能：退回 L1（`L1_PROCESSING_REQUIRED`）、进错误队列、形成人机待办、或生成 evidence_request 补资料。

L2 经 L1 的 public views / API / change feed 消费资产，不回读 L1 私有表。

## 4.3 统一信封：evidence_record

L2 的统一产物是 `evidence_record`，信封与 data_asset 同构：

```text
A. identity（身份）
   record_id           稳定 ID，可展开为 ev:// URI
   record_kind         判别字段（§4.4）
   contract_version    如 evidence_record.v1
   semantic_key        语义聚合 / 去重键（§4.11）

B. subject（主体与语义，检索键）
   subject_key         全形式 subject_kind:subject_id（§2.3）
   subject_domain      company / industry / macro / theme（由 subject_kind
                       映射派生，不单独录入，§6.5.1）
   metric_key          指标（经 Metric Registry 归一）
   relation_key        关系类型（经 Relation Registry 归一，关系型必填）
   scope_key           口径轴 = 成员（经 Scope Registry；未知口径必须显式 unknown）
   claim_nature        fact / estimate / forecast / assumption / opinion / rumor / explanation / note
                       （assumption = 来源直接陈述的假设，如"指引基于汇率 7.2 的假设"；
                         人工假设输入走 change_candidate(target_layer=L5)，§4.8）
   statement_direction 上升 / 下降 / 放量 / 进入 / 退出 / 延迟 等（可选）

C. time（时间）
   event_time / report_period（period_key）
   published_at        自 primary asset 继承
   observed_at         证据入账时间
   （as-of 查询按 §2.5 规则执行）

D. provenance（来源与生产）
   primary_asset_ref     主来源资产（source_tier / trace_level 按它判定）
   supporting_asset_refs 联合抽取的辅助上下文资产
   exact_span / locator  原文精确定位
   source_tier / trace_level
   producer_action_ref   必填（§2.6）
   request_ref           回应哪个 evidence_request（可选）

E. payload（陈述内容，raw + normalized 双轨，§4.10）
   raw：raw_subject_text / raw_metric_text / raw_value / raw_unit /
        raw_time_text / raw_relation_text / raw_statement
   normalized：canonical_subject_ref / metric_ref / normalized_value /
        normalized_unit_ref / normalized_period / relation 角色结构 / normalized_statement

F. state（状态）
   record_status       状态机（§4.4）
   confidence          置信度（§13）
   conflict_status
   importance
   in_current_view     是否在当前采信视图
   downstream_refs     被哪些 L3 / L5 对象引用
```

两层信封的公司 / 时间 / 口径字段命名一一对齐；§4.20 的检索键就是本信封字段的列化索引。

## 4.4 record_kind 与状态机

**record_kind 判别记录形态**，收敛为五类——前四类是**证据记录**（进入证据账本与 record_status 状态机），change_candidate 是共享同一信封的**治理记录**（不属于证据账本）：

| record_kind | 说明 |
|---|---|
| `observed_claim` | 来源直接支持的自然语言 / 半结构化陈述（含解释与口径注记：claim_nature = explanation / note，必须绑定 locator、禁止改写原文） |
| `relation_claim` | 来源直接支持的供应、客户、送样、认证、竞争、替代等关系（角色结构经 Relation Registry 归一） |
| `numeric_observation` | 标准结构化数据或表格字段形成的观测数值，不经 LLM 抽取 |
| `null_observation` | "已查无果"作为 evidence_request 的结论性回答（引用 L1 查空记录，回链 request_ref） |
| `change_candidate` | 治理对象：对 L3 / L4 / L5 的修改候选，经分级审批（§4.8） |

**统一状态机**（主证据记录 record_status 的唯一枚举，钦定于此；适用于 observed_claim / relation_claim / numeric_observation 三类）：

```text
pending / accepted / contested / rejected / provisional / scenario-set / cold / archived
```

- `cold`（冷存）是**状态**不是 kind：弱信号也是一条低追溯的 observed_claim / relation_claim，status = cold。
- 丢弃不建证据记录：丢弃是一次动作，原因作为**丢弃审计记录在 action_log**，保证"某批资料为什么没进 L2"可粗略审计。

**record_kind × status 合法组合矩阵**：

| record_kind | 状态 |
|---|---|
| observed_claim / relation_claim / numeric_observation | record_status 全部八态 |
| null_observation | 入账即 archived（无中间态，不进采信视图） |
| change_candidate | 独立 candidate_status：proposed / approved / rejected / applied（治理生命周期，不共用 record_status，不进采信视图、不参与 as-of 证据账本） |

被 v0.7 否决的 kind 及去向：`cold_signal` → status=cold；`discard_log` → action_log 丢弃审计；`source_note` → observed_claim（claim_nature = note）。

## 4.5 文档型路径：高价值选择性抽取

对 document_unit（text / table / qa / mixed）、纪要、OCR 文本，L2 做高价值选择性抽取。

```text
claim 不是每句话一条。
claim 是可能影响预测、对账、冲突、订阅、复盘或课题推进的证据单元。
```

抽取准入清单（满足其一才入账）：

1. 可能影响收入、价格、订单、产能、良率、成本、费用、毛利率、税率、现金质量、客户结构、供应关系；
2. 可能改变公司 / 行业 / 主题 / 宏观的关键关系；
3. 可能与披露锚、历史证据或当前假设冲突；
4. 未来财报季可能用于验证或归因；
5. 能触发 L3 派生、L5 假设或人机待办；
6. 暂不能采信但值得冷存累计（status = cold 入账）。

普通背景、套话、重复观点、泛泛行业描述，不进入证据账本。

**允许输出空列表**：

```text
evidence_records = []
```

表示当前输入没有达到门槛的高价值证据。过程留痕在 action_log 即可，不为"无 claim"造语义对象。

两种"空"必须区分：**抽取为空** = 空列表 + action_log 留痕；**查询未得** = L1 查空记录（§3.9），是来源层事实，不能被空列表一并简化掉。

**抽取窗口是运行时输入，不是长期对象**。L2 可在运行时组窗（Q + A；表格 + 注释 + 同章节文字；某段 + 前后相邻段落），靠 parent_ref、order_index、heading_path、qa 绑定实现；窗口本身不入账，每条产出证据只记 primary_asset_ref + supporting_asset_refs + exact_span。

## 4.6 结构化数据路径：numeric_observation

Wind / iFinD / Choice / Tushare / 券商库 / 政府协会数据返回的标准结构化数据，**不做 LLM claim 抽取**：

```text
L1 dataset_snapshot
→ L2 numeric_observation（字段校验、registry 归一、口径标注、准入登记）
→ L3 canonical facts / derived facts
```

这是"跳过 LLM 抽取"，不是"绕过 L2 准入"。numeric_observation **不重复存** provider / query_params / as-of——这些沿 primary_asset_ref 一跳继承（§2.6）；source_tier / trace_level 按 primary asset 判定后物化落列（供检索与准入，§4.3 D 组）。L2 只新增它真正产生的东西：

```text
field_mapping（provider 字段 → metric_ref 映射）
口径标注（scope_key，未知则显式 unknown）
单位 / 期间归一结果
quality 判定
```

## 4.7 轻载外部路径：tool_result 准入

web / MCP / Claude / Codex / 插件返回进入 L1 后是 `data_asset(asset_kind = tool_result)`，不直接是证据。

L2 仅在满足以下条件时把它提升为证据：有可定位来源（locator / citation / snippet / URL / 结果 ID）；能区分 agent 总结与原始来源；能定 source_tier / trace_level；能进 raw + normalized 双轨。

硬边界：

> **agent 的总结不是来源。** agent 总结里引用的网页、PDF、API 返回、数据库结果、原文片段才是来源。

没有可定位支撑的，只能 status = cold 或转人机待办，不能 accepted；重要结论必须补更强来源；任何会影响正式预测的 tool_result 证据必须能追到 source_ref 和原始返回片段。

## 4.8 人工工件路径：change_candidate 治理区

人工上传按内容性质证据化：

```text
人工纪要 / 调研笔记 / 专家转写      → document_unit → observed_claim / relation_claim
人工整理表 / 原始数据摘录          → dataset_snapshot 或 document_unit(table) → numeric_observation / observed_claim
人工利润桥 / 手工模型 / 勾稽计算    → artifact_unit → change_candidate(target_layer=L3)
人工框架建议 / 投研模板 / 规则建议  → artifact_unit → change_candidate(target_layer=L4)
人工假设输入（ASP / 出货量 / 毛利率）→ artifact_unit → change_candidate(target_layer=L5)
```

**不允许人工文件直接改 L3 / L4 / L5**。修改候选统一走：

```text
change_candidate(target_layer = L3 / L4 / L5)
→ 人批（批准 / 驳回，留痕 action_log）
→ 对应层机制承接落地
```

change_candidate 是既有机制的**统一入口，不是第二套审批**：target_layer=L5 批准后落为假设账本的人工覆盖记录（§7.7）；target_layer=L4 批准后进入框架 / 规则条目演进流程（§10.13）；target_layer=L3 批准后由 derivation 动作按规则重算生成。

审批分级：低风险类（如个别参数微调）可按规则自动通过并留痕；重大变更（框架结构、口径契约、关键假设覆盖）强制人批。单人研究场景下人批 ≈ 一次显式确认 + 留痕，流程要轻，但留痕不可省。

## 4.9 联合抽取规范

一次 L2 action 可以接收多个 asset_refs 联合抽取：

```text
公告表格 + 表格注释 + 同章节文字；
Q + A；
会议纪要片段 + 附带 Excel 表；
Wind 三大表 snapshot + 财报 document_unit（交叉验证）；
同一问题下的多个 tool_result。
```

四条纪律：

1. 联合只是**运行时 action input**，不新增长期 packet 对象；聚合靠 source_ref、parent_ref、heading_path、subject_key、metric_key、producer_action_ref 等字段自然完成；
2. 每条产出证据记 primary_asset_ref + supporting_asset_refs + exact_span；
3. **防追溯稀释**：source_tier / trace_level 按 primary asset 判定，supporting 只作上下文，不得借联合抽取抬升弱来源等级；
4. **防跨主体污染**：联合范围默认限定同一 subject / 同一 document；跨主体、跨来源域的联合必须由 evidence_request 或人工动作显式圈定。

## 4.10 raw + normalized 双轨

每条主证据记录保留两层：

```text
raw：原文怎么说（还原来源原始表达）
normalized：系统为对账、检索、冲突、派生所做的规范化
```

| raw | normalized | 归一依据 |
|---|---|---|
| raw_subject_text（"旭创"） | canonical_subject_ref | Subject Registry |
| raw_metric_text（"营收"） | metric_ref | Metric Registry |
| raw_value + raw_unit（"100 万张"） | normalized_value + normalized_unit_ref | Unit Registry |
| raw_time_text（"明年"） | normalized_period（四元组，§2.5） | Time Registry |
| raw_relation_text | relation_type + 角色结构 | Relation Registry |
| 口径原文 | scope_key（轴 = 成员） | Scope Registry |

铁律：normalized 不能新增原文没有的事实，只做最小必要标准化；normalized 不覆盖 raw。归一遇到 registry 未收录的对象 → 走 registry_candidate 流程（§6.6），期间以 raw + provisional 值使用。

## 4.11 去重、幂等与取代

- **同一来源同一位置的重复抽取**（模型升级重跑、action 重试）按 `(primary_asset_ref, exact_span, semantic_key)` 幂等：新 action 产物**取代**旧产物（旧版本保留，superseded 关系入账本）。
- **不同来源的同语义陈述**（卖方 A 说 35%、纪要 B 说 30%）**并列入账，不互相覆盖**；谁进当前采信视图由采信规则与人工裁决决定（§4.15）。
- `semantic_key` 生成规范：`subject_key × metric_key / relation_key × period_key × scope_key × claim_nature` 的规范化组合，用于同类证据的召回、去重判断与订阅匹配（与 L1 载体侧的粗语义标签同名不同物，§2.4）。

## 4.12 披露锚对账

外部细分数据不能无解释地违反披露锚。卖方分项加总与财报披露差距过大时：

```text
识别口径差异候选（合并范围 / 期间 / 币种 / 税费 / 一次性项目 / 分类差异）
→ 按对账规则计算偏离度
→ 按偏离度调置信度
→ 超阈值转 contested
→ 必要时生成待办或情景分支
```

对账规则放 L4 规则工件库，L2 加载执行；复杂对账后的结果（分业务收入重构表、对账后毛利率区间）放 L3。

## 4.13 校验隔离

- 生产 agent：从原文抽取证据候选；
- 校验 agent：只看原文和抽取结果，不看生产推理过程；
- 冲突 agent：对比历史证据、当前采信视图、披露锚和相关假设；
- 重要性 agent：只提建议，最终由确定性准入规则决定。

目的不是迷信多 agent，而是降低单次抽取幻觉和顺着错误推理继续错的概率。

## 4.14 冲突检测

关系型证据先经 Relation Registry 归一再判冲突：主体、关系类型、阶段、期间、口径都接近时才进入冲突判断；阶段推进（送样 → 认证 → 量产）不判冲突。冲突类型与处理方式见 §13。

## 4.15 当前采信视图

当前采信视图是系统在某时点认为最适合进入派生或预测的证据集合。它不是第二套真相，而是对并列证据经规则、对账、冲突检测、人工裁决后的当前视图。

- 必须版本化，支持 as-of 查询；
- 视图变化沿 L2 change feed 通知 L3 / L5 / L6；
- 高重要性 contested 证据不能被静默吞掉：必须至少触发人工待办、L3 情景派生、L5 情景分支、影子预测或正式预测阻塞之一。

## 4.16 人工裁决

人工裁决本身是系统长期资产。每次裁决至少记录：裁决对象、结果、理由、使用资料、是否覆盖机器判断、影响哪些证据 / 派生 / 假设、是否触发重算、是否应回写规则或框架。裁决动作落 action_log。

## 4.17 冷存 / 弱信号

status = cold 的证据构成冷存池——L2 账本的边缘区，不是垃圾箱。Tier 3 信源默认先进 cold。

触发机制（缺一不可，否则只是垃圾箱）：同主体同方向累计超阈值；与当前高敏感假设相关；新硬锚出现后可验证；被课题 / evidence_request 查询命中；某 driver 转 contested；临近财报；人工激活。

触发后可：转 pending 重审、升 accepted、生成课题候选、生成待办、或继续 cold。Tier 3 证据可作早期信号、检索线索、课题触发器、辅助印证，但不能单独支撑 accepted 或 valid derived claim。

## 4.18 分流结果

L2 对每个输入的处置去向：

1. 入账为 evidence_record（含 status = cold）；
2. 更新当前采信视图；
3. 生成 change_candidate（治理区）；
4. 转人机待办；
5. 丢弃（action_log 留丢弃审计）。

## 4.19 as-of 语义

L2 必须支持 as-of 查询：

> 回到某个历史时点，系统当时见过哪些证据、采信哪些、否定哪些、冷存哪些、冲突哪些？

as-of 沿 §2.5 时间三轴执行。没有 as-of 就无法复盘——不能用今天才知道的信息评价昨天的预测。

## 4.20 L2 数据目录与服务化

**协议级可检索承诺清单**（即 L2 的检索键，全部列化索引；此外的字段默认只在 payload，不承诺可检索）：

```text
subject_key / subject_domain     谁
metric_key / relation_key        什么指标 / 什么关系
period_key                       哪个期间（事实轴）
scope_key                        哪个口径切片
source_key                       source_tier / trace_level / provider / material_type
status_key                       record_status / conflict_status / in_current_view
semantic_key                     同类聚合与去重
observed_at / published_at       知识轴（as-of 复盘、增量消费）
producer_key                     producer_action_ref（某 run 作废 → 定向失效其产出）
```

**L2 的服务形态复用 disclosure_anchor 蓝图**：PostgreSQL 分 schema（core / public / ops）、public views `evidence_records_v1` 等作为唯一读契约、outbox change feed 通知 L3 / L5 / L6、稳定键列化 + payload jsonb、`ev://` URI、错误模型与 MCP 映射同 §3.11。

L2 catalog 服务的目标：L3 派生取数、L5 订阅失效、冲突检测、as-of 复盘、人工调研前快速定位证据。

# 5. L3：派生证据层

v0.6 的 L3 主体保留，本版只做对接修订。

## 5.1 定位

L3 基于 L2 观测证据和 L4 规则 / 契约 / 规范库构造 derived claims。它回答：

> 系统基于来源证据、口径契约、对账规则、计算规则和框架映射，构造出了什么？

它管理：derived claims、canonical facts、归一化财务事实、口径重构值、对账后指标、分业务 / 分产品 / 分客户重构视图、行业汇总、主题暴露度、供应链、产业链 / 客户 / 技术路线派生图、供 L5 使用的中间事实层。

## 5.2 L3 不是第二套真相

每条 derived claim 必须能回答：用了哪些 L2 证据、哪版当前采信视图、哪版口径契约、哪些规则 / 框架 / registry 条目、在哪个 as-of 时点生成、输入变化时如何失效重算。

```text
L2 = 来源说了什么；
L3 = 系统按规则从这些说法中构造出了什么。
```

## 5.3 L3 的输入

```text
1. L2 当前采信视图中的 observed_claim / relation_claim；
2. L2 contested / scenario-set 证据（用于区间、情景、冲突解释）；
3. L2 numeric_observation（生成 canonical facts、标准化序列、重构视图）；
4. L4 口径契约、对账规则、计算规则、框架条目、规范库。
```

即两类记录 + 一类视图 + 规则。数值型证据跳过 LLM 抽取，但不跳过 L2 准入（§4.6）。

## 5.4 canonical fact

canonical fact 是 derived claim 的一个子类（同一状态机，不另设对象）：由 numeric_observation 按口径契约和字段映射生成的标准化事实。

```text
Wind 返回某公司 2025A 营业收入
→ L2 numeric_observation
→ L3 canonical revenue fact（口径契约 + 字段映射）
→ L3 同比 / 环比 / 费用率 / 毛利率 / 扣非净利润等 derived facts
```

追溯链：canonical fact → numeric_observation → dataset_snapshot → source_ref。

## 5.5 典型派生类型

沿 v0.6：口径重构型（扣非、合并范围重构）；对账后事实型（分业务收入重构表、偏离解释桥）；计算派生型（毛利率、ASP、周转、现金转化率）；关系网络派生型（暴露度、供应链图、客户敏感度）；区间 / 情景派生型（乐观 / 基准 / 悲观路径、敏感性矩阵）。

## 5.6 derived claim 的信息维度

派生主体与主体域、指标 / 事件、派生值（数值 / 区间 / 文本 / 矩阵 / 视图）、时间范围、scope_key、输入证据引用集合、当前采信视图版本、契约 / 规则 / 框架 / registry 版本引用、producer_action_ref（派生动作统一落 action_log，废弃 derivation_run 独立对象名）、as-of、置信度继承逻辑、是否含 contested 输入、是否可进 L5 主假设、失效条件、downstream_refs。

## 5.7 状态与失效

```text
valid / stale / contested / provisional / scenario-derived / archived
```

上游证据、采信视图、规则、契约、框架、registry 任一变化 → 受影响对象标 stale 入失效队列（§8.7）；状态变化沿 L3 change feed 通知 L6 / L5。

## 5.8 L2 / L3 边界例子

```text
L2：纪要说 A 公司向苹果送样；公告说某产线投产；Wind 返回 2025A 营收；
    研报认为某产品毛利率 35%；纪要认为 30%；财报披露整体毛利率 28%。

L3：派生 A 公司苹果链收入暴露度；重构某产品 2027E 收入区间；
    派生该产品当前可用毛利率区间 30%–35%、基准值 32%，
    并标记含 contested 输入、需进 L5 情景分支。
```

## 5.9 L3 到 L5

L5 优先消费 L3（口径统一、对账、冲突处理、计算派生已完成）；但正式快照必须能从 L5 假设递归追到 L3 → L2 → L1（§2.6 审计端契约）。

## 5.10 as-of 语义

L3 必须支持 as-of：回到历史时点，基于当时可得的 L2 证据和当时的规则 / 契约 / registry 版本，派生出了什么。不能用后来的口径与信息评价旧快照。

## 5.11 硬边界

L3 可以不经过自然语言 claim（numeric 路径），但**不能绕过 L1 登记与 L2 准入**：不允许 L3 临时调用 Wind、web 或 agent search 后无登记地生成派生结果。

# 6. L4：知识与规则层

## 6.1 定位

L4 是旁路层，装三类可版本化资产：框架库、规则工件库、规范库（Registry）。它不装事实。

## 6.2 框架库

存放解释结构：行业研究框架、产业链结构模板、驱动因子模板树、商业模式模板、技术路线框架、财务预测模板、三大表建模框架、现金质量检查框架、利润桥模板。

框架条目必须：条目化、版本化、可引用、可被快照记录、可被复盘归因；重大修改需人批。

## 6.3 规则工件库

存放操作规则：载体规范化规则、抽取规则、对账规则、冲突仲裁原则、置信度规则、重要性准入规则、派生规则、聚合规则、课题模板、复盘归因规则、快照发布规则。

规则回答"怎么判断怎么处理"；调度回答"什么时候执行谁执行"；行动是一次执行。三者分离。

## 6.4 口径契约

规则工件库中的最高优先级规则。定义历史重构、未来预测、财报复盘的统一口径，采用：

```text
全局基准 + 公司附录
```

每条契约政策拆两段：文字理由（供人与 agent 理解）+ 可执行规则（引擎执行）。

硬规则：**历史重构、未来预测、财报复盘必须引用同一版口径契约**。契约升版触发相关 L3 失效、公司重算、复盘重述，但不覆盖原快照。

## 6.5 规范库 / Registry

Registry 支撑 raw → normalized，解决主体、单位、时间、指标、关系、口径的统一。它不是世界事实库，也不是投资框架库。

**分期**：第一阶段只做 Subject / Unit / Time + 最小 Metric（刚需）；Relation / Scope 先只强制一条纪律——**未知口径 / 未知关系类型必须显式标记，不得默认同口径**——成熟后再展开。

### 6.5.1 Subject Registry（主体册）

解决"这是不是同一个对象"。范式 = 不透明稳定 ID + 类型化别名 + 标识挂接 + 双状态。

```text
subject_id          不透明稳定 ID（消歧靠 ID + description，不靠名称唯一）
subject_kind        company / security / product / platform / industry /
                    theme / macro_factor（entity_type，经下方映射表唯一确定
                    subject_domain，不扩充四大主体域枚举；customer / supplier
                    是关系角色，不入 kind，见下方规则）
canonical_name      每语言一个首选名
identifiers[]       (scheme, value, valid_from?, valid_to?, source)：scheme 枚举与
                    匹配优先级见下方"主体匹配键规范"。实体标识（LEI/USCC/CIK）与
                    证券标识（ISIN/ticker）分层，company 与 security 分 kind 登记，
                    禁止互相冒充
aliases[]           (text, lang, alias_type, valid_from?, valid_to?, confidence)
                    alias_type：former_name / trading_name / translit / abbrev
status              active / inactive；+ successor_id（合并 / 消亡指后继）
links               parent / owner / issuer / brand_of 等类型化关系
ambiguous_flag      已知歧义标记
```

**subject_kind → subject_domain 初始映射**（无歧义行锁定；标 ◇ 的行**尚未想清楚、还没有细化**——仅为初始默认值，落地 Subject Registry 前需专门确认，届时经 §6.6 registry 升版通道调整，不动协议正文）：

| subject_kind | subject_domain | 说明 |
|---|---|---|
| company | company | 唯一可直接成为 L5 预测建模对象 |
| security | company | 证券沿 issuer 关系归入发行人的消费合同 |
| industry | industry | 有外部分类学锚点，长期存在 |
| theme | theme | 有生命周期的传导假设载体 |
| macro_factor | macro | 只能经 driver mapping 折算进公司 |
| product ◇ | company | 默认沿 owner 归入其公司的消费合同（如"中际旭创 800G 产品线"）；生态级传导载体应登记为 platform 或 theme |
| platform ◇ | theme | 生态级平台是跨公司传导载体（如 Rubin 平台） |

**customer / supplier 不是 subject_kind**：客户、供应商是**关系角色**，不是稳定实体类型——苹果可以同时是客户、供应商和被预测公司，把角色做成实体类型会让实体身份与关系角色混淆。角色经 Relation Registry 的 role_schema 表达（§6.5.5）；某客户 / 供应商本体需要登记为主体时，按 company（或相应 kind）登记，在关系中承担 customer / supplier 角色。

例：Rubin / NVIDIA Rubin / Rubin GPU / Rubin 服务器 / 英伟达 Rubin 平台**不无脑合并**——Rubin 平台（platform）、Rubin GPU（product）、Rubin 服务器（product）是不同 entity，影响完全不同的产业链映射；owner 关系挂英伟达。同名不自动合并，合并只经 identifier 匹配或人批。

**主体匹配键规范**（"合并只经 identifier 匹配或人批"的具体化；范式借 nomenklatura 的加权标识 + GLEIF 的注册号交叉引用）：

| scheme | 层级 / 辖区 | 强度 | 说明 |
|---|---|---|---|
| lei | 公司级，全球 | 强 | 唯一跨市场公司级标识；有注册状态生命周期（会 lapse），必须带时效 |
| uscc | 公司级，中国注册实体 | 强 | 统一社会信用代码，覆盖非上市；红筹 / VIE 的境外上市主体没有 USCC，禁止拿境内运营子公司的 USCC 冒充上市主体 |
| sec_cik | 公司级，美国 SEC 申报主体 | 强 | SEC 铸造、永不复用（edgartools 即以 CIK 为 canonical） |
| hk_cr | 公司级，香港注册实体 | 强 | 香港公司注册处编号；港股上市主体常为开曼 / 百慕大注册，届时该 scheme 不适用 |
| isin | 证券级 | 中 | 经 security → issuer 关系传导到公司 |
| exchange:ticker | 证券级 | 中 | ticker 会变更 / 复用（FIGI 教训），必须带时效 |
| name+jurisdiction | 兜底 | 弱 | 规范化名称 + 辖区，只产生合并候选，不得自动合并 |

五条规则：

1. **强键相等 → 自动判定同一主体**（Registry 上线时的 crosswalk join 即"核验"）；证券级键先归 security，再沿 issuer 关系传导；弱键只出候选，须规则或人批确认。
2. **标识有生命周期**：每条 identifier 带时效与来源；LEI 失效、重组换号、ticker 复用都以时效表达，不改写历史。
3. **辖区限定，禁止跨主体挪用**：一个主体可同时挂多辖区标识（如 NVIDIA：sec_cik + lei），但上市主体与境内运营实体是不同 subject，其关系走 Relation Registry。
4. **L1 采集义务**：所有创建公司 / 证券侧信息的 L1 producer（disclosure_anchor、upload adapter 等）对本表 scheme"有则必填"；新增 scheme 走 §6.6 registry 升版，不动本表已锁定行。
5. **强键校验数据一律走本地快照，不依赖运行时实时在线**：号码本身（LEI / USCC / CIK 串）在 L1 采集端从披露件或录入取得，不查外部服务；号码 ↔ 主体的校验 / 富化数据以定时同步的本地快照消费（GLEIF LEI、SEC bulk 均提供免费全量下载 + delta，是开放数据），按 §15「不依赖实时在线」与 §3.7 dataset_snapshot 手法登记。禁止在归一 / 预测主链路上直接实时调外部 identifier API；确需在线拉取时走 §8.6 evidence_request 受控回路，产物仍先落 L1。

### 6.5.2 Unit Registry（单位册）

范式 = UCUM 代码 + QUDT quantity_kind。**quantity_kind 判断是否同类可比，conversion_mode 判断如何换算**：

```text
unit_code            单位码
quantity_kind        量的种类：monetary / mass / area / count.gpu_die /
                     count.wafer / count.pcb / count.server / percent / bps ……
structure            simple | complex{numerator, denominator}（元/股、颗/米）
conversion_mode      fixed_factor / external_rate_required / domain_ratio_required /
                     not_convertible / unknown（见下方换算规则）
to_canonical_factor  到该 kind 基准单位的线性因子（仅 fixed_factor 时有值）
canonical_unit       每 quantity_kind 一个基准单位
aliases              中文表面形式（片、万片、亿元……）
status               active / deprecated
```

换算规则拆成两个判据（机制判据，不按表面形态分级）——**quantity_kind 判断是否同类可比，conversion_mode 判断如何换算**：

```text
fixed_factor             同 kind 固定因子：元/万元/亿元、吨/千克、片/万片
                         （"万 / 亿"是 10^4 / 10^8 因子，不是新单位）
external_rate_required   同 kind 但无固定因子，需外部汇率 / 价格事实：CNY ↔ USD
domain_ratio_required    跨 kind，需 BOM / 配比事实：服务器台 ↔ GPU 片
                         （配比是带来源、带时效的关系事实，作为 relation_claim /
                           derived claim 存，派生时引用，不进 Unit Registry）
not_convertible          跨 kind 且无配比语义，默认不可换算：GPU 片 ↔ 晶圆片
unknown                  识别不出：quantity_kind = unknown，保留 raw，不得猜
```

币种同属 quantity_kind = monetary（ISO 4217 子类），彼此**同类可比但无固定因子**，换算走 external_rate_required——汇率是带时效的外部事实，不是 registry 属性。复合单位（xxx 颗/万米 vs xxx 颗/米）用 numerator / denominator 结构表达，分母的数量级因子同样按 fixed_factor 处理。

### 6.5.3 Time / Period Registry（时间册）

格式规范见 §2.5（date / timestamp / interval 真值 / YYYYQn / YYYYA / YYYYE 表面 label / 相对时间四元组）。另含：

```text
每主体财年日历表  (subject_id, fiscal_year_end, valid_from, valid_to)
                  ——财年 ≠ 自然年的主体（美股 / 港股）必须经此解析
period 条目       period_key + period_type(instant / duration) + interval 真值 + basis
```

### 6.5.4 Metric Registry（指标册）

范式 = XBRL concept 定义：

```text
metric_id / canonical_name + aliases（收入 / 营收 / revenue）
quantity_kind        绑定后 allowed_units 自动推出，归一时校验拒收不匹配单位
period_type          instant（存量）/ duration（流量）
default_scope        每指标的默认口径（如净利润 default = 合并 + 归母）
aggregation_rule     sum / avg / period_end
sign_convention      正负号约定
口径约束文本
```

### 6.5.5 Relation Registry（关系册）

```text
relation_type    supply / sample_delivery / qualification / purchase /
                 compete / substitute / customer_of ……
role_schema      各角色（supplier / customer / material…）的 subject_kind 约束
inverse_of       A 供货 B ⇔ B 采购 A，归一到单一方向存储
stage 全序       sample < trial < qualified < mass_production
                 （阶段推进不判冲突）
conflict_scope   哪组键相同才构成"同一关系"参与冲突检测
```

例："A 公司给康宁提供 100 吨 X 物料"与"康宁获得 A 公司试样 X 物料 20 吨"先归一（supplier=A、customer=康宁、material=X、relation_type、stage、quantity、time），再按 conflict_scope 判断是否同一关系——阶段与数量不同不等于冲突。

### 6.5.6 Scope / 口径 Registry（口径册）

范式 = XBRL Dimensions 的 axis / member / default member：

```text
scope_axis      consolidation（合并/单体）/ attribution（归母/少数）/
                adjustment（原始/扣非）/ tax_inclusion（含税/不含税）/
                recognition（出货/收入确认）/ product_line / region /
                scenario（actual / estimate / guidance）
members[]       每轴成员 + default_member（如 consolidation 默认合并）
applicability   哪些 metric 可挂该轴
```

三条纪律：事实不带显式成员 = default；default 永不改写；**口径未知必须挂显式 unknown 成员，严禁落 default**。

（币种归 Unit Registry；自然年 / 财年归 Time Registry；预测 / 实际是 scenario 轴而非时间格式。）

## 6.6 Registry 生命周期与升版联动

**新增（候选流程）**：

```text
L2 归一遇到未知主体 / 单位 / 指标 / 关系 / 口径
→ 生成 registry_candidate
→ 期间以 raw_text + provisional normalized 值使用
→ 低风险类按规则自动合并；重要对象人批
→ 升版
```

**改 / 删 / 合并**：条目只 deprecate 不删除；主体合并用 status + merged_into 指针，旧引用按指针解析，不悬挂；每次升版产出旧 → 新映射表。

**版本与联动**：

```text
registry 采用日期戳版本（如 registry@2026-07-01）
归一动作是一条 action_log，其 rule_bundle_ref 显式包含 registry 版本
→ 每条证据可回答"按哪版规范归一"
registry 升版
→ 经 L6 失效队列做重要性准入，按受影响 kind / subject 圈定爆炸半径
→ 受影响 evidence_record 重新归一（产生新版本，不原地改写）或标 stale
→ 禁止自动全量重刷
```

## 6.7 L4 不装事实

玩家、客户、供应商、竞争关系、份额、技术路线位置不放 L4：

```text
来源直接说的关系            → L2 relation_claim
系统推导的供应链图 / 暴露度  → L3 派生证据
"该从哪些维度理解这个行业"   → L4 框架条目
"Rubin 是什么、别名有哪些"   → L4 Subject Registry（命名规范，不是动态事实）
```

Registry 可以存"苹果链是一个客户 / 供应链主题""送样 / 认证 / 量产是不同关系阶段"；不能存"A 公司已进入苹果链""某公司份额 20%"。

## 6.8 可训练大脑

系统通过复盘不断变好，落在 L4：

```text
框架条目 / 规则工件 / registry 条目
→ 被 L2 / L3 / L5 引用 → 产生预测快照 → 财报验证
→ 误差归因到条目 → diff 提案 → 历史重放评测 → 人批晋级
```

前向传播 = 框架 + 规则 + 证据 → 假设 → 预测；loss = 预测与财报实际的误差；反向归因定位到来源 / 规则 / 框架 / 派生 / 假设 / 人工覆盖；参数更新 = 修改条目版本。冻结层：系统边界、原始证据、action_log、快照。早期训练是"版本化文本 + 人审 + 历史重放"，不是自动化模型训练。

## 6.9 共享与公司特例

每家公司每年只有 4 个财报验证点，逐家学习样本太少。行业共性进共享模板条目，公司特例进公司附录；行业玩家名单不进框架层，由 L2 relation_claim 和 L3 派生视图动态生成。

# 7. L5：公司预测层

沿 v0.6 主体，输入引用对齐新对象名。

## 7.1 定位

L5 把观测证据、派生证据、规则、框架和人工判断转化为公司未来财务预测。当前聚焦净利润，但内部必须保留利润桥、关键假设、现金质量检查和中间节点，不允许只有一个净利润数字。

## 7.2 输入优先级

```text
L2 evidence_record（原始并列证据）
→ L2 当前采信视图
→ L3 derived claims / canonical facts / 对账后事实
→ L5 假设账本 / 驱动树 / 利润桥
```

L5 优先消费 L3；正式快照必须能沿引用递归追到 L2 / L1：

```text
forecast_node → assumption → derived claim / canonical fact
→ evidence_record → data_asset / source_ref
```

## 7.3 每家公司一个预测对象

内部至少包括：驱动树、利润桥、假设账本、数据绑定与订阅、现金质量检查、情景分支、工作底稿、正式快照、影子快照、财报季复盘记录。

## 7.4 驱动树与利润桥

净利润阶段也必须有完整利润桥：

```text
收入 → 成本 → 毛利 → 费用 → 经营利润 → 利润总额 → 所得税
→ 少数股东损益 → 归母净利润
```

每个节点要知道：来自哪个框架条目、用了哪些 derived claims、能追到哪些 evidence_record、用了哪些假设、是否托底、是否有冲突、是否人工覆盖、下次验证点。

## 7.5 托底规则

允许托底（历史均值、最近趋势、行业均值、管理层指引、一致预期、人工临时假设），但必须显式标记，不能伪装成深度研究。系统要能回答：哪些节点是研究化 driver，哪些只是托底。长期方向是把高影响托底节点替换为研究化 driver。

## 7.6 数据绑定与订阅

预测节点必须注册自己关心什么数据。订阅采用消费者声明形态（借 dbt exposures）：每个节点声明一条订阅记录，取值即 L2 检索键组：

```text
subject_key × metric_key / relation_key × period_key × scope_key × 来源优先级
```

订阅可指向 L3（优先，如"对账后某产品毛利率"）或 L2（必要时，如"某客户订单放量的高 Tier 新证据"）。新鲜度用两级阈值（warn_after / error_after）挂在订阅上。L2 / L3 变化经 change feed 匹配订阅，由 L6 定位受影响假设、节点与快照。

## 7.7 假设账本

- L2 记录来源说了什么；L3 记录系统派生了什么；**假设账本记录模型当前采用什么输入**。

一个假设至少说明：公司、业务 / 产品 / 客户 / 区域、指标、期间、假设值、引用的 L3 / L2 对象、口径契约、框架条目、是否人工覆盖（人工覆盖经 change_candidate 人批落地，§4.8）、置信度、冲突状态、下次验证点、对净利润敏感度。

## 7.8 现金质量检查

即使正式输出只是净利润，也必须保留现金质量检查（应收、存货、合同负债、经营现金流、资本开支、折旧摊销、减值、费用资本化、非经常性损益）。它不一定改点值，但必须影响置信度、污染标记、待办优先级和复盘归因。

## 7.9 情景分支

只用于高重要性 contested driver。必须限制分支数量、变量数量、持续时间、是否影响正式预测、是否需人工裁决。主预测使用当前采信假设；情景分支用于预测区间、敏感性和待办排序。

## 7.10 正式快照与影子快照

- 影子快照：系统自动生成，用于观察、比较、提前发现变化；
- 正式快照：经发布闸门进入正式输出，pin 清单见 §12.4，发布后不可回改。

# 8. L6：调度脊柱

## 8.1 结构

```text
感知 → 触发 → 准入 → 行动 → 队列
```

## 8.2 感知：最小血缘边

第一阶段不建完整知识图谱，只锁定最小血缘边（其余依赖由 action_log 保留）：

```text
evidence_request → data_asset（获取 / 登记）
data_asset → evidence_record（producer_action_ref + primary / supporting refs）
evidence_record → current_evidence_view
current_evidence_view / evidence_record → derived_claim / canonical_fact
contract / rule_artifact / framework_entry / registry_entry → derived_claim / canonical_fact
derived_claim / canonical_fact / evidence_record → assumption
assumption → forecast_node
forecast_node → snapshot
research_topic → evidence_requests / 产出的证据、派生、假设、框架与规则 diff
```

它要能回答六个工程问题：某 data_asset 变化影响哪些证据？某证据 / 采信视图变化影响哪些派生？契约 / 框架 / registry 升版影响哪些派生和公式？某派生变化影响哪些假设？某假设变化影响哪些节点和快照？某 action 作废影响哪些产物？

## 8.3 触发

- **事件触发**：消费 L1 / L2 / L3 change feed（§2.8）——新资产、证据状态变化、采信视图变化、派生失效、人工裁决、契约 / 框架 / registry 升版、财报披露。只有 materialized 事件触发失效；observed 事件只更新新鲜度。
- **定时触发**：冷存扫描、弱信号累计、假设过期、派生过期、模型陈旧、临近财报、失败重试、影子快照定期重算、订阅新鲜度检查。
- **人工触发**：一等触发源（新增个股、开课题、强制重算、手动裁决），可直通但仍要经准入记录。

## 8.4 准入

准入是触发与行动之间的策略层：控成本、控噪声、控人的注意力、保证可审计。候选行动映射到：立即执行 / 低优先入队 / 仅记录 / 转人工 / 丢弃。

重要性特征沿 v0.6（来源 Tier、追溯等级、影响公司数、预测期间、与假设偏离度、净利润敏感度、临近财报、高置信冲突、是否解决已有待办、是否触发失效、是否改变快照候选）。LLM 可对定性材料打辅助分，但不能单独决定准入。

**成本纪律**：≥500 家跟踪池不默认全量过 LLM。按 material_type / payload_kind / semantic_key / 公司优先级 / 临近财报程度分批调度抽取，低优先资产只登记不抽取，等待订阅或课题命中后再证据化。

## 8.5 行动库

原子行动：获取资料、登记 data_asset、载体规范化、证据抽取、校验、对账、冲突检测、证据状态更新、采信视图更新、registry 候选处理、派生生成 / 重算、标 stale、假设更新、节点重算、快照生成、待办生成、丢弃审计。

复合行动：入库流程、变更传播、派生重算、研究课题、个股初始化、财报复盘、契约升版、registry 升版、框架重放评测、来源可信度更新。

每个行动声明：输入、输出、加载的规则工件、引用的框架条目、执行者（code / llm / human / hybrid）、action_log 记录、失败处理。

## 8.6 evidence_request

evidence_request 是 L6 生成的**控制单据（command）**，不是数据信封。用于把"缺资料"变成受控取证：

```text
request_source     L5 假设缺口 / L3 派生缺口 / L2 冲突 / 人工问题 / 财报复盘
target             目标公司 / 行业 / 主题 + 目标变量 / driver / forecast_node
gap_kind           值缺口 / 结构缺口 / 冲突缺口 / registry 缺口
information_needs  需要的信息类型（数值 / 关系 / 事件 / 观点 / 口径 / 历史数据）
source_policy      允许 / 禁止来源，优先 Tier，最低追溯等级
return_contract    必须形成 data_asset；重要证据必须有 locator / 原文锚
budget             检索轮次上限、工具调用上限、人工待办上限、费用上限
close_condition    结案条件
approval           是否需人工审批
```

状态机：`open / partial / satisfied / closed / expired`。取回的 data_asset / evidence_record 以 request_ref 回链；查空以 null_observation 结案（§3.9）。

例：

```text
目标：某公司 2027E Rubin 相关收入假设
缺口：Rubin 服务器出货量、公司供应关系、单机价值量、送样状态
来源优先级：公告 / 投关 / 卖方纪要 / Wind / web
预算：≤3 轮检索、≤10 次工具调用
返回要求：全部登记 data_asset；L2 只接受有 locator 的证据
```

## 8.7 失效队列

```text
定位受影响对象（血缘 + 订阅）→ 判断重要性 → 标记失效 → 入队
→ 自动重算 / 影子重算 / 人工确认 / 仅观察 → 生成新版本或待办
```

典型链路：新资产 → 新证据 → 采信视图变化 → 相关派生 stale → 重算 → 假设 stale → 影子预测 → 必要时待办或快照候选。规则 / 契约 / registry 升版走同构链路，重要性准入限定爆炸半径。失效不是错误，是系统正常运行状态。

# 9. 研究课题：拉式回路

沿 v0.6 主体；课题与 evidence_request 的关系收口如下。

## 9.1 定义与关系

课题是绑定目标变量的**复合行动**：

```text
课题 = 立题（值课题 / 结构课题）+ 一组 evidence_request + 证据消化
     + 结构 / 取值更新 + 重算 + 结案
```

- 课题可下发多个 evidence_request；request 是原子取证契约，也可不依附课题（由冲突 / 缺口直接触发）；
- 预算规范归口到 evidence_request（§8.6）；课题级预算约束子课题深度、数量、agent 执行次数、待办数量、结案时间；
- 禁止无边界课题（"研究一下 AI 光模块"不合法；"为更新中际旭创 2026E 毛利率假设，研究 800G / 1.6T 价格、良率、客户结构、产能释放"合法）。

## 9.2 课题类型与执行顺序

- **值课题**：驱动树结构已在，只刷新取值 / 采信。证据先行。
- **结构课题**：要新建 / 展开 / 修改驱动树结构或拆解口径。结构先行——先查 / 定 L4 框架模板与口径（新共享结构人批），再改 L5 驱动树骨架并登记数据绑定，然后取数。

两类课题的资料一律走 L1 → L2 → L3，不得绕过证据层改预测。

## 9.3 课题来源与新增个股

课题来源：人工提出、新增个股、关键假设缺失、高重要性冲突、含 contested 输入的派生、弱信号累计、财报复盘发现误差、框架缺失。

新增个股是最大的标准课题，目标是"能出影子预测的最小公司模型"：主营与产品拆分、收入 / 成本 / 毛利结构、上下游与竞争、产能与技术路线、历史财务重构、现金质量、管理层动机、争议点、最小驱动树、未解决待办。未研究透的部分允许托底并显式标记。

# 10. 标准流程

## 10.1 自维护文档型入库

```text
raw PDF / Word / 图片 / 人工文本
→ L1 adapter：登记 source_ref、保存原文 + 哈希、载体规范化
→ data_asset(document_unit) + change feed
→ L2 准入 → 组窗（可多 asset 联合）→ 高价值选择性抽取
→ evidence_record（observed_claim / relation_claim；允许空列表）
→ registry 归一 → 去重 → 披露锚对账 → 冲突检测 → 置信度 / 重要性
→ 分流：入账 / 采信视图 / cold / 待办 / 丢弃审计
→ L6 判断是否触发 L3 / L5
```

## 10.2 标准结构化数据

```text
L6 或人工发起数据需求
→ L1 provider adapter → data_asset(dataset_snapshot)
→ L2 numeric_observation（字段校验、口径标注、registry 归一；不走 LLM 抽取）
→ L3 canonical facts → 同比 / 环比 / 扣非 / 利润桥节点等 derived facts
→ L5 消费
```

## 10.3 轻载外部来源

```text
evidence_request / 人工检索 / agent 调用
→ L1 data_asset(tool_result)
→ L2 检查 locator / snippet / citation
→ 可定位且重要：observed_claim / relation_claim
→ 来源弱但有线索：status = cold
→ 重要但追溯不足：人机待办或补证据 request
→ 无定位无价值：丢弃 + action_log 审计
```

## 10.4 人工上传

```text
上传（人显式声明 material_type）
→ L1 upload adapter → data_asset（document_unit / dataset_snapshot / artifact_unit）
→ L2 按内容性质证据化；修改建议 → change_candidate(target_layer)
→ 人批 → 对应层机制承接 → action_log 留痕
```

## 10.5 混合联合抽取

```text
evidence_request 或人工动作
→ L1 / catalog 按检索键召回多个 data_asset
→ L2 action 接收多 asset_refs（遵守 §4.9 纪律）
→ 联合抽取 / 对账 / 归一
→ 多条 evidence_record，各指 primary + supporting refs
```

## 10.6 观测证据变更传播

```text
证据新增 / 状态变化 / 人工裁决 / 采信视图变化
→ L2 change feed → L6 查订阅与血缘 → 定位受影响 L3 对象
→ 准入 → 标 stale / 入重算队列 → L3 重算或情景派生 → 判断是否影响 L5
```

## 10.7 派生证据重算

```text
derived claim 失效或新建需求
→ 加载 L2 当前采信视图（必要时 contested）+ L4 契约 / 规则 / registry
→ 执行派生（action_log 记录）→ 新版本 derived claim
→ 更新下游引用 → L6 判断是否触发 L5
```

## 10.8 拉式取证

见 §8.6；先查 L2 账本、冷存与历史查空记录，再查 L3 既有派生，确认缺口后才主动取证。

## 10.9 新增个股初始化

```text
人工指定公司 → 初始化课题 → 最小公司档案 + 初始驱动树
→ 接入公告 / 历史财报（L1）→ L2 证据基础 → L3 历史重构与利润桥
→ 核心假设 + 托底标记 → 影子预测 → 待办清单
```

## 10.10 财报季复盘

```text
财报入库 → 作为硬锚进 L2
→ L3 按快照当时的口径契约与 registry 版本重构实际值
→ 对比正式 / 影子快照 → 沿利润桥逐节点定位偏离
→ 误差归因（§14.2 分类）
→ 回写来源可信度 / 规则 / 框架 / registry / 派生逻辑 / 假设 / 待办
→ 必要时提出框架 / 契约 / 规则 diff
```

## 10.11 口径契约升版

```text
发现口径问题 → 契约 diff → 人工审核 → 小范围历史重算验证
→ 升版 → 受影响 derived claims 与预测公式失效（走失效队列）
→ 生成新快照或重述复盘（不改历史快照）
```

## 10.12 Registry 升版

```text
registry_candidate 累积 / 人工修订
→ 低风险自动合并或人批 → 日期戳升版 + 旧→新映射
→ L6 失效队列按 kind / subject 圈定爆炸半径
→ 受影响证据重新归一（新版本，不原地改写）或标 stale
→ 相关派生与假设按 §10.6 传播
```

## 10.13 框架 / 规则条目演进

```text
财报误差 / 课题发现 / 人工判断（或 change_candidate 批准）
→ 框架条目 / 规则工件 diff → as-of 历史重放评测 → 人批 → 升版
→ 受影响派生逻辑、公司模型和假设重检
```

# 12. 执行日志、版本与快照

## 12.1 action_log：统一执行账本

action_log 是全系统唯一执行账本概念（v0.6 的 M-LOG 为曾用名；L1 的 processing_run 是它在解析场景的特化实现）。最小字段集：

```text
action_id            稳定 ID（act:// URI）
action_type          载体规范化 / 抽取 / 校验 / 对账 / 派生 / 归一 / 裁决 / 重算 ……
executor_type        code / llm / human / hybrid
model_ref            provider + model name + version / snapshot（纯代码动作为 null）
code_ref             代码 / 规则执行体版本（纯代码动作必填）
rule_bundle_ref      prompt / 解析配置 / 抽取 spec / 校验器 / registry 版本的打包引用
input_asset_refs     直接输入（data_asset / evidence_record / 视图版本）
output_refs          产出（evidence_record / derived claim / 快照 / 待办）
trigger_ref          由什么触发（change feed 事件 / request / 人工指令 / 定时）
started_at / finished_at / status / error_summary
discard_notes        丢弃审计（哪些输入为何未产出证据）
```

## 12.2 轻量追溯规范

按 §2.6 执行：记录只带 producer_action_ref；prompt_version / schema_version / temperature 不作为记录级默认字段；rule_bundle 粒度须能区分 prompt / parser / 校验器 / registry 变更。追溯目标是**可归因**：出错时能回答"来源变了、模型变了、还是规则变了"。

## 12.3 不可变与可变

**不可变（append-only + 版本化——一跳引用成立的前提）**：

- 自维护 raw 原文与文件哈希；
- source_ref / source_access 历史记录（含查空）；
- data_asset 各版本快照（新版本取代，superseded_by 指向，不覆盖）；
- evidence_record 各版本与状态变迁历史；
- derived claim / canonical fact 历史版本；
- action_log；
- registry 各日期戳版本与旧→新映射；
- 发布后的预测快照；财报复盘原始记录。

**可变视图（变化必须能追到历史版本）**：

- L2 当前采信视图；L3 当前有效派生视图；
- 当前假设、当前预测模型实例、当前待办状态；
- 框架 / 规则 / 契约 / registry 的"当前版"指针。

## 12.4 快照 pin 清单

正式快照必须 pin **版本号**（不仅是对象 ID）：

```text
L2 当前采信视图版本
L3 派生证据 / canonical facts 版本集合
口径契约版本
框架条目版本集合
规则工件版本集合
registry 版本（日期戳）
外部 provider as-of（如 Wind 取数时点）
producer action_log 引用集合
模型版本 / 假设版本
利润桥、中间节点、现金质量检查、情景分支、敏感变量、最脆弱假设
人工覆盖记录、发布理由、未解决冲突
```

## 12.5 快照不可回改

发现旧预测错了：生成新快照、或生成重述复盘、或标记旧快照受某后验信息影响；不覆盖原始发布记录。

# 13. 冲突、置信度与情景管理

沿 v0.6 收敛。

**冲突类型**：数值、时间、口径、主体、来源、事实与观点混用、估算与披露锚冲突、观测与派生冲突、预测与实际披露冲突、框架解释冲突、人机判断冲突。关系型冲突先经 Relation Registry 归一（§4.14）。

**置信度来源**（不能只由 LLM 打分）：来源 Tier、追溯等级、与硬锚一致性、多源印证、来源历史准确率、信息直接性、期间与口径明确性、抽取校验结果、是否依赖 contested 输入、是否被财报验证、是否有人裁决。

**冲突处理**：降置信、转 contested、生成待办、生成情景分支、暂时采信硬锚、等待新资料、请求人工裁决、阻塞正式快照（不阻塞影子快照）。

**情景分支**只服务预测区间和不确定性表达；系统仍须有当前主假设。

# 14. 财报季复盘与系统学习

财报是系统的验证集。复盘不是写点评，而是训练和纠错过程。

## 14.1 逐节点复盘

沿利润桥（§7.4 节点链）逐节点定位偏离，比率形态（毛利率 / 费用率 / 税率）同步核对；现金质量同步核对（利润是否转化为现金、应收 / 存货 / 合同负债 / 资本开支是否异常）。

## 14.2 误差归因分类

来源错误、抽取错误、归一错误（registry）、口径错误、对账失败、L2 采信错误、L3 派生逻辑错误、假设方向 / 节奏错误、模型结构错误、框架条目错误、规则工件错误、人工覆盖错误、突发事件、披露变化、蒙对但逻辑错、蒙错但方向合理。归因到"抽取 / 归一 / 规则"级别依赖 action_log 的 model_ref + rule_bundle_ref（§12.2）。

## 14.3 回写

来源可信度、抽取规则、对账规则、派生规则、口径契约、registry 条目、框架条目、驱动树、假设账本、课题模板、待办排序、快照发布规则。复盘不回写，系统不会变好。

复盘必须 as-of：按快照当时的契约、registry 与证据视图重构，不能用后验信息评价旧预测。

# 15. 当前阶段工程取舍

1. **L1 先轻后重，但"轻"只指存储不指职责**：不强求全量 raw data lake；披露 PDF 与人工上传件自维护，其他来源保留访问与追溯记录。raw 处理职责全部在 L1，不因"轻"而下放 L2。
2. **先把 L2 / L3 / L5 做硬**：证据能入账、能追溯、能冲突、能裁决；派生能说明输入 / 规则 / as-of、能失效重算；假设能影响预测；预测能快照；快照能复盘。
3. **Registry 分期**（§6.5）：先 Subject / Unit / Time + 最小 Metric；Relation / Scope 先只强制"未知必须显式标记"。
4. **LLM 成本分批**（§8.4）：≥500 家跟踪池不默认全量抽取。
5. **数据目录第一天建**：检索键、URI、public views 随首个服务落地（disclosure_anchor 已验证）；change feed 端点与两事件语义随 disclosure_anchor 分阶段落地（§3.10）；L2 复用同一蓝图。
6. **baseline claims 暂不启用**：一致预期后续作为对照模块，经 L2 预测型证据 + L3 baseline 派生视图进入，不直接进 L5 主假设。
7. **不依赖实时在线**：定时批处理、人工拉起、session 式 harness、局部重算、影子快照常算、正式快照人工过闸。
8. **harness 无关**：控制逻辑沉淀在框架条目、规则工件、口径契约、action_log、快照约定、待办机制，不绑定 Claude / Codex / MCP / 某个搜索工具。

# 16. 硬边界

1. 系统唯一正式产出是公司未来财务预测；当前阶段是契约口径下净利润预测。
2. 系统不做估值、选股、买卖建议、便宜判断、组合构建。
3. L1 是来源资产层，不是全量 raw data lake；L1 的统一出口是 data_asset 信封。
4. document_unit 不是 L1 的唯一出口，只是 asset_kind 之一；其稳定 ID 即 asset_id（unit_kind、document_unit_id 为已收敛的曾用名）。
5. source_ref 是 data_asset 的 provenance 引用，可由视图或 endpoint 派生，不要求独立对象存储。
6. 所有来源一个信封：新需求先加规范和扩展字段，默认不新增顶层对象（例外须满足独立生命周期 / 状态机 / 权限边界并经协议升版）；L1 / L2 各一个信封，不强并为一。
7. raw 止于 L1：L2 不得处理 raw PDF / OCR / image / audio / Excel，收到即返回 L1_PROCESSING_REQUIRED 或回流。
8. 公告 / 财报 PDF 是自维护硬锚：原文、哈希、document_unit、producer_action_ref、结构上下文尽量保存。
9. L1 只做载体规范化与结构上下文，不做投资语义判断；不得因"像套话"让实质信息对下游永久不可见。
10. company_ref / report_period / material_type 必须从 document 继承到 unit 级可检索上下文（契约层承诺，存储可范式化）。
11. 人工上传统一走 L1 upload adapter，material_type 由人显式声明，L1 不做语义推断。
12. 查空记录在 L1 provenance 层；仅当回应 evidence_request 时才生成 L2 null_observation，不在两层重复建对象。
13. L2 是观测证据层：吸收精选高价值信息、registry 归一、维护采信视图 / 冲突 / 冷存 / 裁决 / as-of 账本。
14. 提纯通过选择性证据化实现：不修改、不删除 L1 资产；每条证据必须指回原文定位（primary_asset_ref + exact_span）。
15. claim 抽取是高价值选择性抽取，允许 evidence_records = []；抽取为空与查询未得是两回事。
16. L2 可联合多个 data_asset 抽取，但不新增 claim packet / evidence packet；tier / trace 按 primary asset 判定；跨主体联合须显式圈定。
17. 标准结构化数据跳过 LLM 抽取，但不得绕过 L2 准入；numeric_observation 不冗余拷贝 L1 provenance，一跳继承。
18. tool / web / MCP / Claude / Codex 返回先是 data_asset(tool_result)，不是证据；agent 总结不是来源。
19. 对 L3 / L4 / L5 的修改候选一律经 change_candidate 走审批留痕：低风险类可按规则自动通过（§4.8），重大变更强制人批，不得直接落层；change_candidate 不进采信视图。
20. record_kind 判别记录形态：证据四类共用 record_status 状态机，change_candidate 是共享信封的治理记录，不属于证据账本；冷存是状态（status = cold）不是 kind；丢弃审计记在 action_log。
21. raw + normalized 双轨必须保留；normalized 不新增原文没有的事实；口径未知必须显式 unknown，严禁落 default。
22. 来源直接支持的关系放 L2；系统推导的暴露度 / 供应链图放 L3；理解框架与命名规范放 L4。
23. L3 可从 numeric_observation 生成 canonical facts（derived claim 子类，同一状态机），不必都先变自然语言 claim。
24. L3 不得绕过 L1 登记与 L2 准入直接调用外部来源生成派生事实。
25. 每条模型参与的 L2 / L3 产物必须有 producer_action_ref；action_log 记 model_ref + rule_bundle_ref + 输入输出引用。
26. 正常消费一跳，审计递归全链；一跳引用的前提是被引对象 append-only 且版本化。
27. Registry 是 L4 规范库，支撑 raw → normalized，不装动态事实；条目只 deprecate 不删除，合并用 merged_into 指针。
28. Registry 升版经 L6 失效队列限定爆炸半径；重新归一产生新版本，不原地改写；禁止自动全量重刷。
29. 单位换算由 quantity_kind（是否同类可比）+ conversion_mode（如何换算）两个判据决定；跨 kind 配比与汇率是带来源、带时效的外部事实，不进 Unit Registry。
30. 时间三轴（event_time / published_at / observed_at）不增第四轴；as-of 沿 published_at 截断防前视偏差。
31. 拉式回路经 evidence_request 控制：绑定目标、预算与结案条件，禁止无边界搜索；agent 不得绕过 L1 / L2 改预测。
32. 每层对下游暴露同构 change feed；observed 与 materialized 两种事件，失效只由 materialized 触发。
33. 高重要性冲突不能吞掉：必须进入 contested、情景、待办、阻塞或人工裁决。
34. 情景分支只给高重要性 contested driver，数量受限。
35. 能确定性完成的不交给 LLM；LLM 评分只能作为准入特征之一；生产与校验隔离。
36. 净利润阶段必须保留完整利润桥与现金质量检查。
37. 历史重构、未来预测、财报复盘必须引用同一版口径契约。
38. 正式快照必须 pin 版本号（含 registry 版本与 provider as-of），发布后不可回改。
39. 账本、日志和快照必须支持 as-of 复盘；复盘必须逐节点归因并回写上游。
40. 对外读契约以 *_v1 视图 / endpoint 版本化暴露；跨服务只经 public 契约消费，不回读私有表。
41. 课题是复合行动不是新层，必须绑定目标变量；课题资料必须走 L1 / L2 / L3。
42. demo 期允许定时 / 人工拉起的批式运行；系统控制逻辑必须 harness 无关。

# 18. 一句话收口

这个系统不是"更强的搜索助手"，而是一个围绕财务预测长期运转的证据、规则、假设和复盘机器。

v0.6 把证据体系拆清楚：L2 管来源直接说了什么，L3 管系统构造出了什么。

v0.7 把入口协议收成一套范式：

```text
L1：所有来源都变成 data_asset 信封，raw 在 L1 截止；
L2：只吸收 data_asset，做高价值证据化、registry 归一、对账、冲突和采信；
L3：基于 L2 与 L4 构造公司 / 行业 / 主题 / 宏观的派生事实；
L4：提供框架、规则、口径契约和规范库；
L5：只消费可追溯的派生证据与假设，不直接相信资料或 agent 总结；
L6：用 change feed（推）和 evidence_request（拉）把全链路串起来；
全系统：一个信封 + kind 判别 + 规范登记，一跳引用 + 递归审计，
        追溯轻量、快照 pin 版本、as-of 可复盘。
```

来源形态可以复杂，入口契约必须统一；claim 抽取必须克制，结构化数据不必文本化；外部工具返回不能直接采信；所有进入预测链的东西都必须能追溯、能校验、能冲突、能失效、能复盘。
