# AI Agent 投研预测引擎顶层框架协议 v0.7 二次修订稿

> 用途：替换上一版《v0.7 升级修改稿》。  
> 目标：在 v0.6 已经完成 L2 / L3 拆分的基础上，重新收口 L1 / L2 的输入契约、证据准入、数据目录、规范库和拉式取证机制。  
> 写法：仍然是顶层架构协议，不写 SQL、DDL、API 细节、目录结构。

---

## 0. v0.7 二次修订的核心判断

v0.6 的 L2 / L3 拆分保留：

```text
L2 = 观测证据层：来源直接说了什么、哪些采信、哪些冲突、能否追溯。
L3 = 派生证据层：系统基于 L2 证据和 L4 规则构造出了什么。
```

但上一版 v0.7 的问题是：为了兼容 PDF、API、web、MCP、人工工件、结构化数据，新增了过多对象名，导致 `source_ref + typed payload`、`structured observation`、`tool_observation`、`artifact_ref` 等概念互相重叠。

二次修订后，核心改为：

```text
L1 统一产物：data_asset 信封
L2 统一产物：evidence_record 证据记录
L4 支撑：registry / normalization rules / extraction rules
L6 串联：change feed + evidence_request + action log
```

其中：

- `source_ref` 保留，但不再作为“L1 统一出口”的名称；它是 `data_asset` 信封里的来源 / 访问 / 原文定位引用，可以由视图或 endpoint 派生。
- 不再说 `typed payload`，改成“统一信封 + 判别字段 + payload”。
- 不再写 A 类 / B 类清洗，改成 L1 的“载体规范化”和 L2 的“证据化 / 语义归一”。
- L2 不处理 raw PDF、raw OCR、raw audio、raw image。L2 只接收 L1 已登记、已结构化、可追溯的数据资产。
- L2 可以在一次动作中联合多个 L1 数据资产抽取证据，但不新增长期 `claim packet / evidence packet` 对象。
- 结构化数据可以跳过 LLM claim 抽取，但不能绕过 L2 的来源、口径、准入和追溯。
- 模型追溯只保留必要信息：`model_ref` 与 `rule_bundle_ref / prompt_rule_ref`，挂在 action log / processing run 上，不在每条 claim 上堆字段。

## 1. 从外部项目借鉴的原则

这类系统没有完全同型项目，但几个成熟协议和工程项目有可借鉴的设计取向。

### 1.1 MCP 的启发：资源引用，而不是到处内联

MCP 的资源机制强调：服务器暴露资源，资源由 URI 唯一标识，客户端按 URI 取上下文。对本系统的启发是：

```text
source_ref 不应该被理解成一大坨来源对象。
它更像可解析的 provenance resource reference。
```

在 `disclosure_anchor` 里，`source_ref` 可以是：

```text
source_access / document / document_unit / processing_run
→ source_refs_v1 视图
→ GET /v1/units/{id}/source-ref
```

也就是说，`source_ref` 可以是派生视图，而不是独立主表。

### 1.2 AG-UI 的启发：统一信封 + type 判别 + rawEvent

AG-UI 的 typed event 思路值得借鉴：每个事件有稳定基础字段，具体内容放在不同 event type 的 payload 中，同时可保留 rawEvent。

对本系统的启发是：

```text
不要为每类来源发明一套完全不同对象。
统一信封足够稳定，payload 根据 kind 扩展。
```

所以 L1 不写成：

```text
source_ref + typed payload
```

而写成：

```text
data_asset = identity + scope + time + provenance + quality + payload
asset_kind / payload_kind 只是判别字段
```

### 1.3 OpenLineage 的启发：最小核心 + 可扩展元数据

OpenLineage 的核心是 run / job / dataset，再通过 facets 扩展元数据。对本系统的启发是：

```text
不要把所有版本、模型、规则、prompt、schema 都塞进每条 claim。
把执行过程放在 action_log / processing_run；claim 只引用 producer。
```

因此 v0.7 不要求每条 L2 claim 都重复记录一堆运行字段。只需：

```text
producer_ref / action_log_id
→ action_log 记录 model_ref、rule_bundle_ref、input_asset_refs、output_refs、执行时间
```

### 1.4 Dagster external assets 的启发：外部资产可以登记，不必都自维护

很多数据系统不会真正拥有所有外部数据。更合理的是把外部系统的数据建模成 external asset，并记录它何时更新、如何观察、如何被下游使用。

对本系统的启发是：

```text
Wind / iFinD / web / MCP / 第三方 API 可以是 L1 data_asset。
它们不必都落成本地 raw 文件。
但只要进入预测链，就必须有 provenance、as-of、provider、query、版本或定位信息。
```

### 1.5 Unstructured / LlamaIndex 的启发：文档结构在前，抽取在后

文档解析类项目通常先把 PDF、HTML、Word、图片等转成带结构的 document elements，再在这些元素 / chunks 上做实体、关系、claim 或图谱抽取。

对本系统的启发是：

```text
PDF / OCR / 表格结构 / Q&A 绑定属于 L1。
claim 抽取、主体识别、语义归一属于 L2。
```

L2 不能退回去做 PDF parsing。否则 L2 会变成全系统最重、最混乱的 raw data 处理层。

## 2. 术语替换

v0.7 二次修订建议做如下替换。

| 原表达 | 新表达 | 说明 |
|---|---|---|
| `source_ref + typed payload` | `data_asset 信封` | `source_ref` 是信封内的 provenance 引用，不是统一出口名 |
| `document_payload / dataset_payload / tool_observation_payload` | `asset_kind + payload_kind` | 用少数判别字段表达差异，不拆多套对象 |
| A 类清洗 | L1 载体规范化 | 只做稳定、可复核、不含投资语义的结构处理 |
| B 类语义清洗 | 删除 | 语义归一发生在 L2 claim / evidence 抽取过程中，不生成独立“清洗后文本资产” |
| structured observation | `evidence_record(record_kind=numeric_observation)` | 结构化数据进入 L2 后的一种证据记录，不单列体系 |
| tool_observation | `data_asset(asset_kind=tool_result)` | L1 捕获的工具结果，不直接等于证据 |
| claim packet / evidence packet | 不引入 | 通过字段、索引、source、section、subject、metric、action_log 自然聚合 |
| extraction_run / derivation_run 大对象 | action_log / processing_run 轻量引用 | 只记录 model_ref、rule_bundle_ref、输入输出引用和时间 |

# 3. L1：来源资产层的新契约

## 3.1 L1 的定位

L1 不是“文档层”，也不是“大而全 raw data lake”。

L1 是所有外部输入进入系统前的**来源资产层**，负责把不同来源转成可被下游引用、可追溯、可增量感知的 `data_asset`。

L1 回答：

```text
这条资料 / 数据 / 工具结果来自哪里？
什么时候取得？
用什么 adapter / provider / query / parser 取得？
它现在是什么可消费形态？
它的追溯等级、质量状态和下游契约是什么？
```

L1 不回答：

```text
这是不是高价值投资信息？
它支持哪个预测假设？
它和历史证据是否冲突？
它应不应该被采信？
```

这些属于 L2 及之后。

## 3.2 L1 统一信封：data_asset

L1 的统一出口不是 `document_unit`，也不是 `source_ref + typed payload`，而是 `data_asset` 信封。

架构层只要求它有六组信息，不规定具体 schema。

```text
A. identity
   asset_id
   asset_kind
   payload_kind
   contract_version
   content_hash / snapshot_hash
   quality_status

B. scope
   subject_candidates
   company_refs / security_refs
   industry_refs
   theme_refs
   region_refs
   title / heading_path / semantic_key

C. time
   observed_at
   source_publish_time
   event_time
   report_period
   as_of_time

D. provenance
   source_ref
   provider / adapter / tool
   query_params / access_params
   source_tier
   trace_level
   locator
   raw_asset_ref

E. payload
   text / table / qa / recordset / search_result / calculation_table / metadata
   payload_json

F. change
   processing_run_ref
   parser_ref
   change_seq
   is_active
```

其中：

- `asset_kind` 是少量稳定判别字段；
- `payload_kind` 表达具体内容形态；
- `payload_json` 承接变化快的内容；
- 公司、时间、主题、质量、hash、period 这类查询键应列化 / 索引化；
- `source_ref` 是 provenance 引用，可以来自视图，也可以由 endpoint 派生。

这与 `disclosure_anchor` 的设计方向一致：稳定查询键列化，复杂内容放 payload；统一信封，判别式字段，契约版本化，public view 暴露给未来 L2。

## 3.3 asset_kind 建议保持少而稳

不要一开始把来源类型拆得太细。建议先用以下几类：

| asset_kind | 说明 | 例子 |
|---|---|---|
| `document_unit` | 自维护文档 / 人工文本 / OCR 后文本的最小可追溯单元 | 公告段落、表格、Q&A、会议纪要片段 |
| `dataset_snapshot` | 标准结构化查询结果或数据快照 | Wind 三大表、行业数据库、Tushare 查询结果 |
| `tool_result` | web / MCP / Codex / Claude search / 插件返回的轻载外部结果 | 搜索结果、网页片段、MCP tool JSON |
| `artifact_unit` | 人工上传的计算工件、模型表、勾稽表被 L1 结构化后的单元 | Excel 区块、手工利润桥、调研问题清单 |
| `null_result` | 查空 / 无结果 / 未命中记录 | 某次搜索没有找到某产品毛利率 |

注意：人工上传不是单独 `asset_kind`。人工上传只是来源入口。上传后按内容形态变成 `document_unit`、`dataset_snapshot` 或 `artifact_unit`。

## 3.4 L1 对 raw data 的边界

L1 必须处理 raw data，L2 不处理 raw data。

```text
raw PDF / raw image / raw OCR / raw audio / raw PPT / raw Excel
→ L1 adapter / upload service / parser service
→ data_asset
→ L2
```

如果 L2 API 收到 raw PDF、未 OCR 图片、未解析音频、未结构化 Excel，应返回：

```text
L1_PROCESSING_REQUIRED
```

或者由 L6 生成回流任务，把资料送回对应 L1 adapter。L2 不应自行解析文件。

这条边界必须硬写。否则 L2 会承担 PDF parser、OCR、表格识别、web fetch、结构化数据 adapter、claim 抽取、冲突检测全部职责，后续会不可维护。

## 3.5 L1 载体规范化，不再称 A 类清洗

v0.7 删除 A / B 类清洗叫法。

L1 做的是：

> **载体规范化 / carrier normalization**

它只处理结构和载体问题：

- PDF / Word / PPT / 图片 / OCR / 文本解析；
- 段落、标题、表格、Q&A、列表、注释切分；
- 表格标题、表头、行头、单位、脚注保留；
- Q&A 问题和回答绑定；
- heading_path / order_index / semantic_key / content_hash 生成；
- 页眉页脚、页码、水印、控制字符等稳定噪声处理；
- raw 文件 / raw payload 保真留存或登记；
- parser_ref / contract_version / quality_status 记录。

L1 不做：

- claim 抽取；
- 高价值判断；
- 预测相关性判断；
- 投资主题归因；
- 证据采信；
- 冲突仲裁。

安全红线：L1 不得因“像套话”删除可能含有实质风险、业绩变化、会计政策、重大事项的信息。可以标记质量或噪声，但不得让下游不可见。

## 3.6 document 级上下文和 unit 级上下文合并为 scope / context

上一版把 document 级上下文和 document_unit 级上下文分开，容易让人看不懂。v0.7 改成统一的 `scope / context`。

每个 `data_asset` 都应尽量带上可索引上下文：

```text
company_refs / security_refs
industry_refs
theme_refs
primary_subject_candidates
source_type
filing_type / material_type
report_period / event_time / publish_time / upload_time
title
heading_path
unit_kind / payload_kind
semantic_key
quality_status
```

对 `document_unit` 来说，`company_code`、`security_code`、`report_period`、`filing_type` 不是只属于 document，它们应从 document 继承到 unit 的可检索上下文。否则未来 L2 / L3 很难按公司、期间、资料类型、主题快速召回。

## 3.7 disclosure_anchor 的定位

`disclosure_anchor` 是 L1 中“上市公司公告 / 财报 PDF”路径的落地实现，不等于整个 L1。

它现有方向是合理的，可作为 L1 其他 adapter 的模板：

```text
PostgreSQL 主库 + 文件系统
三 schema：core / public / ops
public views 作为跨服务读契约
processing_run 管 active / history
source_access 作为访问登记落点
source_refs_v1 作为 source_ref 派生视图
outbox_event 作为 change feed
unit_kind + payload 作为统一信封
稳定查询键列化，变化内容放 jsonb payload
```

v0.7 只建议补强一点：`document_unit` 的 public view 需要保留足够的 scope keys，例如：

```text
company_ref
security_ref
filing_type
report_period
announcement_date
unit_kind
heading_path
semantic_key
quality_status
content_hash
contract_version
processing_run_ref
source_ref
```

这样未来 L2 可以直接通过 API / public view / MCP resource 获取资产，而不是回到数据库私有表。

# 4. L2：证据入口与观测证据层

## 4.1 L2 的重新定位

L2 是系统的消化系统和免疫系统。

它的职责不是“处理 raw data”，而是：

```text
吸收 L1 交付的精选可用数据资产；
判断哪些信息值得进入证据循环；
把高价值文本 / 表格 / 工具结果 / 结构化数据转成观测证据；
做主体、时间、单位、指标、关系、口径的语义归一；
做去重、对账、冲突、置信度、冷存、待办、丢弃；
维护 as-of 可复盘的观测证据账本和当前采信视图。
```

L2 不直接处理：

```text
raw PDF
raw image
raw OCR
raw audio
raw web page fetching
第三方 API 原始鉴权 / 拉取
```

这些都属于 L1 adapter 或 L6 调度动作。

## 4.2 L2 输入准入

L2 只接受满足以下条件的输入：

```text
有 asset_id；
有 asset_kind / payload_kind；
有 contract_version；
有 source_ref 或等价 provenance；
有 trace_level；
有基本 scope / time / quality_status；
payload 已由 L1 结构化到可消费形态。
```

不满足条件的输入不进入抽取，只能：

```text
退回 L1 处理；
进入错误队列；
形成人机待办；
或生成 evidence_request 补资料。
```

## 4.3 L2 可以联合多个 data_asset 抽取

L2 不应被限制为“一次只处理一个 document_unit”。

一次 L2 action 可以接收多个 `asset_ref`：

```text
公告里的某个表格 + 表格注释 + 同章节文字；
Q + A；
会议纪要片段 + 附带 Excel 表；
Wind 三大表 snapshot + 财报 document_unit；
web search result + 公司公告相关段落；
同一问题下的多个 tool_result。
```

但这只是运行时 action input，不新增长期 `evidence packet` 对象。

每条输出证据记录只要保留：

```text
primary_asset_ref
supporting_asset_refs
exact_span / locator
producer_action_ref
```

后续自然可以按 source、section、subject、metric、relation、action_log 聚合。

## 4.4 L2 统一输出：evidence_record

L2 不再新增一堆长期对象名，而是统一叫 `evidence_record`。通过 `record_kind` 判别用途。

建议先保留少量 record_kind：

| record_kind | 说明 |
|---|---|
| `observed_claim` | 来源直接支持的自然语言 / 半结构化陈述 |
| `relation_claim` | 来源直接支持的供应、客户、送样、认证、竞争、替代等关系 |
| `numeric_observation` | 标准结构化数据或表格字段形成的观测数值 |
| `source_note` | 有价值但暂不构成 claim 的来源说明或摘要 |
| `null_observation` | 查询未得 / 查空记录 |
| `cold_signal` | 弱信号，暂不采信但可累计触发 |
| `change_candidate` | 人工上传工件或模型输出提出的 L3 / L4 / L5 修改候选，需人批 |
| `discard_log` | 丢弃或不入账原因的轻量记录 |

其中前三类是 L2 主账本核心，后几类是边缘区或治理记录。

## 4.5 文档型 data_asset：高价值选择性 claim 抽取

对 `document_unit`、表格、Q&A、会议纪要、OCR 文本，L2 做高价值选择性抽取。

硬原则：

```text
claim 不是每句话一条。
claim 是可能影响预测、对账、冲突、订阅、复盘或课题推进的证据单元。
```

允许输出：

```text
evidence_records = []
```

这表示当前输入没有达到入账门槛的高价值证据，不需要写成“模型返回无高价值 claim”的复杂语义对象。

抽取准入优先看：

- 是否可能影响收入、价格、订单、产能、良率、成本、费用、毛利率、现金质量、客户结构、供应关系；
- 是否可能改变公司 / 行业 / 主题 / 宏观的关键关系；
- 是否与披露锚、历史证据或当前假设冲突；
- 是否未来能被财报、公告、调研验证；
- 是否能触发 L3 派生、L5 假设或人机待办。

泛泛背景、重复观点、寒暄、无预测价值的行业常识，不进入正式 observed_claim。

## 4.6 标准结构化数据：不做 LLM claim 抽取

Wind / iFinD / Choice / Tushare / 第三方结构化数据库返回的数据，不应让 LLM 从文本里“抽 claim”。

路径应是：

```text
L1 dataset_snapshot
→ L2 numeric_observation / source_note / null_observation
→ L3 canonical financial facts / derived facts
```

可以说逻辑上接近 L1 → L3，但工程上不能绕过 L2 准入。L2 要记录：

```text
provider
query_params
as_of_time
field_mapping
period
source_tier
trace_level
口径说明
quality_status
```

例如 Wind 三大表：

```text
L1：登记 provider、dataset、query、取数时间、返回字段、provider 版本或口径说明。
L2：形成 numeric_observation，不做 LLM claim 抽取。
L3：按口径契约生成标准化财务事实、同比环比、扣非、利润桥和派生指标。
```

## 4.7 轻载外部来源：先是 data_asset，不直接是证据

Claude / Codex / MCP / web search / 插件返回结果进入 L1 时，先是 `data_asset(asset_kind=tool_result)`。

L2 只在满足以下条件时，把它提升为证据：

```text
有可定位来源；
有可复查片段或引用；
能区分 agent 总结与原始来源；
能识别 source_tier / trace_level；
能进入 raw + normalized 双轨。
```

硬边界：

> agent 的总结不是来源；agent 总结引用的网页、PDF、API 结果、数据库返回，才是来源。

如果没有 locator、snippet、URL、数据库 query、文件引用等支撑，只能进入 `cold_signal` 或 `todo`，不能直接 accepted。

## 4.8 人工上传：入口统一，不单独开体系

人工上传资料先进入 L1 upload / artifact adapter，再变成统一 `data_asset`。

按内容性质分流：

```text
人工会议纪要 / 调研笔记 / 专家转写 → document_unit → L2 observed_claim
人工整理表 / 原始数据摘录 → dataset_snapshot 或 document_unit(table) → L2 numeric_observation / observed_claim
人工利润桥 / 手工模型 / 勾稽计算 → artifact_unit → L2 change_candidate / todo
人工框架建议 / 投研模板 → artifact_unit → L2 change_candidate / todo
人工假设输入 → artifact_unit → L2 change_candidate / todo
```

不能让人工上传的 Excel 或模型表直接改 L3 / L4 / L5。

对 L3 / L4 / L5 的修改，应先变成：

```text
change_candidate(target_layer=L3/L4/L5)
→ 人批
→ 对应层更新
→ M-LOG 留痕
```

这可以避免人工文件绕过证据链、口径契约和复盘机制。

## 4.9 raw + normalized 双轨

每条主证据记录至少应有 raw 与 normalized 两层。

```text
raw：原文怎么说
normalized：系统为了对账、检索、冲突和派生如何规范化
```

示例维度：

```text
raw_subject_text       → canonical_subject_ref
raw_metric_text        → metric_ref
raw_value              → normalized_value
raw_unit               → normalized_unit_ref
raw_time_text          → normalized_time / period_ref
raw_relation_text      → relation_type_ref + role mapping
raw_statement          → normalized_statement
```

normalized 不能新增原文没有的事实。它只做最小必要标准化。

## 4.10 L2 数据目录和检索键

L2 很快会变大，必须从第一天设计数据目录和索引键。

建议最小检索键：

```text
subject_key        公司 / 产品 / 平台 / 客户 / 供应商 / 行业 / 主题
subject_domain     company / industry / macro / theme / product / customer / supplier
metric_key         收入 / 毛利率 / 价格 / 订单 / 产能 / 良率 / 费用率等
relation_key       supply / sample / qualification / purchase / compete / substitute 等
period_key         2026Q1 / 2026FY / 2027E / event_date
scope_key          产品 / 区域 / 客户 / 业务线 / 合并范围 / 口径
source_key         source_tier / trace_level / provider / material_type
status_key         pending / accepted / contested / rejected / cold / todo
semantic_key       语义聚合键，用于同一类 claim 去重与召回
```

L2 catalog 的目的不是复杂搜索体验，而是支撑：

- L3 派生取数；
- L5 订阅和失效；
- 冲突检测；
- as-of 复盘；
- 人工调研前快速定位证据。

# 5. 规范库 / Registry：L2 归一化的支撑层

## 5.1 Registry 的定位

Registry 是 L4 中的规范库，工程上可以是数据库 / 服务 / 配置文件组合。

它不是世界事实库，也不是投资框架库。它支撑的是：

```text
raw data → normalized data
```

重点解决主体、单位、时间、指标、关系、口径的统一。

## 5.2 第一阶段需要的 registry

### 5.2.1 Subject Registry

解决“这是不是同一个对象”。

例如：

```text
Rubin
NVIDIA Rubin
Rubin GPU
Rubin server
Rubin 服务器
英伟达 Rubin 平台
```

这些不一定全部等价。Registry 要能表达：

```text
canonical_name
aliases
entity_type
parent / child
owner / issuer
valid_from / valid_to
ambiguous_flag
mapping_confidence
```

Rubin 服务器、Rubin GPU、Rubin 平台不能无脑合并。它们可能影响完全不同的产业链映射。

### 5.2.2 Unit Registry

解决单位标准化和可换算边界。

单位不是只存“中文名 → 英文名”。需要至少区分：

```text
exact_convertible       元 / 万元 / 亿元；吨 / 千克
scale_convertible       片 / 万片；平方米 / 万平方米
context_convertible     张 / 片 / 台 / 柜，需要行业对象才能换算
not_convertible         GPU 片 / 晶圆片 / PCB 张 / 服务器台，不能直接换
ambiguous               原文单位不清或上下文缺失
```

示例：

```text
100 万张 PCB
→ raw_unit=万张
→ normalized_unit=张
→ conversion_status=scale_convertible

1 台 Rubin 服务器
→ 不能直接换算成 GPU 片、HBM 颗数、PCB 张数
→ conversion_status=context_convertible / not_convertible
```

### 5.2.3 Time / Period Registry

建议固定格式：

```text
date: YYYY-MM-DD
quarter: YYYYQn，例如 2026Q1
fiscal_year: YYYYFY，例如 2026FY
forecast_period: YYYYE / YYYYQnE，例如 2027E、2027Q1E
as_of_time: ISO-8601 timestamp
```

相对时间必须记录解析基准：

```text
raw_time_text = 明年
source_publish_time = 2026-06-30
normalized_time = 2027FY 或 2027
relative_time_basis = source_publish_time
```

### 5.2.4 Metric Registry

解决指标归一：

```text
收入 / 营收 / sales / revenue
毛利率 / gross margin
出货量 / shipment volume
产能 / capacity
良率 / yield
ASP / 单价
```

每个 metric 至少要有：

```text
metric_id
canonical_name
dimension
allowed_units
period_type
aggregation_rule
口径约束
```

### 5.2.5 Relation Registry

解决关系方向和阶段。

例如：

```text
A 公司给康宁提供 100 吨 X 物料
康宁获得 A 公司试样 X 物料 20 吨
```

不能简单判冲突。应先归一成：

```text
supplier = A
customer = 康宁
material = X
relation_type = supply / sample_delivery / qualification / purchase
relation_status = formal_supply / sample / trial / qualified / mass_production
quantity = ...
time = ...
```

Relation Registry 至少要有：

```text
relation_type
role_schema
allowed_status
inverse_mapping
conflict_scope
```

### 5.2.6 Scope / 口径 Registry

口径包括：

```text
合并 / 单体
含税 / 不含税
人民币 / 美元
财报口径 / 扣非口径
产品口径 / 业务线口径
自然年 / 财年
出货 / 收入确认
样品 / 小批量 / 量产
```

L2 不需要一开始做很全，但必须能把未知口径标记出来，而不是默认为同口径。

## 5.3 Registry 的更新机制

Registry 必须支持演进，但不能让 agent 随意改。

建议规则：

```text
L2 抽取遇到未知主体 / 单位 / 指标 / 关系：
→ 生成 registry_candidate
→ 可临时使用 raw_text + provisional normalized value
→ 进入 todo 或低风险自动合并规则
→ 重要对象由人批
→ registry 升版后触发相关 evidence_record 重新归一或标记 stale
```

Registry 更新是系统质量提升的核心动作之一。它不应作为“儿戏式标签表”，而应是 L2 / L3 / L5 可复盘的标准化支撑。

# 6. 模型和规则追溯：保持轻量

上一版写得过重。v0.7 改成轻量追溯。

## 6.1 每条 claim 不重复塞完整 run 元数据

每条 `evidence_record` 只需记录：

```text
producer_action_ref
model_ref（可选，可从 action 继承）
rule_bundle_ref（可选，可从 action 继承）
```

完整执行信息在 M-LOG / action_log 里：

```text
action_id
input_asset_refs
output_record_refs
action_type
executor_type: code / llm / human / hybrid
model_ref: provider + model name + model version/snapshot
rule_bundle_ref: prompt / rules / parser config / extraction spec 的版本引用
started_at / finished_at
status
error_summary
```

如果是纯规则或代码动作：

```text
model_ref = null
code_ref / rule_bundle_ref = versioned reference
```

## 6.2 prompt_version / schema_version 不作为默认字段

除非某个阶段确实需要细分，否则不在每条记录里默认保存：

```text
prompt_version
schema_version
validator_version
temperature
decoding_config
```

这些可以作为 `rule_bundle_ref` 或 action_log 的可选扩展。

目标是能回答：

```text
这条证据由哪个模型、哪套规则、哪些输入生成？
```

而不是为了低频审计把所有技术参数塞进主账本。

# 7. L3 与新 L1 / L2 的对接

L3 的定位不在本轮大改，只做对接修正。

## 7.1 L3 输入不只来自 observed_claim

L3 可以吃三类 L2 证据记录：

```text
observed_claim / relation_claim
numeric_observation
accepted / contested / scenario-set 证据视图
```

例如：

```text
Wind 三大表 dataset_snapshot
→ L2 numeric_observation
→ L3 canonical financial fact / 利润桥 / 同环比 / 扣非重构
```

这不是绕过 L2，而是绕过 LLM claim 抽取。

## 7.2 L3 不直接吃 raw L1

L3 不直接处理 raw PDF，也不直接把 web search result 总结成 derived fact。

L3 可通过 L2 证据回溯到 L1 asset / source_ref，但不应跳过 L2 准入、采信和冲突状态。

## 7.3 L3 derived claim 保留原 v0.6 边界

```text
来源直接说的 → L2
系统按规则推出来的 → L3
框架模板 / normalization registry / 对账规则 → L4
模型采用的预测输入 → L5 假设账本
```

例如：

```text
L2：纪要说 A 公司向苹果送样。
L2：公告说某产线已投产。
L2：Wind 返回 2025FY 营收。

L3：系统派生 A 公司苹果链收入暴露度。
L3：系统重构某产品 2027E 收入区间。
L3：系统计算对账后毛利率区间。
```

# 8. 拉式回路：evidence_request

## 8.1 evidence_request 的定位

`evidence_request` 不是新层，也不是 L2 独有对象。

它由 L6 根据 L3 / L5 / 人工问题生成，用来控制“缺资料时怎么拉数据”。

```text
L5 假设缺口 / L3 派生缺口 / L2 冲突缺口 / 人工问题
→ L6 生成 evidence_request
→ L1 获取或登记 data_asset
→ L2 准入与证据化
→ L3 派生
→ L5 更新假设或生成待办
```

## 8.2 evidence_request 应绑定目标

禁止无边界搜索。每个 request 至少绑定：

```text
target_subject
目标变量 / 预测节点 / 派生对象
缺口类型：值缺口 / 结构缺口 / 冲突缺口 / registry 缺口
允许来源层级
优先 adapter
返回要求：必须形成 data_asset，重要证据必须有 source_ref / locator
是否允许轻载外部来源
是否需要人工审批
```

例如：

```text
目标：某公司 2027E Rubin 相关收入假设
缺口：Rubin 服务器出货量、公司供应关系、单机价值量、产品送样状态
来源优先级：公告 / 投关 / 卖方纪要 / Wind / web
返回要求：全部登记为 data_asset；L2 只接受有 locator 的 claim
```

# 9. 标准流程替换

## 9.1 自维护文档型流程

```text
raw PDF / Word / 图片 / 人工文本
→ L1 adapter 解析和载体规范化
→ document / processing_run / document_unit data_asset
→ change feed 通知 L2
→ L2 选择相关 asset 或多 asset 联合抽取
→ evidence_record: observed_claim / relation_claim / numeric_observation / cold_signal / discard_log
→ L2 去重、归一、对账、冲突、采信
→ L3 派生
→ L5 假设或待办
```

## 9.2 标准结构化数据流程

```text
API / 数据库查询
→ L1 dataset_snapshot data_asset
→ L2 numeric_observation 准入
→ L3 canonical facts / derived facts
→ L5 消费
```

## 9.3 轻载外部来源流程

```text
web / MCP / Claude search / Codex search / 插件
→ L1 tool_result data_asset
→ L2 检查 locator / snippet / query / source_tier / trace_level
→ 可追溯则转 observed_claim / relation_claim / source_note
→ 不足则 cold_signal / todo / discard_log
```

## 9.4 人工上传流程

```text
人工上传文件 / 文本 / 表格 / 图片 / 模型表
→ L1 upload adapter 形成 data_asset
→ L2 按内容性质转 evidence_record
→ 若是框架 / 假设 / 模型修改建议，则形成 change_candidate
→ 人批
→ L3 / L4 / L5 更新
→ M-LOG 留痕
```

## 9.5 混合输入抽取流程

```text
evidence_request 或人工动作
→ L1 / catalog 召回多个 data_asset
→ L2 action 接收 multiple asset_refs
→ 联合抽取 / 对账 / 归一
→ 输出多条 evidence_record
→ 每条 evidence_record 指向 primary_asset_ref + supporting_asset_refs
```

不创建长期 packet 对象。

# 10. L2 / L3 / L5 的追溯方式

不要让每层复制全链路字段。

采用：

```text
正常消费看一跳；审计追溯递归解析全链。
```

具体为：

```text
L2 evidence_record → L1 data_asset / source_ref
L3 derived_claim → L2 evidence_record / current_view / L4 rule refs
L5 assumption → L3 derived_claim / L2 evidence_record（必要时）/ L4 framework refs
snapshot → L5 assumption / L3 view / L2 view / contract refs / action_log
```

也就是说：

- L2 需要能看到 L1；
- L3 平时消费 L2，但可通过 L2 回查 L1；
- L5 平时消费 L3，但正式快照必须能递归追到 L2 / L1；
- 全链路由 references 和 action_log 解析，不在每层冗余存一遍。

# 11. v0.7 需要写入硬边界

建议把以下边界加入 v0.7 的硬边界章节：

1. `document_unit` 不是 L1 的唯一出口；L1 的统一出口是 `data_asset` 信封。
2. `source_ref` 是 data_asset 的 provenance 引用，可以由视图或 endpoint 派生，不要求作为独立对象存储。
3. L2 不能处理 raw PDF、raw OCR、raw image、raw audio、raw Excel；这些必须先经 L1 adapter 规范化。
4. L2 可以联合多个 L1 data_asset 抽取证据，但不新增长期 claim packet / evidence packet。
5. 删除 A / B 类清洗叫法；L1 做载体规范化，L2 做证据化和语义归一。
6. claim 抽取是高价值选择性抽取，允许 `evidence_records=[]`。
7. 标准结构化数据跳过 LLM claim 抽取，但不能绕过 L2 准入、口径、来源和追溯。
8. tool / web / MCP / Claude / Codex 结果先是 L1 data_asset，不是证据；agent 总结不是来源。
9. 人工上传先进入 L1，按内容性质变成 data_asset；对 L3 / L4 / L5 的修改建议先成为 change_candidate，需人批。
10. Registry 是 L4 规范库，支撑 raw → normalized，不是事实库。
11. 模型追溯轻量化：主账本引用 producer_action_ref；action_log 记录 model_ref 与 rule_bundle_ref。
12. 上层正常消费一跳，审计时递归追溯全链。
13. L2 / L3 / L5 的检索和订阅依赖 subject / metric / period / relation / scope / source / status 等稳定 keys，从第一天建立数据目录意识。

# 12. 对 v0.6 文档的具体替换建议

## 12.1 替换 §1.2 L1 / L2 / L3 的本质关系

建议改成：

```text
L1 = 来源资产层：把外部资料、结构化数据、工具结果、人工上传件转成可追溯、可消费、可增量感知的 data_asset。
L2 = 观测证据层：从 L1 data_asset 中吸收高价值信息，形成 observed / numeric / relation evidence，统一主体、时间、单位、指标、关系和口径，维护采信、冲突、冷存和待办。
L3 = 派生证据层：基于 L2 当前证据视图和 L4 规则 / registry / 口径契约，生成公司、行业、主题、宏观层面的 derived claims、canonical facts 和对账后事实。
```

## 12.2 替换 §2.2 L1 的数据资产分型

用 `data_asset` 信封替代“几类 payload 各自一套”的写法。

建议写：

```text
L1 不强制所有来源转成 document_unit。
L1 强制所有来源转成 data_asset。
```

然后保留少量 `asset_kind`。

## 12.3 替换 §3.2 / §3.4 L2 输入与标准处理链

建议改成：

```text
L2 接收 L1 public views / API / change feed 暴露的 data_asset，不接收 raw data。
L2 标准链路：

L1 data_asset / multiple data_assets
→ 输入准入
→ 高价值选择性抽取 / 数值观测登记 / 工具结果准入 / 人工工件候选分流
→ raw + normalized 双轨
→ registry 归一
→ 去重与新旧判断
→ 披露锚对账
→ 冲突检测
→ 置信度与重要性
→ 分流到 evidence_record / current_view / cold / todo / discard
```

## 12.4 删除 §3.5 轻处理与 B 类语义清洗

整节删除，替换为：

```text
L2 不生成独立“语义清洗后文本”。
语义理解、主体识别、时间识别、指标识别、关系识别和 claim 抽取是同一个证据化动作的不同输出。
规则负责约束、校验、归一和拒绝；LLM 负责候选理解和结构化。
```

## 12.5 增加 Registry 章节

建议放在 L4 内，标题为：

```text
## L4.x 规范库 / Registry
```

并说明它只解决 raw → normalized，不装事实、不装投资判断。

## 12.6 调整 §9 标准流程

把单一路径入库改成四条路径：

```text
自维护文档型流程；
标准结构化数据流程；
轻载外部来源流程；
人工上传流程；
混合输入抽取流程。
```

# 13. 一句话收口

v0.7 的重点不是新增更多对象，而是把 L1 / L2 的协议收成一套简单、稳定、可扩展的范式：

```text
L1：所有来源都变成 data_asset 信封；raw data 在 L1 截止。
L2：只吸收 data_asset，做高价值证据化、归一、对账、冲突和采信。
L3：基于 L2 和 L4 构造公司 / 行业 / 主题 / 宏观的派生事实。
L4：提供 registry、口径契约、框架和规则。
L5：只消费可追溯的派生证据和假设，不直接相信资料或 agent 总结。
L6：通过 evidence_request、change feed、action_log 和失效队列把全链路串起来。
```

这一版比上一版 v0.7 更少对象、更像协议、更贴近你已经在做的 `disclosure_anchor` 形态，也更适合未来包装成 API / MCP resource 给其他服务使用。
