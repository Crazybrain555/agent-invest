# AI Agent 投研预测引擎顶层框架协议 v0.7 升级修改稿

> 用途：本文件不是重新写一份完整 v0.7 正文，而是给出从 v0.6 升级到 v0.7 时应当替换、增补、删除的架构级修改稿。  
> 范围：仍然只讨论顶层架构和层间职责，不写代码、不写 SQL、不写详细 schema、不写目录结构。  
> 核心目标不变：系统唯一正式产出是公司未来财务预测，当前阶段聚焦契约口径下未来季度 / 年度净利润预测。

---

## 0. v0.7 的核心改动一句话

v0.6 已经把 L2 / L3 拆清楚：

```text
L2 = 观测证据层：来源直接说了什么；
L3 = 派生证据层：系统基于证据和规则构造出了什么。
```

v0.7 继续补上一个更底层的工程现实：

```text
L1 的统一出口不是 document_unit，而是 source_ref + typed payload；
document_unit 只是 typed payload 的一种。
```

因此 L2 也不能再被写成“接收 document_unit 后抽 claim”的单一路径，而应被定义为：

```text
L2 = 证据入口路由 + 观测证据账本。
```

它既要能处理 PDF / 纪要 / OCR / 文本这类文档型输入，也要能处理 Wind / iFinD / Choice / Tushare 这类结构化数据，还要能处理 web / MCP / Claude / Codex / API 工具返回、人工上传表格、人工计算工件等复杂输入。

---

# 1. v0.7 版本说明替换稿

建议将 v0.6 的“版本说明”替换为以下内容。

## 版本说明

v0.7 基于 v0.6 继续收口，核心调整不是推翻 L2 / L3 拆分，而是进一步修正 L1 / L2 的输入契约和处理边界。

v0.6 的主要改动是把原来混在 L3 的证据体系拆成：

1. **L2 观测证据层**：维护来源直接支持的 observed claims、当前采信视图、冲突状态、关系型 claims、人工裁决和冷存；
2. **L3 派生证据层**：维护 derived claims、归一化事实、对账后事实、关系网络派生视图和跨公司 / 行业 / 主题 / 宏观的派生证据。

v0.7 保留这个判断，但进一步修正四个问题：

1. **L1 的统一出口不是 document_unit，而是 source_ref + typed payload。**  
   document_unit 只适合公告、财报 PDF、会议纪要、OCR 文本、人工上传文本等自维护文档型来源。标准结构化数据、web / MCP / agent harness 返回、人工计算表格不应被强行转成 document_unit。

2. **L2 不再被写成单一“文本 claim 抽取流水线”。**  
   L2 的入口先做证据路由：判断 typed payload 的形态，再选择文档 claim 抽取、结构化观测登记、轻载外部来源准入、人工工件分流等路径。

3. **删除“B 类语义清洗”作为独立中间层的表述。**  
   L2 不生成一份“语义清洗后文本”作为核心资产。语义归一发生在 claim 抽取和结构化过程中。claim 抽取、主体识别、时间识别、指标识别、口径识别、单位归一和关系解析通常是同一次 LLM 语义理解动作的不同输出，再由规则、目录和校验器约束。

4. **引入 evidence_request、structured observation、tool_observation、extraction_run / derivation_run 等关键概念。**  
   预测缺口通过 evidence_request 发起拉式取证；标准结构化数据可绕过 LLM claim 抽取，但不能绕过 L1 / L2 追溯登记；web / MCP / Claude / Codex 的输出先作为 tool_observation 登记，agent 总结本身不是来源；所有模型参与生成的 L2 / L3 产物必须记录模型、prompt、schema、规则和运行版本。

v0.7 的主链路调整为：

```text
L1 source_ref + typed payload
→ L2 evidence intake / observed claims / structured observations
→ L3 derived claims / canonical facts / reconstructed views
→ L5 assumptions / driver tree / forecast nodes
→ forecast snapshot
```

这版文档仍然不写代码、不写 SQL、不写详细 schema、不写目录结构，只锁定顶层架构、层间职责、运行机制和硬边界。

# 2. 系统宪法需要补充的原则

v0.6 的系统宪法大体保留，但建议在 §0.4 “设计原则”中做以下替换和增补。

## 2.1 替换“LLM 不做确定性工作”的表述

v0.6 原句：

```text
LLM 不做确定性工作：能用确定性规则做的，不交给 LLM。LLM 主要负责抽取、归纳、消歧、提出候选解释和生成待办。
```

建议改成：

```text
LLM 负责语义候选，规则负责约束、校验、归一和拒绝。

能确定性完成的动作不交给 LLM，例如文件哈希、来源登记、证券代码精确匹配、数值单位可精确换算、数据服务字段校验、版本记录等。

但非结构化文本中的 claim 抽取、主体消歧、时间指代解析、关系识别、口径判断、观点与事实区分，通常需要 LLM 参与。LLM 的输出只是候选，必须经过原文锚定、结构化校验、来源等级、置信度规则和冲突检测后，才允许进入 L2 长期资产。
```

## 2.2 新增原则：source_ref 是共同锚点

```text
source_ref 是所有来源进入系统的共同锚点。

document_unit、dataset_snapshot、query_result、tool_observation、artifact_ref 都只是 source_ref 下的不同 payload 形态。

系统不要求所有来源都转成 document_unit，但要求所有进入预测链的证据都能追到 source_ref。
```

## 2.3 新增原则：claim 是高价值证据单元，不是逐句切片

```text
claim 不是每句话一条，也不是全文知识图谱化结果。

claim 是可能影响预测、冲突、对账、订阅、复盘或研究课题的证据单元。L2 抽取时允许模型返回“无高价值 claim”。宁可早期少抽高价值 claims，也不要把 L2 做成无边界碎片库。
```

## 2.4 新增原则：raw + normalized 双轨

```text
主体、时间、单位、数值、关系、口径必须保留 raw + normalized 双轨。

raw 负责还原来源原始表达；normalized 负责系统计算、检索、对账和传播。normalized 不能新增原文没有的事实，也不能覆盖 raw。
```

## 2.5 新增原则：模型产物必须有 run 追溯

```text
所有由模型生成或模型参与生成的 L2 / L3 对象，都必须能追到对应的 extraction_run 或 derivation_run。

run 记录模型、provider、模型版本或快照、prompt 版本、schema 版本、规则版本、校验器版本、运行时间和输入范围。否则模型升级后无法判断差异来自来源变化、模型变化、prompt 变化还是规则变化。
```

# 3. 总体形态建议修改

v0.6 总体主图可保留，但建议把 L1 和 L2 的名称及箭头语义改得更明确。

## 3.1 主图建议替换为

```text
                        ┌────────────────────────┐
                        │  L4 知识与规则层         │
                        │  框架库 / 规则工件库     │
                        │  规范库 / registry      │
                        └───────────┬────────────┘
                                    │ 加载规则 / 引用框架 / 引用规范
                                    ▼
┌────────────────┐    ┌────────────────────┐    ┌────────────────────┐    ┌──────────────┐    ┌──────────────┐
│ L1 来源资产层   │ -> │ L2 证据入口与观测层 │ -> │ L3 派生证据层       │ -> │ L5 公司预测层 │ -> │ 预测快照      │
│ source_ref     │    │ intake + observed  │    │ derived / canonical│    │ 驱动树/假设   │    │ 正式/影子     │
│ typed payload  │    │ claims / obs       │    │ facts / views      │    └──────────────┘    └──────────────┘
└────────────────┘    └────────────────────┘    └────────────────────┘            │
        ▲                         ▲                         ▲                    │
        │                         └────── evidence_request / 课题取证 ────────────┘
        │
        └──────── PDF / 公告服务 / API / Wind / web / MCP / Claude / Codex / 人工上传 / Excel / OCR

               ┌──────────────────────────────────────────────┐
               │ L6 调度脊柱：感知 / 触发 / 准入 / 行动 / 队列 │
               └──────────────────────────────────────────────┘
```

## 3.2 L1 / L2 / L3 的关系改写为

```text
L1 = 来源资产层：数据从哪里来，以什么形态进入，能否追溯。
L2 = 证据入口与观测证据层：什么可以进入证据循环，来源直接支持了什么。
L3 = 派生证据层：系统基于 L2 观测证据、结构化观测数据和 L4 规则构造出了什么。
```

其中：

```text
source_ref 是 L1 到 L2 的共同锚点；
document_unit 是文档型 payload 的最小追溯单元；
structured observation 是标准结构化数据经过 L2 准入后的观测资产；
observed claim 是来源直接支持的自然语言 / 半结构化证据；
derived claim / canonical fact 是 L3 基于规则、契约、对账和计算形成的派生资产。
```

# 4. L1：来源资产层修改稿

建议将 v0.6 第 2 章改成以下方向。

## 4.1 L1 的定位

L1 是系统把外部输入变成**可引用、可复查、可追溯、可进入 L2 准入的来源资产**的逻辑层。

L1 不等于公告 PDF 服务，也不等于 document_unit 生产层。`disclosure_anchor` 只是 L1 中负责上市公司公告 / 财报 PDF 的自维护文档型路径。

L1 负责回答：

- 数据来自哪里；
- 通过什么 adapter / provider / tool / human channel 取得；
- 什么时候取得；
- 查询参数、访问工具、provider 版本、parser 版本是什么；
- 是否保存原始字节、快照或返回记录；
- 下游通过什么 source_ref 和 payload 消费。

L1 不负责：

- 判断投资重要性；
- 抽取 claim；
- 判断冲突；
- 生成当前采信视图；
- 生成 derived claims；
- 修改假设或预测。

## 4.2 L1 的统一出口：source_ref + typed payload

v0.7 应明确：

```text
所有来源都必须形成 source_ref；
不是所有来源都必须形成 document_unit。
```

L1 输出的统一结构是概念上的：

```text
source_ref + typed payload
```

其中 typed payload 至少分四类。

| payload 类型 | 适用来源 | L1 产物 | L2 处理路径 |
|---|---|---|---|
| document_payload | 公告、财报 PDF、纪要、OCR 文本、人工上传文本、PPT / Word 转写 | document、document_unit、unit_context、parser_run | 文档型 claim 抽取 |
| dataset_payload | Wind / iFinD / Choice / Tushare、券商库、政府统计、协会数据、海关数据 | dataset_snapshot / query_result、字段、查询参数、provider 版本 | 结构化观测准入，不走 LLM claim 抽取 |
| tool_observation_payload | web search、MCP、Claude / Codex web、插件返回、API 工具返回 | tool_observation、query、tool、返回摘要、locator、citation、raw response 可选 | 轻载外部来源准入，必要时抽 claim 或进冷存 |
| artifact_payload | Excel 勾稽表、人工计算表、模型表、调研问题清单、图片 OCR 后结果 | artifact_ref、文件 hash、表格结构、作者、时间、内容性质标记 | 按内容性质分流到 L2 / L3 / L5 |

## 4.3 document_payload：自维护文档型来源

文档型来源仍然需要 document_unit，而且要比 v0.6 更重视结构上下文。

L1 应尽量给每个 document_unit 提供结构上下文，但不做投资语义判断。

### document 级上下文

```text
source_ref
source_type
title
company_code / company_name
announcement_date / publish_time / meeting_time
report_period
file_hash
parser_version
provider / channel
```

### document_unit 级上下文

```text
unit_id
unit_type：title / paragraph / table / table_row / q / a / list / note / image_caption
unit_text
page_no / bbox，可选
sequence_index
parent_unit_id
section_path
table_id / table_title / row_header / col_header / unit_hint
qa_group_id
previous_unit_id / next_unit_id
raw_text_span / normalized_text_span
```

L1 可以做：

- PDF 解析；
- 表格结构保留；
- 标题路径保留；
- Q&A 绑定；
- 段落顺序和前后关系；
- 页眉页脚、水印、页码、控制字符等确定性清理；
- 文件 hash 和 parser_run 记录。

L1 不做：

- 这是订单 claim；
- 这是 Rubin 主题；
- 这是苹果链机会；
- 这是高价值信息；
- 这是需要进入 L5 的假设。

一句话：

```text
L1 负责让 unit 不孤立；L2 负责理解 unit 在说什么。
```

## 4.4 dataset_payload：标准结构化数据

标准结构化数据不应强行转成 document_unit，也不应交给 LLM 从文本里抽 claim。

例如：

- Wind 三大表；
- iFinD 财务字段；
- Choice 行业数据；
- Tushare 结构化数据；
- 券商数据库导出的标准字段；
- 政府 / 协会提供的标准序列。

L1 需要保留：

```text
source_ref
provider
dataset_key
query_parameters
query_time
as_of_time
returned_fields
provider_version / adapter_version
raw_result 或可复查结果摘要
```

后续路径是：

```text
L1 dataset_payload
→ L2 thin evidence gate / structured observation
→ L3 canonical financial facts / derived facts
→ L5 assumptions / forecast nodes
```

注意：结构化数据可以绕过 L2 的 LLM claim 抽取，但不能绕过 L2 的证据准入和来源登记。

## 4.5 tool_observation_payload：轻载外部来源

web / MCP / Claude / Codex / 插件返回，不能直接当系统证据。

它们首先是 tool_observation。

tool_observation 至少要记录：

```text
source_ref
who_or_what_called_it
call_time
tool_name / harness
query / prompt / parameters
returned_items
source_locator：URL / title / citation / chunk_id / snippet / provider_result_id
raw_response，可选
model_or_tool_version，可选
```

硬边界：

```text
agent 的总结不是来源；agent 总结里引用的网页、PDF、API 返回、数据库返回、原文片段才是来源。
```

如果 tool_observation 没有可定位来源或片段，只能作为低追溯线索，进入冷存或待办，不能直接成为 accepted claim。

## 4.6 artifact_payload：人工上传和人工计算工件

人工上传不按文件类型决定层级，而按内容性质分流。

同样是 Excel，可能有三种性质：

```text
来源陈述：卖方给的分业务预测、调研得到的订单数据、公司披露数据摘录 → L2；
计算派生：你自己做的利润桥、口径重构、勾稽测算 → L3；
模型假设：你手工设定的 ASP、毛利率、出货量假设 → L5。
```

因此 L1 对人工工件只负责登记：

```text
artifact_ref
source_ref
文件 hash
作者 / 上传人
产生时间 / 上传时间
资料类型
涉及公司 / 行业 / 主题候选
是否原始来源 / 转述 / 计算产物 / 模型假设
可复核性
敏感标记
```

具体进入 L2、L3 还是 L5，由 L2 入口准入和人工标记共同决定。

# 5. L2：证据入口与观测证据层修改稿

建议将 v0.6 第 3 章重写为以下方向。

## 5.1 L2 的定位

L2 是系统的证据入口、消化系统和免疫系统。

它负责判断：

```text
什么东西允许进入系统证据循环；
以什么形态进入；
它来自哪里；
是否能追溯；
是否能采信；
是否会与已有证据冲突；
是否可能污染预测。
```

L2 不是单纯的文本抽取层。它长期维护：

- observed claims；
- structured observations；
- 当前采信视图；
- contested / rejected / provisional / scenario-set 状态；
- 关系型 claims；
- 冷存 / 弱信号；
- 人工裁决记录；
- as-of 查询所需的历史视图。

L2 负责回答：

```text
来源直接支持了什么？
这些证据以什么形式进入系统？
当前是否被采信？
是否有冲突？
是否只能冷存或待核验？
```

L2 不负责回答：

```text
系统基于这些证据最终推导出了什么？
```

后者属于 L3。

## 5.2 L2 的输入：source_ref + typed payload

L2 不再只接收 document_unit。L2 接收的是：

```text
source_ref + typed payload
```

并根据 payload 类型走不同路径：

| 输入 | L2 路径 | 产物 |
|---|---|---|
| document_payload | 抽取窗口 → 高价值 claim 抽取 → 校验 / 对账 / 冲突 | observed claims |
| dataset_payload | 字段校验 → 口径 / provider / as-of 登记 → 结构化观测准入 | structured observations |
| tool_observation_payload | 来源定位检查 → 追溯等级判断 → 必要时抽 claim / 冷存 / 待办 | observed claims / cold signal / todo |
| artifact_payload | 内容性质判断 → 来源陈述 / 计算派生 / 模型假设分流 | L2 / L3 / L5 分流 |

这意味着标准结构化数据可以逻辑上走：

```text
L1 → L2 thin gate → L3
```

而不是必须走：

```text
L1 → L2 natural language claim → L3
```

## 5.3 删除“B 类语义清洗”

v0.7 建议从 L2 正文中删除“B 类语义清洗 / 精简”作为独立处理步骤的表述。

不要再写：

```text
轻处理 → B 类语义清洗 → 主体识别 → claim 抽取
```

建议改为：

```text
source_ref + typed payload
→ 证据入口路由
→ 按 payload 类型选择处理路径
→ 对文档型 payload 构造运行时抽取窗口
→ 高价值 claim 选择性抽取
→ 原文锚定
→ raw + normalized 双轨规范化
→ 主体 / 指标 / 时间 / 单位 / 关系 / 口径解析
→ 校验隔离
→ 去重与新旧判断
→ 披露锚对账
→ 冲突检测
→ 置信度与重要性判断
→ 分流：observed claim / structured observation / current view / cold / todo / drop
```

语义归一发生在 claim 化过程中，不形成独立“清洗文本”资产。

## 5.4 抽取窗口：运行时输入，不是长期对象

文档型 payload 中，L2 不应机械地对每个 document_unit 单独抽 claim。

L2 可以在运行时构造 extraction window：

```text
Q + A；
表格标题 + 表头 + 表格行 + 注释；
章节标题 + 下面几个段落；
某段话 + 前后相邻段落；
同一小节下的一组 document_units。
```

extraction window 只是运行时输入，不建议作为长期复杂对象入账。

每条 claim 只需要记录：

```text
source_ref
primary_unit
supporting_units
exact_span
extraction_run_id
```

这样既能让模型看到足够上下文，又不会新增一个容易失控的中间层。

## 5.5 高价值 claim 选择性抽取

L2 抽取 claim 时必须有入账门槛。

claim 不是每句话一条。claim 是可能影响预测、冲突、对账、订阅、复盘或课题的证据单元。

抽取准入建议是：

1. 可能影响公司未来财务预测；
2. 可能影响重要 driver：收入、价格、订单、产能、良率、成本、费用、客户、毛利率、税率、现金质量；
3. 可能改变公司 / 行业 / 主题 / 宏观的关键关系；
4. 可能与披露锚、历史 claim、当前假设或派生证据发生冲突；
5. 未来财报季可能用于验证或归因；
6. 虽然现在不能采信，但足以进入冷存或待办。

普通背景、套话、重复观点、泛泛行业描述，不进入正式 observed claims。

模型必须允许返回：

```text
无高价值 claim。
```

## 5.6 不引入 claim packet

v0.7 不新增 claim packet / evidence packet 对象。

原因：packet 容易混合来源、章节、主题、逻辑链、推票理由、任务批次等不同概念，后续会变成新的混乱对象。

同一来源、同一段逻辑、同一主题下的 claims，可以通过稳定字段自然聚合：

```text
source_ref
document_id
section_path
qa_group_id
primary_unit / supporting_units
extraction_run_id
source_type
subject_domain
primary_subject
metric_type / event_type / relation_type
claim_nature
routing_tags
subscription_keys
```

即：

```text
不新增 packet 对象；
用字段体系和分类体系完成自动聚合。
```

## 5.7 L2 claim 的信息维度

v0.7 建议把 claim 的信息维度分成六组。仍然不是数据库 schema，只是架构层必须保留的信息。

### A. 追溯组

```text
source_ref
primary_unit / supporting_units / source_locator
exact_span / supporting_span
claim_text_raw
claim_text_normalized
extraction_run_id
trace_level
source_tier
```

`claim_text_normalized` 只能做最小必要归一，不能新增原文没有的事实。

### B. 主体与语义组

```text
subject_domain：company / industry / macro / theme / product_platform 等
primary_subject
subject_role
metric_type / event_type / relation_type
claim_nature：fact / estimate / forecast / opinion / rumor / relationship / explanation / assumption / management_quality_opinion
source_stance：公司披露 / 管理层表述 / 卖方判断 / 专家转述 / 市场传闻 / 数据服务字段
statement_direction：上升 / 下降 / 放量 / 进入 / 退出 / 延迟 / 改善 / 恶化等
```

主体不能只写公司。比如：

```text
Rubin 2027 年出货量
```

第一主体可能是：

```text
product_platform = NVIDIA Rubin platform
```

而不是简单写成：

```text
company = 英伟达
```

英伟达是该平台的 owner / ecosystem anchor，但不等于所有 Rubin claim 的 primary_subject。

### C. 数值、时间、单位和口径组

```text
raw_value
normalized_value
raw_unit
normalized_unit
unit_conversion_status：exact_convertible / domain_convertible / ambiguous / not_convertible
raw_time_text
normalized_time
source_publish_time
event_time
period
as_of_time
relative_time_basis
口径标签：财报口径 / 扣非口径 / 产品口径 / 区域口径 / 含税不含税 / 合并单体等
```

时间必须保留解析依据。例如“明年投产”应记录：

```text
raw_time_text = 明年
source_publish_time = 2026-06-30
normalized_time = 2027
relative_time_basis = 以资料时间为基准
```

单位不能乱转。

```text
元 / 万元 / 亿元：通常可精确换算；
吨 / 千克：通常可精确换算；
片 / 张 / 万张：不一定可换算；
GPU 片 / 晶圆片 / PCB 张 / 服务器台：不能直接换算。
```

### D. 关系组

关系型 claim 必须规范化角色和方向。

例如：

```text
A 公司给康宁提供 100 吨 X 物料；
康宁获得 A 公司试样 X 物料 20 吨。
```

不能简单判为同一 claim 或冲突 claim。应解析为：

```text
supplier = A 公司
customer = 康宁
material = X 物料
relation_type = supply / sample_delivery / qualification / purchase / order
quantity = 100 吨 / 20 吨
status = formal_supply / sample / trial / qualified / mass_production
time = ...
```

只有在主体、关系类型、阶段、期间、口径都接近时，才进入冲突判断。

### E. 系统状态组

```text
confidence
claim_status：pending / accepted / contested / rejected / archived / provisional / scenario-set
conflict_status
current_view_status
downstream_refs
routing_tags
subscription_keys
importance_score
需要人工确认与否
```

routing_tags 只用于召回和传播，不能当事实使用。

### F. 模型与运行组

claim 不必重复记录所有模型细节，但必须指向 extraction_run。

extraction_run 至少记录：

```text
model_provider
model_name
model_version / model_snapshot
prompt_version
schema_version
rule_version
validator_version
input_payload_ids
temperature / decoding_config，可选
run_time
executor：code / agent / human-assisted
```

## 5.8 structured observation

对标准结构化数据，L2 不一定产生 natural language claim，而是产生 structured observation。

structured observation 表达的是：

```text
某个 provider 在某个 as-of 时点，按某个 query 和字段口径返回了一组结构化数据。
```

它应至少记录：

```text
source_ref
provider / dataset_key
query_parameters
returned_fields
report_period / data_period
provider_as_of_time
system_access_time
field_level_lineage
provider_version / adapter_version
quality_check_status
口径说明
```

L3 再基于 structured observation 生成：

```text
canonical financial facts
口径重构值
同比 / 环比
扣非口径
财务比率
利润桥节点
```

## 5.9 tool_observation 的准入

web / MCP / Claude / Codex / 插件返回，不应直接进入 accepted claim。

处理原则：

1. 有明确 locator、citation、snippet、URL、结果 ID 的，可以作为 G2 或相应追溯等级进入 L2；
2. 只有 agent 总结、没有可定位来源的，只能进入冷存或待办；
3. 重要结论必须补充更强来源；
4. 任何会影响正式预测的 tool_observation，都必须能追到 source_ref 和原始返回片段。

## 5.10 人工工件的分流

人工上传的内容必须按性质分流：

| 内容性质 | 进入层 | 例子 |
|---|---|---|
| 来源陈述 | L2 | 调研纪要、卖方给的产品送样信息、公司口头表述、专家访谈 |
| 结构化摘录 | L2 structured observation | 手工整理的财报摘录、调研表格原始数据 |
| 计算派生 | L3 | 利润桥计算表、口径重构表、勾稽关系表 |
| 模型假设 | L5 | 手工设定的 ASP、出货量、毛利率、情景参数 |
| 框架规则 | L4 | 行业研究模板、抽取规则、对账规则 |

# 6. L3：派生证据层需要同步修改的点

v0.6 的 L3 主体方向正确，但需要补充结构化观测输入和 run 追溯。

## 6.1 L3 的输入改为四类

v0.6 写的是：

```text
L3 的输入主要来自 L2 当前采信视图、contested claims 和 L4 规则框架。
```

v0.7 建议改为：

```text
L3 的输入来自四类：

1. L2 当前采信视图中的 observed claims；
2. L2 contested / scenario-set claims，用于区间、情景和冲突解释；
3. L2 structured observations，用于生成 canonical facts、财务事实、标准化序列和重构视图；
4. L4 口径契约、对账规则、计算规则、框架条目和规范库。
```

## 6.2 L3 可以生成 canonical facts

标准结构化数据进入 L3 后，常见派生产物不是普通 derived claim，而是 canonical fact。

例如：

```text
Wind 返回某公司 2025A 营业收入；
L2 登记 structured observation；
L3 按口径契约和字段映射生成 canonical revenue fact；
L3 再生成同比、环比、费用率、毛利率、扣非净利润等 derived facts。
```

这类 canonical fact 仍然必须可追溯：

```text
canonical fact
→ structured observation
→ source_ref
→ provider / query / as-of / returned field
```

## 6.3 L3 的 derivation_run

每条 L3 derived claim / canonical fact / reconstructed view 都必须指向 derivation_run。

如果是纯规则计算，derivation_run 记录：

```text
method_version
contract_version
rule_artifact_version
framework_entry_version
input_view_version
validator_version
run_time
```

如果 L3 使用 LLM 做主题映射、关系网络推断、暴露度判断、逻辑归纳，则还要记录：

```text
model_provider
model_name
model_version / snapshot
prompt_version
schema_version
```

## 6.4 L3 不允许绕过 L1 / L2 直接吃外部来源

可以允许 L3 从结构化观测数据直接派生，但不能允许 L3 临时调用 Wind、web 或 agent search 后无登记地生成派生结果。

硬规则：

```text
L3 可以不经过 natural language claim；
但不能不经过 source_ref 和 L2 evidence gate。
```

# 7. L4：增加规范库 / registry

v0.6 的 L4 “框架库 / 规则工件库”保留，但 v0.7 建议在 L4 中显式增加一类：

```text
规范库 / registry
```

它不装事实，而装系统跨层使用的命名、单位、指标、关系和标签规范。

## 7.1 规范库包括

```text
主体目录：公司、子公司、产品、平台、技术路线、客户、供应商、行业、主题；
别名表：Rubin / NVIDIA Rubin / Rubin GPU / Rubin server；
指标目录：收入、ASP、出货量、产能、良率、毛利率、费用率、现金流；
单位规范：元、亿元、吨、片、张、台、柜、bps、百分比；
时间规范：年度、季度、时点、期间、预测期、相对时间解析规则；
关系类型规范：供应、送样、认证、量产、采购、替代、竞争、客户关系；
软标签体系：AI server、Rubin、HBM、ABF、PCB、CCL、散热、电源、光模块等 routing tags。
```

## 7.2 规范库的边界

规范库不应存：

```text
A 公司已经进入苹果链；
B 公司供应英伟达 GB300；
某公司在某环节份额 20%；
某客户订单开始放量。
```

这些是来源直接支持的 observed claims，应放 L2。

规范库可以存：

```text
苹果链是一个客户 / 供应链主题；
Rubin 是 NVIDIA AI 平台相关实体；
AI 服务器研究通常关注 GPU、HBM、PCB、ABF、CCL、光模块、散热、电源、ODM；
送样、认证、量产、正式供货是不同关系阶段。
```

系统推导出的主题暴露、供应链影响、公司映射，属于 L3。

# 8. L6：调度脊柱新增 evidence_request

v0.7 应在 L6 和研究课题中显式加入 evidence_request。

## 8.1 为什么需要 evidence_request

拉式回路不能变成：

```text
agent 缺数据 → 自己上网 → 总结一个答案 → 直接改预测
```

正确链路应是：

```text
L5 假设缺口 / L3 派生缺口 / L2 冲突缺口
→ L6 生成 evidence_request
→ L1 获取或登记来源
→ L2 证据准入
→ L3 派生
→ L5 更新假设
```

## 8.2 evidence_request 的概念字段

这不是详细 schema，只是架构层必须表达的维度。

```text
request_source：来自 L5 假设缺口 / L3 派生缺口 / L2 冲突 / 人工指令 / 财报复盘
目标公司 / 行业 / 主题 / 宏观对象
目标变量 / driver / forecast_node
缺口描述
需要的信息类型：数值 / 关系 / 事件 / 观点 / 口径 / 框架 / 竞品 / 历史数据
优先来源：Tier 0A / 0B / 1 / 2 / F
允许来源与禁止来源
追溯要求：最低 G 几
返回要求：必须形成 source_ref；重要 claim 必须有原文锚或结构化 query 记录
预算：检索轮次、工具次数、人工待办上限
结案条件
```

## 8.3 L6 最小血缘边更新

v0.7 的最小血缘边建议改为：

```text
evidence_request → source_ref
source_ref → typed_payload
source_ref / document_unit / dataset_snapshot / tool_observation / artifact_ref → observed_claim / structured_observation
observed_claim → current_evidence_view
structured_observation → canonical_fact / derived_claim
current_evidence_view / observed_claim → derived_claim
contract / rule_artifact / framework_entry / registry_entry → derived_claim / canonical_fact
observed_claim / structured_observation / derived_claim / canonical_fact → assumption
assumption → forecast_node
forecast_node → snapshot
research_topic → evidence_requests / produced claims / derived claims / assumptions / framework_diffs / rule_diffs
```

# 9. 标准流程需要替换的部分

## 9.1 新入库流程

建议替换 v0.6 §9.1。

```text
资料进入 / 查询产生 / 人工上传 / 工具调用
→ L1 登记 source_ref
→ L1 生成 typed payload
   - document_payload：document / document_unit / unit_context
   - dataset_payload：dataset_snapshot / query_result
   - tool_observation_payload：tool_observation / locator / snippet
   - artifact_payload：artifact_ref / structured_table / file hash
→ L2 evidence intake router 判断 payload 类型
→ 文档型：构造运行时 extraction window → 高价值 claim 抽取
→ 结构化数据型：字段校验 / provider / as-of / 口径登记 → structured observation
→ 轻载外部型：source locator 检查 → 抽 claim / 冷存 / 待办 / 丢弃
→ 人工工件型：按内容性质分流到 L2 / L3 / L5 / L4
→ L2 校验隔离、去重、新旧判断、披露锚对账、冲突检测
→ L2 分流到 observed claims / structured observations / current view / cold / todo / drop
→ L6 判断是否触发 L3 派生或 L5 行动
```

## 9.2 标准结构化数据流程

新增。

```text
L6 或人工发起数据需求
→ L1 调用 provider / adapter
→ 形成 source_ref + dataset_payload
→ L2 thin evidence gate：字段校验、provider 版本、query 参数、as-of、追溯等级
→ 形成 structured observation
→ L3 按口径契约和字段映射生成 canonical facts
→ L3 生成财务比率、同比、环比、利润桥节点等 derived facts
→ L5 消费 canonical / derived facts
```

硬边界：

```text
标准结构化数据不走 LLM claim 抽取；
但不能绕过 source_ref、L2 准入和 as-of 记录。
```

## 9.3 轻载外部来源流程

新增。

```text
evidence_request / 人工检索 / agent harness 调用
→ L1 形成 source_ref + tool_observation
→ L2 检查 source_locator / snippet / citation / raw response
→ 若来源可定位且信息重要：抽 observed claim
→ 若来源弱但有线索：进冷存
→ 若重要但追溯不足：生成人工待办或补证据请求
→ 若无定位、无价值、重复：丢弃并记录原因
```

硬边界：

```text
agent 总结不能直接进入 accepted claim；
只有被登记并可追溯的来源片段、API 返回或原文定位，才能进入证据链。
```

## 9.4 拉式取证流程

建议替换 v0.6 中课题主动找资料的宽泛表达。

```text
L5 假设缺口 / L3 派生缺口 / L2 高重要性冲突 / 人工问题
→ L6 生成 evidence_request
→ 查 L2 当前观测证据、冷存和历史检索记录
→ 查 L3 既有派生证据和 canonical facts
→ 判断是否需要主动取证
→ L1 调用公告服务 / API / web / MCP / 人工上传 / provider adapter
→ 形成 source_ref + typed payload
→ L2 证据准入与分流
→ L3 派生或重算
→ L5 假设更新、影子快照或待办
```

# 11. 当前 disclosure_anchor / L1 PDF 服务的直接影响

你现在正在做上市公司公告 / 财报 PDF 服务。v0.7 对这个服务的影响不是推翻，而是把它在 L1 中的位置说清楚。

## 11.1 继续做扎实 document_unit

公告 / 财报 PDF 属于自维护文档型来源，应该继续产出：

```text
source_ref
document
document_unit
unit_context
parser_run
file_hash
page / table / section / qa / sequence
```

## 11.2 不要把 document_unit 当成全系统唯一输入契约

当前服务只覆盖 L1 的 document_payload 路径。未来还会有：

```text
dataset adapter；
web / MCP / agent observation adapter；
human upload adapter；
artifact adapter。
```

这些不一定产 document_unit。

所以顶层文档不要写死：

```text
L1 输出 document_unit，L2 消费 document_unit。
```

应该写成：

```text
L1 输出 source_ref + typed payload；
document_unit 是 document_payload 的标准组成部分。
```

## 11.3 document_unit 不要切太碎

建议保持：

```text
段落 / 表格 / 表格行 / Q&A / 标题块 / 注释
```

不要默认切到句子级。

原因：

```text
L1 的最小追溯单元不等于 L2 的最小抽取输入；
L2 可以用多个 document_unit 组成运行时 extraction window。
```

## 11.4 L1 只做结构上下文，不做投资语义

L1 可以保留：

```text
资料类型、标题、公司、公告日期、报告期、章节、表格标题、表头、Q&A 关系、前后 unit。
```

L1 不要提前判断：

```text
订单、产能、毛利率、苹果链、Rubin、重要性、进入预测。
```

这些是 L2 / L4 / L5 的职责。

# 12. 硬边界更新稿

建议将 v0.6 的硬边界增补 / 替换为以下条目。

1. 系统唯一正式产出仍是公司未来财务预测；当前阶段是契约口径下净利润预测。
2. 系统不做估值、选股、买卖建议、便宜判断、组合构建。
3. L1 是来源资产层，不是全量 raw data lake。
4. source_ref 是所有来源进入系统的共同锚点。
5. document_unit 不是 L1 的唯一出口，只是 document_payload 的最小追溯单元。
6. L1 输出 source_ref + typed payload；typed payload 至少包括 document_payload、dataset_payload、tool_observation_payload、artifact_payload。
7. 公告 / 财报 PDF 是自维护硬锚，应尽量保存原文、hash、document_unit、parser_run 和结构上下文。
8. 标准结构化数据不走 LLM claim 抽取，但必须经过 L2 thin evidence gate，记录 provider、query、as-of、字段和口径。
9. web / MCP / Claude / Codex / 插件返回首先是 tool_observation，不是系统证据。
10. agent 总结不是来源；agent 总结中可定位的网页、API 返回、PDF、数据库结果、原文片段才可能成为来源。
11. L2 是证据入口与观测证据层，职责包括准入、分流、observed claims、structured observations、当前采信视图、冲突、冷存和人工裁决。
12. L2 不生成独立“B 类语义清洗文本”作为核心资产。
13. claim 抽取是高价值选择性抽取，不是逐句全量抽取。
14. claim 可以来自一个或多个 document_unit，但必须记录 primary_unit、supporting_units 和 exact_span。
15. 不引入 claim packet / evidence packet；用 source_ref、section_path、qa_group_id、subject、metric、relation、routing_tags、extraction_run 等字段自然聚合。
16. claim 必须保留 raw + normalized 双轨，特别是主体、时间、数值、单位、关系和口径。
17. routing_tags 只用于召回和传播，不能当事实使用。
18. 来源直接支持的关系放 L2；系统推导的暴露度、供应链影响、主题扩散放 L3；行业理解模板和规范目录放 L4。
19. L3 可以从 L2 structured observations 生成 canonical facts，不必所有输入都先变成 natural language claim。
20. L3 不能绕过 L1 / L2 直接调用外部来源生成派生事实。
21. 所有模型参与生成的 L2 / L3 产物必须记录 extraction_run 或 derivation_run。
22. run 记录模型、prompt、schema、规则、校验器、provider adapter 和执行时间。
23. L4 除框架库和规则工件库外，增加规范库 / registry，但 registry 不装动态事实。
24. 主体、指标、单位、时间、关系类型、别名、软标签体系进入 L4 registry。
25. 拉式回路通过 evidence_request 控制，不允许 agent 绕过 L1 / L2 直接改预测。
26. 人工上传按内容性质分流：来源陈述进 L2，计算派生进 L3，模型假设进 L5，框架规则进 L4。
27. 高重要性冲突不能吞掉，必须进入 contested、情景、待办、阻塞或人工裁决。
28. 正式快照必须能追到 source_ref、observed claims / structured observations、derived claims / canonical facts、假设、规则、框架和 run 版本。
29. as-of 语义必须覆盖 L2、L3、L5 和快照。
30. 系统控制逻辑必须 harness 无关。

# 13. 术语表增补

建议在 v0.6 术语表中新增或替换以下术语。

| 术语 | 含义 |
|---|---|
| source_ref | 所有来源进入系统的共同追溯锚点，指向一次文件、查询、访问、工具返回或人工上传 |
| typed payload | source_ref 下的具体数据形态，包括 document_payload、dataset_payload、tool_observation_payload、artifact_payload |
| document_payload | 自维护文档型来源的 payload，包含 document、document_unit、unit_context、parser_run |
| document_unit | 文档型来源的最小可追溯结构单元，如段落、表格、Q&A、标题块、注释 |
| unit_context | L1 为 document_unit 提供的结构上下文，如章节、表头、Q&A 绑定、前后关系；不是投资语义标签 |
| dataset_payload | 标准结构化数据的 payload，包含 provider、dataset、query、字段、as-of、返回记录 |
| structured observation | 结构化数据经过 L2 准入后形成的观测资产，可被 L3 派生 canonical facts |
| tool_observation | web / MCP / Claude / Codex / 插件返回在 L1 的记录形态，尚不等于证据 |
| artifact_payload | 人工上传或人工计算工件的 payload，需按内容性质分流到 L2 / L3 / L5 / L4 |
| extraction window | L2 对文档型 payload 运行时组织给模型看的上下文窗口，不作为长期核心对象 |
| extraction_run | 一次 claim 抽取运行，记录模型、prompt、schema、规则、校验器、输入范围和运行时间 |
| derivation_run | 一次 L3 派生运行，记录输入、方法、口径契约、规则、框架、模型和运行时间 |
| canonical fact | L3 基于结构化观测数据和口径契约生成的标准化事实，如标准财务字段、重构值 |
| evidence_request | L6 从预测缺口、派生缺口、冲突或人工问题出发生成的取证需求单 |
| registry / 规范库 | L4 中维护主体、别名、指标、单位、时间、关系类型和软标签的规范资产，不装动态事实 |
| routing_tags | 用于召回和传播的软标签，不能作为事实使用 |

# 14. 一句话收口：v0.7 相比 v0.6 到底改了什么

v0.6 解决的是：

```text
L2 / L3 不能混在一起。
L2 管来源直接支持的 observed claims；
L3 管系统派生出的 derived claims。
```

v0.7 解决的是：

```text
L1 / L2 不能被写成只服务文档的流水线。
L1 的共同锚点是 source_ref；
L1 的输出是 typed payload；
L2 的入口是 evidence intake；
文档 claim 抽取只是 L2 的一条路径；
结构化数据、轻载外部来源、人工工件都必须有各自的准入和分流规则。
```

最终主链路应收成：

```text
L1 source_ref + typed payload
→ L2 evidence intake / observed claims / structured observations
→ L3 derived claims / canonical facts / reconstructed views
→ L5 assumptions / driver tree / forecast nodes
→ forecast snapshot
```

这个版本的重点不是堆更多概念，而是防止两个真实运行时会撞墙的问题：

1. 把所有来源都强行塞成 document_unit；
2. 把 L2 写成无边界的全文 claim 抽取器。

v0.7 的原则是：

```text
来源形态可以复杂；
入口契约必须统一；
claim 抽取必须克制；
结构化数据不必文本化；
外部工具返回不能直接采信；
所有进入预测链的东西都必须能追溯、能校验、能冲突、能失效、能复盘。
```
